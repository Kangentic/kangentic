# Embedded browser decision log

Open questions resolved during the build:

## 1. Cookie isolation

per-task persistent partitions (`persist:kng-<projectId>-<taskId>`). Isolates each task's dev environment so concurrent tasks never share a `localhost` jar, while persisting across restarts. Replaced the original single shared jar when agent automation shipped (the shared jar let an agent read another context's logged-in sessions, and concurrent worktrees clobbered each other's localhost cookies). The key was per-WORKTREE-PATH at first (`persist:kngbrowser-<hash(worktreePath)>`), then re-keyed to task IDENTITY (decision 32) so the jar follows the task through any path change. Refined by decision 33: the `localhost` isolation this entry is about is kept, but NON-localhost (identity-provider) cookies are now shared project-wide, so a Google login is entered once per project rather than once per task.

## 2. Host renderer CSP

not added in this iteration. The webview is process-isolated, so the absence is not a same-origin escape risk. Defense-in-depth pass deferred.

## 3. DevTools exposure

not enabled. Adds a security surface for the inspect feature; not worth it given Inspect mode covers the common need.

## 4. File downloads

unhandled. A page with `<a download>` will trigger Chromium's default behavior (likely route through `defaultSession` to `Downloads/`). Future hardening: explicit `will-download` deny.

## 5. Permissions

all permission requests (camera, mic, geolocation, notifications, ...) are denied via `setPermissionRequestHandler` on the guest session. Hardened when agent automation shipped, since agent-driven navigation could otherwise reach a page that auto-prompts.

## 6. Adapter capability shape

resolved via `getSubmissionVerifier(contextType)` returning a per-context callback. The callback consumes adapter-specific signals (e.g. Claude's JSONL transcript for command-injection) and returns a boolean.

## 7. Pop-out window

shipped, built as a child `BrowserWindow` exactly as this entry originally proposed, rather than retrofitting re-parenting. A `<webview>` guest's lifetime is bound to its DOM node, so moving the pane between hosts destroys and recreates the guest; the pop-out therefore mounts a fresh `BrowserPane` whose new guest registers under a NEW surface handle (the in-app pane's handle retires and answers `surface-gone` pointing at the pop-out's). The outgoing in-app pane's unmount unregisters only the guest id it registered, which is what stops it clobbering the newer registration. See `.claude/rules/pop-out-surface-registry.md`.

## 8. Surviving a project switch

a task-detail window whose Browser pane is open is RETAINED when its project is backgrounded: it stays in the window map, rendering in place but invisible (`opacity: 0`) and inert, so its guest keeps running and the task's agent can keep driving it. It renders from a frozen task row (the board store is project-scoped) and drops its terminal, so the standing cost is one composited zero-opacity webview per pane. Returning to the project ADOPTS the retained window rather than rebuilding it, preserving the guest. Hiding must not use `visibility: hidden` or offscreen positioning: both stop compositing, which hangs `Page.captureScreenshot` until its 5 s bound, so the agent gets no screenshot. On Electron 45 the hung capture does not wedge the guest's other CDP commands (decision 26). See `.claude/rules/retained-pane-never-remounts.md`.

## 9. Cross-project pane isolation

the `kangentic_browser_*` tools resolve a target scoped to the caller's own project, taken from the MCP URL path rather than from tool arguments. Before that, an agent in one project could drive another project's pane by omitting `taskId` (the registry default spanned every pane on the machine) or by naming a sessionId it read out of `list_panes`. The pane's registered `projectId` is backfilled in the main process from the session registry, because the renderer's value is ambient `currentProject` and goes stale in a pop-out.

## 10. Popups allowed

`window.open` and `target=_blank` from the pane used to hit a blanket deny handler, so any site whose sign-in is a popup presented as a dead button with nothing in the UI to explain it. The pane now carries `allowpopups` (Electron otherwise disables `window.open` inside the guest before the main process ever sees the request) and the guest's `setWindowOpenHandler` is `createWebviewWindowOpenHandler` (`src/main/window-open-policy.ts`), which allows http(s) and denies everything else with the same `[WINDOW_OPEN]` warn the external handler uses. It denies `mailto:` where the app window's handler allows it: guest pages are agent-navigable and `shell.openExternal` is ShellExecute on Windows, and the guest's `will-navigate` already blocks non-http(s), so this is parity rather than a new restriction. `allowpopups` is unconditional on purpose and is not the trust boundary - a renderer attribute cannot be trusted to be honest, the main-process handler is what enforces policy, and gating the attribute behind a setting would only recreate the dead-button symptom behind a switch nobody would find. It must also reach the DOM as a STRING: React types the attribute boolean, `allowpopups` is absent from react-dom's attribute table, and a boolean is dropped with a console warning, which would leave the whole policy unreachable behind a passing typecheck.

## 11. Popup chrome and hardening

the popup is a real OS window with `frame: true` and its title forced to the target's host (`accounts.google.com`, or `Not secure - <host>` for http), because the OS title bar is the only origin indicator the window has and a page free to name itself would be a phishing surface: `page-title-updated` is `preventDefault()`ed and the title re-asserted on `did-navigate` and `did-navigate-in-page`, while the constructor title is seeded from the requested URL so the window is labelled before its first byte loads. There is deliberately no synchronous title call at hardening time, because `getURL()` is still empty there and would clobber that seeded title. Its `webPreferences` repeat the guest's hardening exactly (no preload, `nodeIntegration: false`, `contextIsolation: true`, `sandbox: true`, `webSecurity: true`) plus `webviewTag: false`, since a child window inherits none of the opener's preferences on Electron 30 and later. Custom HTML chrome was rejected as a second renderer surface to build and test for a window that is open for fifteen seconds, and `WindowOpenHandlerResponse.createWindow` was rejected too even though it would remove an ordering dependency: it needs a literal `new BrowserWindow(` in a third file and would break the two-site rule in `.claude/rules/pop-out-surface-registry.md`. The popup is instead described declaratively through `overrideBrowserWindowOptions` and hardened in `did-create-window`, which fires after `web-contents-created` has already given the popup the external handler and therefore wins by running last. The popup is deliberately not registered in `browserPaneRegistry` and so is invisible to the `kangentic_browser_*` tools: an agent should not be able to drive a live sign-in window. Live-verified: `window.open` from a guest produces an OS window titled `example.com` rather than the page's own title. Since Electron 45 the popup's `sandbox` must also MATCH the guest's (forced on in `will-attach-webview`): a popup whose sandbox differs from its opener's gets its own process and no opener. Measured on 45.0.0 (2026-10-22): with `sandbox: false` on the popup, the guest's `window.open` returned null and the main-side `opener` check failed too; with it matching, a loopback popup saw `window.opener`, its `postMessage` reached the pane's page, and `popup.closed` read false. `browser-popup-window.spec.ts` asserts the handle, `closed` and the main-side `opener`. All three held after the popup's own navigation failed (`ERR_NAME_NOT_RESOLVED`), so CI's network access does not decide the test.

## 12. Popup cookie jar

`overrideBrowserWindowOptions.webPreferences.session` is set to the guest's own `Session` OBJECT rather than to a partition string, which Electron documents as taking precedence and which puts the popup in the exact per-task jar the pane uses without the main process re-deriving the partition name. This is not only about cookies: a popup in a different storage partition is in a different browsing context group, which severs `window.opener` and the `postMessage` channel almost every OAuth flow uses to hand its result back, and breaks the `popup.closed` poll that tells the opener the user gave up. All three were verified live against a real guest: a cookie set in the guest was readable from the popup, `popup.opener === window` held, and `window.close()` from the opener tore the popup down. A popup may itself open one more popup under the identical policy, so a chained identity-provider hop stays in the same jar instead of being ejected to the system browser; popups are capped at four per pane as a runaway guard, counted at GRANT rather than at creation because `did-create-window` fires after the handler has already answered and a burst of `window.open` calls would otherwise clear a materialized-count check every time.

## 13. File downloads

allowed, and saved without a prompt to the OS Downloads folder (`app.getPath('downloads')`, with a ` (n)` suffix inserted before the extension when the name is taken), which is what Chrome does by default. This replaces the original "unhandled, future hardening: explicit deny" position, which on inspection bought nothing: the agent driving the pane already has full filesystem write through its own tools, so a deny would only have broken the human's use of the pane, and leaving the event unhandled raises a native save dialog that can block an agent-driven pane. The handler is installed at most once per `Session` behind a `WeakSet` guard, because panes sharing a worktree share a partition and `session.on` accumulates listeners where `setPermissionRequestHandler` merely overwrites. The host window is resolved from the download's INITIATING webContents rather than from an install-time closure, since the one install serves every pane on that Session and a captured host goes stale as soon as the first pane closes. Progress is surfaced on the host window's taskbar via `setProgressBar`, and a toast naming the file (a click on it shows the file in its folder, reusing the existing `shell:showItemInFolder` channel) is pushed on `BROWSER_DOWNLOAD_DONE`.

## 14. Permissions on the popup

the popup shares the guest's `Session`, so the deny policy from decision 5 already covers it and no second handler exists or is needed. What this pass did close is that the guest session had a permission REQUEST handler and no permission CHECK handler, so synchronous checks fell through to Electron's default instead of the pane's policy. Both handlers now read one predicate, `isEmbeddedBrowserPermissionAllowed` in `src/main/permission-policy.ts`, mirroring how the first-party session already keeps its two in lockstep. The predicate grants exactly one permission, `clipboard-sanitized-write`: it is gesture-gated, cannot read the clipboard, is what a real browser allows without prompting, and is listed only because adding a blanket-deny check handler would otherwise newly break `navigator.clipboard.writeText` in the user's own dev server, which would be a regression dressed as hardening. Camera, microphone, geolocation, notifications, MIDI, serial, HID, and USB all stay denied.

## 15. Google federated sign-in stays blocked

Google returns `Error 403: disallowed_useragent` for OAuth in any embedded user agent, and a top-level Electron `BrowserWindow` is still an embedded user agent by that definition, so the popup work does not make "Log in with Google" complete inside the pane and was never expected to. What it changes is the failure mode: a dead button becomes a chromed window showing Google's own error, and every provider that does not enforce the rule works. Spoofing the user agent to strip the `Electron/` token was considered and rejected: it is a deliberate anti-phishing control on Google's side rather than a bug, `<webview useragent>` would misrepresent the app to every site the pane visits and not just to Google, and the token list is a moving target we would maintain forever. When the popup lands on Google's OAuth error path the main process raises a `dialog.showMessageBox` parented to that popup offering "Open in my browser", and the copy is honest about its own limit: signing in there signs the user into their real browser and leaves the pane logged out, so the pane's own answer is a non-Google sign-in method on that site. The detector matches a provider OAuth ERROR URL, not the user-agent refusal specifically (that string is in the rendered page, not the URL), and the prompt wording is hedged to match. **Correction (2026-08-26, empirically re-verified):** this decision was originally framed as "Google federated sign-in stays blocked", which was too broad. FIRST-PARTY Google sign-in - navigating the pane to `accounts.google.com` directly and signing in - COMPLETES inside the pane and yields a full authenticated session (verified live: the `SID` / `__Secure-1PSID` / `LSID` / `__Host-GAPS` / `ACCOUNT_CHOOSER` family was present afterward, and Gmail plus the account avatar rendered). What Google refuses is specifically the OAuth POPUP path - a third-party site's "Sign in with Google" button that opens an OAuth window - which is still an embedded user agent by Google's definition and still bounces to `disallowed_useragent`. So the decision holds for the popup path (the reason the refusal detector and its dialog exist) but not for first-party sign-in, which works and is what decision 33's shared-login feature carries across worktrees. The `disallowed_useragent` refusal SIGNATURE itself remains uncaptured from a live bounce (the `Unverified` row in the [Limitations and future work](browser-pane.md#limitations-and-future-work) table stands): the first-party test did not trigger it. **Correction (2026-09-22):** the rejection of stripping the `Electron/` token is reversed by decision 41. A firewall that rejects the token broke ordinary pages in the pane, which this decision did not weigh. Decision 41 answers the misrepresentation and moving-target reasons given here and accepts the Google one knowingly. The refusal detector and its dialog are unchanged.

## 16. An agent never moves the user's keyboard focus

measured on Electron 41 with a terminal focused in an OS-focused window, one `Input.dispatchMouseEvent` moved `document.activeElement` to the `<webview>` and flipped `document.hasFocus()` to false, so the rest of what the user was typing went into the page. Separately, `kangentic_browser_open_pane` opened a task-detail window whose arriving terminal then legitimately won `resolveArrivalFocus`'s tier 2. Both are closed, and the shape is recorded in `.claude/rules/agent-driven-focus.md`: `withGuest` arms `Emulation.setFocusEmulationEnabled` and announces each drive over `BROWSER_AGENT_INPUT`, the pane restores the user's element only AFTER the drive ends, and an agent-opened window is stamped `openedByAgent` so a new exclusive tier denies arrival focus to every terminal. Restoring DURING a drive was the original design and was reversed on measurement: it breaks the running tool, because once focus leaves the guest its own focused element loses it too and the `type` tool's characters land nowhere. Focus emulation makes the page BEHAVE focused so a blur-sensitive page still works under automation, but it is not what makes a keystroke land - see decisions 18 and 19 for what the pane actually does about the focus move.

## 17. The user can keep typing while an agent drives

restoring focus after the drive still left a window (tens to hundreds of milliseconds) in which the guest genuinely holds focus, so a user mid-sentence would watch their text flow out of the terminal and into a web form. The two input paths turn out to be separable at the guest, which is what makes this fixable rather than a documented limitation: CDP `Input.dispatchKeyEvent` does NOT fire `before-input-event`, while real user input does (main-side instrumentation with a positive control recorded ZERO events across a 120-round drive of ~3400 dispatched keys, while the user's own `Shift` and `Control` presses came through the same handler; an earlier `Ctrl+r` A/B suggested the same conclusion but is unreliable evidence, having run while the guest held no real focus). So any `before-input-event` arriving while a drive is in flight is provably the user's: main `preventDefault()`s it before the page can see it, encodes it as terminal bytes (`src/shared/terminal-key-encoding.ts`, which returns null and DROPS anything it has no safe mapping for), and pushes it to the pane, which writes it to the terminal the user was typing in. Verified end to end on a live guest: characters typed into a driven pane left the page value empty while appearing on the terminal's prompt, an Enter executed the command, and the same keystrokes with no drive in flight typed into the page normally. Re-measured on Electron 45.0.0 (2026-10-22, Windows) against a live `<webview>` guest: a CDP `Input.dispatchKeyEvent` keyDown and keyUp fired zero `before-input-event`s, while `webContents.sendInputEvent`, which takes the input router a real key takes, fired both. Physical keystrokes were not repeated on 45.

## 18. Selector-less `type` / `keypress` are a known limitation, not a bug to fix with focus management

Chromium routes keyboard input only to a focused widget, while mouse input is hit-tested and needs none. So a selector-bearing call works (its synthesized mousedown focuses the guest as a direct side effect of the same input pipeline, and the characters follow inside the SAME call), while a selector-less one only lands when the pane already holds focus. Measured over one 25-second run against a live guest: `kangentic_browser_keypress` returned `ok: true` 278 times and delivered ONE DOM keydown. Two things that look like fixes and are not: `webContents.focus()` cannot focus a guest at all (Electron early-returns for one to avoid a fatal NOTREACHED in `WebContentsViewChildFrame`, `electron_api_web_contents.cc`), and `Emulation.setFocusEmulationEnabled` does not affect input ROUTING (`document.hasFocus()` inside the guest was already `true` while keys were being dropped). An implementation that DID acquire guest focus for interact drives was built and measured, and is the reason this is now a documented limitation: holding focus across calls put the agent's own text into the user's terminal at 28, then 95, then 207 characters as mitigations were added, because a `<webview>` is an out-of-process iframe whose focus acquisition is asynchronous and never atomic - anything dispatched before it lands goes to whichever widget still holds focus. Workaround for the common flow: `kangentic_browser_type` maps `\n` to Enter, so `{selector, text: "query\n"}` searches and submits in one call. See `.claude/rules/agent-driven-focus.md`. **Correction (2026-09-24, task #720): an unfocused key is not dropped, it is misdelivered, so it is now refused.** "Only lands when the pane holds focus" hid where the other keys went. An agent sent `keypress Escape` to close a dialog while the user's terminal held focus, and each press interrupted the agent that sent it, because the Escape reached that terminal. Measured on Electron 41 with a standalone probe (a textarea standing in for the terminal beside a 740x749 guest, driven by the shipped `cdp.ts`): with the textarea focused, a selector-less `x` and `Escape` arrived at the textarea as trusted keydowns on a same-origin page and with a cross-site iframe focused inside the guest alike, and the guest's `before-input-event` fired zero times, so the interception path in `src/main/index.ts` was never involved. With the host body focused they reached the host body, where a document-level Escape closes a task window. After a click, or with the pane already focused, they reached the focused frame, cross-site iframe included. The fix is `keyboardFocusIsInHost` (`src/main/browser/cdp/keyboard-focus.ts`), checked in `dispatchKeyEvent` before every key event. It reads `hostWebContents.focusedFrame`, which named a host frame in exactly the probe cells whose keys landed in the host, with the window focused and blurred. `guest.isFocused()` and `webContents.getFocusedWebContents()` could not tell the cells apart. The check is synchronous and runs in the same turn as `sendCommand`, so focus cannot move in between, which a renderer-side `executeJavaScript` probe could not promise. A refused key surfaces as `pane-not-focused`, and `keypress` gained a `selector` so the click-then-key form covers it too. Focus is only read, never taken, so this is not a fourth attempt at focus acquisition. `tests/e2e/browser-agent-key-focus.spec.ts` checks the same behavior through the real tools against a live guest on CI's Linux, and it also passed on Windows against Electron 45.0.0 (2026-10-22). **Second correction (same task): the workaround above did not submit a plain form, and typed twice into xterm.js.** `typeText` sent each character as a text-free keyDown followed by a separate `char` carrying the text. Measured with the same probe: `"query\n"` submitted no form, `"a\nb"` reached a textarea as `ab`, a field whose keydown handler cancelled letters received them anyway, and xterm.js, which handles printable keys on keydown, received every character twice. The text now rides the keyDown with no `char`, which is how Chromium's own keyboard and Puppeteer deliver a keystroke, and a newline is Enter carrying `\r`. All four cases then behaved like a real keyboard, and plain inputs, `input` events, contenteditable and non-ASCII text were unchanged. `keypress Enter` carries `\r` too, so it also submits a form now.

## 19. An agent drive is shown, not hidden

the accepted answer to "the agent moved my keyboard focus". Interacting with a page means clicking it, and a click gives the guest real keyboard focus, so the move cannot be designed away; three attempts to make it invisible and safe were built and measured, and each put keystrokes on the wrong side. Instead, while a drive is open the terminal side of the split dims (opacity only - it stays mounted, live, and one click away), the Browser pane takes an accent border, and its toolbar reads "Agent typing here". State lives in `src/renderer/stores/agent-drive-store.ts`, keyed by sessionId, with `BrowserPane` translating from the guest id the signal carries. The keystroke interception stays underneath as the safety net, so a user who types anyway lands in their terminal rather than in a web form. The residual, accepted deliberately: focus does move to the pane during a drive, and the user is told so rather than surprised by it.

## 20. The pane hears about a BURST, not each tool call

`endAgentInput` debounces its end-of-drive announcement, and a call arriving inside the quiet window cancels it. Announcing every call made the pane hand the user's focus back between each consecutive pair: measured at 810 trusted `focusin` events on the terminal during a single drive, against 11 with the debounce. The residual, accepted deliberately: focus still moves to the pane once per burst, as the unavoidable consequence of clicking a page, and returns when the agent stops.

## 21. Text can reach the pane's note input without a keyboard

the note input ("What should the agent do with this?") is where you describe what the agent should do with a capture, and it was the one place in that workflow a keyboard was mandatory: dictation could only ever resolve a TERMINAL, and a keystroke intercepted mid-drive was DROPPED unless the user had been in one. Both are the same missing mechanism - getting text into a React-controlled input - and `src/renderer/utils/text-target.ts` is now it. Two properties are load-bearing. It is ALLOW-BY-DEFAULT: any focused text field is a target, anywhere in the app - a new-task title, a search box, a rename field. It shipped first as an opt-in marker per field, which is safer to reason about and wrong in practice, because every new field silently did nothing until someone remembered to mark it and there is no version of "dictation works here but not there" a user can predict. The exclusions are therefore structural rather than a list to maintain: a `type` that does not hold prose (`password` above all), disabled, read-only, and an explicit `data-no-text-target` opt-out honoured on the field or any ancestor. **The exclusion that matters most is xterm's `.xterm-helper-textarea`**, which is a real `<textarea>` and so matches an allow-by-default rule - it must not, because a terminal already has a delivery path (PTY bytes) and a DOM write would land the transcript in a hidden node xterm clears on the next keystroke, so the words vanish and the shell never sees them. That is a silent, total break of the one path that already worked, and it is denied by class rather than by marker because it is xterm's element and we do not render it. And it writes through the prototype's native `value` setter plus a dispatched `input` event, because assigning `.value` directly updates React's own value tracker too, so React sees no change, never fires `onChange`, and the next render reverts the write - correct-looking for exactly one frame. Dictation resolves such a field as a tier ABOVE every window tier (DOM focus in a field is the most direct statement of intent there is; the window tiers are proxies for it), and release honors the existing auto-submit setting by pressing Enter on the field, which is already what the note input maps to Send. **Auto-submit is scoped by the field's surroundings, not by the field.** Enter in a standalone box does the one thing the user expects; in a multi-field form it commits EVERY field, so dictating a title into the New Task dialog would create the task the instant the user let go of the key with the rest of the form still empty. `mayAutoSubmit` therefore refuses when the field's enclosing `<form>` holds more than one text input - a `<form>` being precisely the declaration that its fields commit together, which makes the rule structural rather than a list of dialogs to maintain (the Browser pane's URL bar is a form with ONE input, so it still submits). Refusing only downgrades release to insert-and-leave; the words still land. The chip reads the resolved decision (`willSubmit`) rather than the raw setting, so its "Release to send" hint never promises a commit the sink will refuse. Closing the note-input case also required `shouldArmFocusGuard` to stop treating "focus was inside the pane" as "not a steal" for text targets specifically: the note input lives inside the pane, so the guard had never armed for it at all. **Dictating into a field inside the GUEST PAGE was ruled a different mechanism and left unsupported here** - it looked to need an async `Runtime.evaluate` round trip per press just to learn which element the guest has focused, a new non-agent CDP path (every path today goes through `withGuest`, which would flash "Agent typing here" and arm the focus guard on the user's own dictation), erase-and-retype partials firing the page's own input handlers on every revision, and an active refusal for `type="password"` - which the renderer-side case never has to make, because it cannot reach one. That estimate was wrong on the mechanism and is superseded by decision 24, which ships it.

## 22. A push-to-talk guard is scoped to the PTY it protects, and is never silent

an auto-submit paste writes bracketed content into a terminal, and fresh bytes arriving mid-paste would split it, so dictation refuses a press aimed at a terminal whose paste is still landing. That guard shipped as one global boolean checked before the target was even resolved, which made it wrong in both directions. Wrong in SCOPE: a paste into a terminal also refused a different terminal, the pane's note input, any app field, and a guest page - none of which can write to a PTY at all, so the common flow of dictating into the agent and then clicking over to the Browser pane simply did nothing. Wrong in VOICE: it said nothing, and the window is not brief. `terminal-submit.ts` deliberately waits for the TUI to settle instead of sleeping a fixed amount ("fast when the machine is fast, patient when it is not"), so it stretches under load - captured live at 2.1 seconds, with two consecutive presses logging `startDictation {active:false, submitting:true}` and doing nothing at all. Silent, global, and seconds long is indistinguishable from a broken button, and was reported as one ("works sometimes, seems to need a reset"). It is now a SET of session ids, checked after the target resolves, and a refused press raises a `busy` chip that names the reason and clears itself. The general form: a guard should name the resource it is protecting, not a global condition, and a refusal the user can trigger by hand needs to be visible.

## 23. The dictation chip anchors to the target, not to the window

it used to anchor to the focused WINDOW and centre horizontally, which is the worst possible rule for a split task-detail window: measured on a real one, frame 538..2022 with the terminal pane at 539..1280 and the Browser pane at 1281..2021, so the window's centre (1280) IS the split seam. The chip straddled the divider whichever side was being dictated into, and its bottom edge landed on the Browser pane's own Clear / Inspect controls. It now anchors to the thing the words are landing in. A text input is exact (it is a DOM node). **A terminal anchors to its PANE, and specifically NOT to its caret.** The caret was tried first and looked like the elegant answer, because xterm appears to compute it for us: it keeps `.xterm-helper-textarea` positioned ON the cursor so an IME composes in the right place, sized to one cell - measured on a live WebGL terminal at `left: 588px; top: 17px`, 7x17. That behaviour is real and still not a usable anchor, because it holds only while the cursor is SHOWN. An agent TUI hides it (`[?25l`), and with it hidden xterm PARKS the textarea somewhere unrelated - measured at `left: 721px; top: 799px` in a 741x829 pane while the caret was on line 2 - then snaps it onto the real caret the instant input arrives. So the chip appeared near the pane's bottom, then slid 468px up the screen the moment the user started speaking, on every single utterance. The pane's bottom BAND is stable, is always inside the right pane, depends on nothing internal to xterm, and lands where the caret would have been anyway, since a TUI keeps its input box at the bottom. How wide that band is was measured rather than guessed: on a live Claude TUI the bottom FIVE rows are the input region (a rule, the prompt line, a rule, a blank, and the status line), so `TERMINAL_INPUT_RESERVE_PX` clears 85px and the chip sits above the words being dictated instead of on them - it covered under three rows before that was checked. It stays a pixel constant rather than rows times a measured cell height, because the only element that reports the cell size is the helper textarea this anchor exists to stop depending on, and it is an approximation either way: the box grows with a multi-line draft, so no fixed number clears every state. The general lesson is worth more than the fix: an internal element positioned for someone ELSE's purpose tracks what that purpose needs, not what you want, and it stops tracking exactly when their need lapses. Placement prefers below and flips above when there is no room, which is the common case rather than the exception - a terminal's anchor IS its pane's bottom edge, and the note field is the last row of its own pane. Horizontal clamping is to the PANE (`data-anchor-bounds`, declared on the Browser pane), because clamping an input to its own FIELD was tried and is wrong: a field narrower than the chip leaves it overhanging, and a field near a pane edge then spills into the neighbour, which is the bug being removed. Two registries already existed and neither could answer "where is this session drawn" - `terminal-mount-registry` holds a refcount, `terminal-grid-registry` is `__KANGENTIC_DEV__`-gated and compiles away - hence a third, tiny `terminal-anchor-registry`.

## 24. Guest-page fields ARE reachable, and the first estimate that said otherwise was wrong

this shipped as a documented non-goal on the reasoning that it needed an async `Runtime.evaluate` per press and a new non-agent CDP path, because every CDP path goes through `withGuest` and would flash "Agent typing here" on the user's own dictation. All of that was mistaken. `<webview>.executeJavaScript` runs a string in the guest straight from the renderer, measured at 1ms to read the focused element and 2ms to write into it, and it touches neither the CDP driver, `withGuest`, nor the agent-input signal - `BrowserPane` already uses the same call for Inspect. `guest-text-target.ts` owns the three injected scripts, and they are deliberately tiny: read some facts, or write one exact string. Every DECISION - eligibility, auto-submit, what the value becomes - stays host-side, so no rule has a second copy living in a template literal where no test can reach it. Password fields refuse (the probe reports `reason: 'password'` and the chip says so, anchored to the field rather than a far corner). **Dictation never SUBMITS in a guest - it only fills.** An earlier version ran the host's multi-field rule against the guest's own form, which was strictly worse than not trying: that rule is our inference about a page we do not control, and a single-field form is not automatically safe (a "type DELETE to confirm" box is one field). Filling the field and letting the person press Enter costs one keystroke and deletes a whole class of wrong guesses, along with the submit script, the form-field count, and the branch that consumed them. **Permanent limitation:** `executeJavaScript` runs in the guest's TOP frame only, so a field inside a cross-origin iframe is unreachable. Electron 45 validates the reply IPC of a `<webview>` `executeJavaScript` against the sending frame, so this path was re-checked on 45.0.0 (2026-10-22): the real `probeGuestField` and `writeGuestField`, imported into a live preview renderer, found a guest text field eligible, wrote a partial, replaced it with the revision, and the page saw both `input` events.

## 25. A guest consumes the mouse outright, so main forwards the back/forward buttons

dictation and back-navigation both live on `Mouse:Back`, and both were simply dead whenever the page had focus. Measured with a real mouse against a live guest: one back-button press produced 31 events inside the page and **ZERO** on the host window, so no renderer listener could ever see it. Three candidate fixes were considered and two were wrong on the evidence: `BrowserWindow`'s `app-command` never fired at all (the `WM_APPCOMMAND`-goes-to-the-window reasoning did not hold), and Electron's own docs list only `left`/`middle`/`right` for `MouseInputEvent.button`, which nearly ruled out the option that works. `webContents.on('input-event')` on the guest DOES report `button: 'back'`, with a real mouseDown/mouseUp PAIR (measured: a 1534ms hold) - which is what makes push-to-HOLD possible rather than a one-shot toggle. Main forwards those over `BROWSER_GUEST_MOUSE_BUTTON` with a MAIN-side timestamp, because the renderer's own clock is congested by the work a press starts (mic permission, engine start, AudioWorklet load: an 80ms timer measured 414ms), which would misfile a tap as a hold. `mouseLeave` synthesises a release: a real press whose pointer left the webview reported its DOWN and never an UP, which would otherwise strand dictation recording with the microphone open. The forward is gated on the user's actual binding, so rebinding push-to-talk to a key stops the button dictating. `input-event` is observational with no `preventDefault`, so the page still sees the button - acceptable because Chromium does not navigate a `<webview>` on it, which is why the navigation had to be built by hand in the first place.

## 26. Concurrent drivers are serialized per GUEST, not per pane or per caller

three `general-purpose` subagents drove one pane at once, interleaving navigations, clicks and screenshots, each believing it had exclusive control, and nothing logged it. Serializing per caller cannot work: subagents inherit the parent's `mcp.json` verbatim, so every one of them presents the parent's `callerSessionId` and they are indistinguishable at the transport. The FIFO (`src/main/browser/guest-drive-queue.ts`, a p-queue of one keyed by `webContentsId`, mirroring `withTaskLock`) is therefore keyed by the thing actually contended - the guest - and acquired inside `withGuest` after `resolveLiveGuest`, so `beginAgentInput` / the body / `endAgentInput` all run under it and a queued drive does not announce. Three unbounded bodies were bounded first, because a FIFO turns one stuck holder into everyone's problem: `wait` now acquires per poll rather than holding for its whole 60s, `navigate` is raced against `NAVIGATE_TIMEOUT_MS`, and `eval` against `EVALUATE_TIMEOUT_MS` in `browser-tools.ts`. The eval bound sits at the TOOL rather than in `runtimeEvaluate`, deliberately: that helper defaults to `awaitPromise: true` and is shared with the dev inspection bridge, and `kangentic_browser_eval` is the only caller running caller-authored JavaScript - the rest pass fixed, short probes. Without it an expression that never settles (`new Promise(() => {})`) holds the guest for good, since the FIFO bounds ACQUISITION only and a body that has started runs to completion. Honest limits, unchanged by any lock: a mutex does not stop worker A navigating away from the page worker B is mid-verify on, and `cdp.ts`'s `Promise.race` abandons rather than cancels, so a hung capture stays pending in the guest after its 5 s bound. This said it head-of-line-blocks that guest's transport. Re-measured on Electron 45.1.0 (Chromium 156) on Windows with a `<webview>` guest, it does not: a minimized, hidden or covered host hung the capture, the next `Runtime.evaluate` answered at once, and a capture once the window was restored took 19 ms. `webContents.capturePage` hangs the same way, so it is no fallback, and `setBackgroundThrottling(false)` changes nothing. Only turning off Chromium's occlusion tracking (`disable-backgrounding-occluded-windows` and the `CalculateNativeWinOcclusion` feature) let a covered host capture, in 22 ms, at the cost of a covered window painting on; a minimized host still hung. It was not adopted. The reported shape is reproduced end to end by `scripts/rigs/browser-contention/` - three concurrent callers on ONE session id, against a live preview, at zero quota - and verified red-green by disabling the lock: 40 of 120 keystrokes arrive without it, on both a lane and a real task-detail pane, and 120 of 120 with it. Note WHICH way it fails, because it is not the obvious one: concurrent click-then-type sequences race for focus and two callers' input is LOST outright rather than interleaved, so a test that only checks for shredding passes with the fix removed.

## 27. A subagent gets its own offscreen LANE, and a lane is not a pane

(SUPERSEDED by decision 39: the `isolated` argument is gone and a task has one surface; the registry and lifetime mechanics below still hold for its offscreen form) - one-pane-per-task is assumed by `browserPaneRegistry`'s map, the store's `browserOpenTasks`, and `DetailOwnerRegistry`, and all three are about the user-visible task-detail window. An offscreen lane has no window and no renderer involvement, so it registers into the SAME registry under its own `lane_` handle carrying `kind: 'lane'` (and `handoff: true` when main stood it up for a closed pane), and `withGuest` / `resolveLiveGuest` need no change at all; `resolveTarget` ranks by kind (visible pane, then hand-off lane, then isolated lane) so an implicit call stays deterministic while surfaces coexist. Substrate is an offscreen `BrowserWindow` (`offscreen: true`, `show: false`), reusing the task partition so a subagent inherits the user's login. Offscreen is not a preference: `initially_hidden` is set only in the NON-offscreen branch of `electron_api_web_contents.cc`, so an offscreen WebContents is never marked hidden and keeps its own compositor - whereas a VISIBLE lane window the user happens to cover stops rendering on Windows and re-enters the `Page.captureScreenshot` hang. Routing is a server-issued handle (`open_pane` with `isolated: true` returns one, passed back as `sessionId`), so the discriminator is the ACT OF ASKING, not who is asking - no `agent_id`, no hook, no adapter capability, and it works for all ten agent CLIs. Hook-stamped `agent_id` routing was designed and rejected: Claude-only, needs a second `EXTERNAL_SCRIPTS` hook script (`event-bridge.js` suppresses stdout by design and `updatedInput` IS stdout), and rests on an undocumented per-instance guarantee. Lane isolation is COOPERATIVE and cannot be enforced, for the same reason per-caller serialization cannot; `list_panes` therefore labels lanes and counts them without handing out other callers' ids.

## 28. `LANE_FRAME_RATE` is 10, and that number was measured

offscreen rendering copies a full frame bitmap on every paint, so lanes are throttled; the first value shipped was 2 and was wrong. Time for a wheel-driven scroll to land: unthrottled 100ms, 10fps 100ms, 2fps 300ms. At 2fps an agent that scrolls and immediately screenshots captures the PRE-scroll frame - a silently wrong answer, which is worse than a slow one. 10fps has no measurable penalty and is still a 6x saving over the default. Capture is unaffected by throttling either way (`Page.captureScreenshot` forces its own frame; an explicit `invalidate()` first produced byte-identical images at every rate tested). Also measured, so it is not re-derived: `sandbox: true` on a lane costs nothing, and `Input.dispatchMouseEvent` genuinely lands on an offscreen guest (the page's listener fired, and a `mouseWheel` actually scrolled) - assert that the PAGE received the input, never merely that the CDP command returned.

## 29. An agent's browser survives the user closing the task window

the pane's guest dies with its DOM node, so a subagent mid-verify lost its browser the moment the user navigated away, and it reported "agent disconnected". Closing a window is a statement about the user's layout, not about the agent's work, so a pane being driven is handed off to a lane (`src/main/browser/browser-lane-handoff.ts`) instead of destroyed. `HANDOFF_REASONS` is an allowlist, not a denylist: `self-heal-dead-guest` is excluded, because a guest the registry just evicted as dead has nothing to hand off and reviving it would resurrect a corpse; a close the agent asked for itself (`close_pane` marks its targets deliberate) is excluded too, since standing a lane up behind the agent's back would undo what it requested. The lane registers under a NEW `lane_` handle: an agent holding the old `pane_` handle gets `surface-gone` naming the lane rather than being silently retargeted (decision 34). Lane lifetime is tied to the OWNING SESSION, never to the subagent - nine of ten agents have no `SubagentStop` hook - with four backstops on existing machinery: `resolveLiveGuest` self-heals a dead entry, session end destroys that session's lanes, an idle timeout reclaims an untouched one, and `destroyAllLanes()` sweeps both when the main window closes and on quit (`browserPaneRegistry.detachAll()` is the neighbouring shutdown call, but it detaches CDP rather than destroying lanes). Later, a task's work ending (a move to Done or To Do, a backlog demote, a delete, or a project delete) also destroys the task's lanes (`closeTaskWindows`, after its sessions end), and a hand-off lane whose agent ended while it was still opening is destroyed as soon as it opens. That last backstop needs the sweep to be able to SEE a lane: `openLane` awaits a cookie-jar seed before it constructs its window, so a lane opening during the teardown is not in the map yet, and a sweep generation captured on entry is what makes it abandon instead of outliving the sweep that was meant to remove it. Without that, the surviving offscreen window holds `getAllWindows()` above zero, `window-all-closed` never fires, and the app lives on invisibly (Sentry DESKTOP-J crashed a second launch into exactly that state). Two of those were written and initially never called (`destroyLanesForSession`, `touchLane`); a cleanup path with no caller is not a backstop, and the idle reclaim would have reaped ACTIVE lanes without the second.

## 30. The dev-port ledger answers a question; it does not assign

an earlier pass leased a port per task at worktree creation and defaulted the task's pane to it. That was wrong in both halves. A port Kangentic chose is a number the user never configured (the first default, 4200, is ANGULAR's, and a task's pane opened onto a developer's own running dashboard), and a real project pins its own ports - often several - in `angular.json`, a vite config, a compose file. So nothing is reserved up front: `kangentic_reserve_dev_ports` answers "give me N ports nothing else is using", `kangentic_check_dev_ports` reports what a task holds and what is actually listening, and the pane defaults to nothing. What the ledger is FOR is the one thing a project's own config cannot do - see across every task and every project at once, so two agents starting servers at the same moment do not pick the same number. The table is global (`<configDir>/index.db`) for that reason, which scopes it to one Kangentic INSTANCE rather than the machine: `configDir` honours `KANGENTIC_DATA_DIR`, so a `/preview` keeps its own ledger and a reservation does not cross between instances. It is keyed on `task_id` rather than `worktree_path` (a Done round-trip nulls the path), and its index on `task_id` is deliberately non-unique so one task can hold an API and a frontend. A lease is only ever advisory: the authority is a bind probe, which is what stops a port something else already holds from being handed out - the other Kangentic instance included, which is what makes the instance scope above safe. There is no background reclaim, and the two release paths (task delete, project delete) are the whole lifetime - see `dev-port-allocator.ts`'s header for the residual that leaves untreated.

## 31. A build-error overlay is reported as an ERROR, not screenshotted

`kangentic_browser_screenshot` used to faithfully return a picture of a dev server's full-screen error overlay, which is technically correct and practically useless: the agent spends a turn working out that the red rectangle is not the app, and when several agents share one dev server the one that reads the overlay usually is not the one who broke the build, so it has no reason to suspect a build error at all. Detection runs INSIDE the same `drive()` call as the capture (`src/main/browser/dev-server-error.ts`, called from `browser-tools.ts`), so the two cannot disagree about what was on screen. It keys on the CUSTOM ELEMENT rather than scraping text, because Vite renders `<vite-error-overlay>` with its content in a shadow root and the message never reaches `document.body.innerText` - a text-based check would see nothing at all. It is deliberately framework-shaped (Vite's overlay, and Next's `nextjs-portal`) rather than a generic heuristic, and the probe never throws or reports an error of its own: absence of a KNOWN overlay means "no error detected", never "the page is fine", so a dev server this does not recognize behaves exactly as it does today. That is the honest failure direction - a missed overlay costs what it already costs, while a false positive would break a working tool. The `dev-server-error` envelope names the offending file when the overlay gives one, and says outright that the build error may belong to another agent sharing the worktree.

## 32. Jars are keyed by TASK IDENTITY, which fixes the intra-task logout and makes the orphan sweep a name-parse

the jar was first keyed by worktree PATH (`persist:kngbrowser-<hash(worktreePath)>`), so any path change (a relocate, a rename, a Done round-trip landing on a different folder) dropped the jar and logged the user out. Re-keying to `persist:kng-<projectId>-<taskId>` (plus a per-project `kng-<projectId>-identity` jar) makes the jar follow the TASK - the path can change, the id cannot - which retires that logout at the root rather than instrumenting around it. It also makes the names SELF-DESCRIBING, so reclaiming orphans (a deleted task or project leaves a jar "Clear browser data" no longer reaches, holding live session cookies) is a name-parse plus an existence check: `sweepOrphanedBrowserPartitions` (`src/main/browser/browser-partition-cleanup.ts`, wired in `index.ts` on app-ready, packaged builds included) deletes every `kng-` jar whose PROJECT is gone (checked against the global project list, no per-project DB) or whose TASK is gone (a light read-only `SELECT id FROM tasks` on a THROWAWAY connection - deliberately NOT `getProjectDb`, which would migrate and cache a connection for every project at startup). The abandoned path-hash `kngbrowser-<hash>` jars are reclaimed once here too: the re-key is breaking, so old jars are swept and the user signs in once more. It ABSTAINS rather than over-delete: a project-list read failure aborts the whole sweep, and a per-project task-read failure keeps that project's jars, so a transient fault never presents an empty set that would wipe everything. There is deliberately NO mid-run hook: with task-keyed jars the correct reclaim trigger is task DELETION, not worktree removal (where the jar must SURVIVE for a Done round-trip), and the startup sweep covers task-gone and project-gone reliably. A 10-minute mtime grace period keeps the sweep from racing a pane that just created its jar, and an `assertRemovablePartitionPath` guard refuses to `fs.rm` anything that is not a direct `kng-`/`kngbrowser-` child of the Partitions root.

## 33. A project's IdP login is shared across its tasks; the dev app stays isolated

decision 1 keys the jar per task so two dev servers never clobber each other's `localhost` session, but the same isolation made you re-enter your Google (or any identity-provider) login once per task, for an account the real browser next door was already signed into. The fix splits sharing by cookie DOMAIN: NON-localhost cookies are shared project-wide through a per-project identity jar (`persist:kng-<projectId>-identity`), while `localhost` / `127.0.0.1` / `[::1]` / `*.localhost` cookies are never copied in either direction (`isLocalCookieDomain` in `src/main/browser/cookie-seed.ts` is the single chokepoint). The mechanism (`src/main/browser/jar-seeder.ts`): each time a pane or lane binds a task jar (a load boundary - first open, reopen, or after a restart) it first syncs the identity jar's non-local cookies IN via `browser:jarEnsure`, so a task opens already signed into whatever the project last signed into; and a write-back listener mirrors that jar's non-local cookie ADDS back OUT into the identity jar, so a sign-in in one task reaches the others (and every future task, and survives a restart, since every jar is an on-disk `persist:` partition). The identity jar itself carries no listener, and the write-back is suppressed while a programmatic sync is writing (best-effort: a change event Chromium delivers after the sync settles can echo an identical cookie back into the identity jar, an idempotent re-add), so the hub cannot loop even though it is effectively two-way through it. Add-ONLY on purpose: a sign-OUT is not propagated (Clear Browser Data is the explicit wipe-everywhere path, and it already includes the identity jar), and mirroring only `removed === false` changes means Google's constant token rotation (which fires paired remove+add) mirrors the new value without ever removing anything. This was gated on one empirical result and shipped only after it: signing into a real Google account in one worktree pane, copying its 25 `.google.com` / `accounts.google.com` cookies into a second task's jar, and loading `myaccount.google.com` there resolved SIGNED IN with no re-auth prompt (2026-08-26) - so a copied session is not defeated by Google's device-bound `__Secure-1PSIDTS/3PSIDTS` credentials for this account and Electron-Chromium version. The `src/devtools/main/cookie-jar-routes.ts` rig (list/copy jars over the dev inspection bridge, behind Allow Unsafe Operations) is how that test is re-run. Accepted cost, stated rather than found in review: a fresh task's pane now starts holding the project's IdP session cookies where before it started clean, so an agent driving a fresh pane can act with the user's Google session - the same judgment decision 27 already made for subagent lanes ("a subagent inherits the user's login"), extended across tasks for non-local domains only. The deliberate limit, stated precisely: the sharing is ADDITIVE, not a clean single-account replacement. `copyCookies` only adds/overwrites by name and the write-back never mirrors a removal, so signing into a second Google account does NOT evict the first - a jar can end up holding a MIXED set of two accounts' cookies (one account's `__Secure-1PSID` alongside the other's rotating `SIDCC`), which Google may meet with a "verify it's you" challenge. So two DIFFERENT Google accounts across tasks at the same time is UNSUPPORTED (not merely "last one wins"); the escape hatch is Clear Browser Data, which wipes every jar including the identity jar. `localhost` dev-app logins are unaffected - they are never copied, so two tasks on different dev-app accounts always work. Instant live propagation while both panes are open, with no reload, is a non-goal for this cut (it needs a two-way live mirror with loop-guarding); the load-boundary sync already covers reopen, new tasks, and restart.

## 34. A surface handle names one tab for its lifetime, and a task-bound caller never resolves to another task's pane

reported as "the app keeps logging me out": an agent verifying an OIDC-protected SPA (tokens in `sessionStorage`) saw the same `sessionId` land in a different tab across two consecutive `navigate` calls, `sessionStorage` gone and `localStorage` intact. The registry's own log lines named three defects. (1) The registry keyed entries by the task's AGENT SESSION id and `register()` overwrote unconditionally, so every remount of the visible pane re-bound the same key to a new guest: one session id was observed bound to webContents 7, 14, 16, 18, 20, 22, 26, 31, 33 in a single agent session, and the agent's explicit `sessionId` silently followed. (2) Every task-window close/reopen cost TWO fresh documents (the hand-off lane, then the reopened pane), and the user was opening and closing two task windows every 30-60s while watching two agents. (3) `resolveTarget`'s caller-task rule fell through on zero matches to "the single pane in the project": task #17's agent, whose own pane had died and whose hand-off lane had failed to load, navigated task #18's logged-in app to an identity-provider URL (`[browser-drive] cap=navigate caller=95a32bd8 pane=a5058ec6 wc=26`). The fix: a handle is minted per GUEST (`pane_<8hex>`, mirroring `lane_<8hex>`) and bound to that webContents for its whole life - re-registering the same guest keeps it, a new guest gets a new one; retired handles are remembered (a bounded ring) so a stale handle answers `surface-gone` with the reason, how long ago, what did not carry over, and the task's current surface, while a value that was never a handle (an agent session id) answers `no-pane-open` with the same pointer; the implicit default for a caller with a task is OWN-TASK-ONLY, ranked visible pane > hand-off lane > isolated lane, refusing rather than borrowing another task's pane; `open_pane` counts only visible panes as "already open"; the renderer unregisters by guest id (`BROWSER_PANE_UNREGISTER` takes a `webContentsId`) and re-registers the same guest on a session rotation instead of unregistering; and `close_pane` marks its targets deliberate so the hand-off leaves them alone. `webContentsId` IS a reliable "new tab" signal; the ticket's contrary note was an OIDC silent renew re-populating the new tab from the still-valid IdP cookie. The forensics: `[browser-pane]` / `[browser-lane]` / `[browser-drive]` lines (`pane=` + `wc=` per drive) from the project's `.kangentic/logs`, correlated with each agent's `events.jsonl` `tool_start` timestamps and the IPC log's `detail:requestOpen`, which attributes a window churn to the user rather than to an agent's `open_pane`.

## 35. A closed task window PARKS its Browser pane while the agent is live

defect (2) above was the original symptom, and the hand-off lane could not fix it: the lane is a fresh document, and so is the reopened pane, so per-tab state died twice per close. Retention (decision 8) already keeps a window mounted and hidden across a project switch, so a user close of a task-detail window whose pane is mounted (showing or held), whose task's agent session is running, and which actually has a `<webview>` guest registered (`browserGuestTasks`) now does the same: the window stays in the map, hidden with `opacity: 0` and inert, drops its terminal, leaves `order` / focus / the tile tree / the ownership report / the terminal claim set / the workspace blob, and reopening the task un-parks it in place - the same guest, the same surface handle, `sessionStorage` and in-memory state intact. The generic window store stays a mechanism (`parkWindow` / `unparkWindow`; `closeWindow` is the unconditional drop); the BOARD layer owns the policy through `WindowManagerLayerOptions.shouldParkOnClose`, consumed at the one place every user close converges (`WindowFrame`'s exit-animation `onClose`), and a reaper mounted with the board bridges drops a parked window the moment its pane closes, its guest goes away, or its session stops running. The guest condition is load-bearing rather than belt-and-braces: pane-open is a store flag the user sets by pressing a pill and says nothing about whether a page exists, so a pane with no URL (the empty state attaches no `<webview>`) or one detached into a pop-out would otherwise park a window that is hidden indefinitely with nothing inside it to preserve. `browserGuestTasks` is set on the guest's `dom-ready` and cleared when its node unmounts, which is exactly the "a page is really here" fact, and the reaper subscribes to it so a guest dying wakes the sweep. `isWindowDormant` (parked OR retained) is the single predicate every hidden-window exclusion reads - including the drag-and-dock resolver and the store's dock paths: a parked window keeps floating invisibly at its old geometry (a full-height half after a 2-up dock), and before that exclusion a window dragged across that half docked INTO the ghost and came out tiled beside a partner the user could neither see nor drag away from; `findWindowTreeViolations` now reports a leaf pointing at a dormant window. The hand-off lane stays as the fallback for a guest that genuinely dies (a reload, displacement to another host, the pane detaching into a pop-out). One race the live probe caught: the UI's stop flips the renderer's session to exited (and so drops the parked window) at the same moment `kill()` stamps the registry entry, while the PTY is still exiting - so the hand-off's liveness check is `SessionRegistry.hasLiveSessionForTask` (running or queued AND no kill in flight), not "is there a running row", or a lane was stood up for an agent being stopped and torn down moments later.

## 36. Hiding the pane with the Browser pill HOLDS it while the agent is live

the same cycle as decision 35, one level down: the pill (its shortcut, or opening Changes / the Description peek over the pane) unmounted `BrowserPane`, which destroyed the guest, stood up a hand-off lane (log line `handoff ... lane=lane_70d1af47`, wrongly captioned "window closed"), and toggling the pill back built a fresh pane with a fresh document, so a user who put the pane away to see more terminal reset the agent's tab twice. Now a UI hide keeps the pane mounted and hidden in its own fixed slot of the split row (`browserSlot` in `TaskDetailBody`, absolutely positioned over the right side at the width it would show at, `opacity: 0`, inert, pointer-events off) while the terminal takes the whole row; the slot is deliberately NOT the one Changes / Description render into, so opening Changes over a hidden pane restyles rather than remounts. State is `browserHeldTasks` in the session store: `toggleBrowserOpen` (the only UI path) passes `hold`, while `setBrowserOpen(taskId, false)` without it - the agent's `close_pane` push and hydration - DISCARDS, so an agent asking for its tab to go still gets that. A held pane counts as mounted everywhere parking does (`shouldParkOnClose`, `planWindowRetention`), so closing the window or switching projects with a hidden pane keeps it like a showing one (subject to the same guest requirement as decision 35: a held pane that never loaded a page has nothing to park for), and the park reaper also releases holds whose session stopped, so a pane hidden under one session never re-mounts invisibly under the task's next. Cost is what leaving the pane open costs: one composited zero-opacity webview, bounded by the session; cheaper than the lane round-trip it replaces (two fresh documents plus an offscreen window). Measured on a preview (Electron 41, Windows, a small test SPA): each hidden guest is one renderer process of ~121 MB working set, whether showing, held, or parked; two tasks' worth appeared as +2 renderer processes and disappeared within seconds of each session's end (window dropped, hold released, registry entry gone, process exited); 30 park / un-park cycles on one task left the process count, window store, DOM frames, claims, and registry exactly where they started, with the board renderer +10 MB after 10 cycles and the same +10 MB after 30 (heap headroom, not per-cycle growth) and the main process flat. The weight therefore scales with CONCURRENT live agents that opened a pane, not with time; a real app's guest is larger (an Angular dashboard is a few hundred MB), and a long-running session keeps its hidden guest for as long as it runs. The hand-off is now only for a guest that genuinely unmounts (reload, pop-out, displacement, the task leaving the board), and its log line says which reason.

## 37. Close browser is the user's discard, and Hide never is

hold and park made a kept guest a sunk cost (~121 MB for as long as the session runs) with no user path to end it short of the session ending or the agent's `close_pane`. The Command Terminal already has the right two-verb model (the title-bar toggle hides and keeps every PTY; a per-window Stop destroys), so the browser copies it: the Browser pill hides and shows, and a separate **Close browser** control destroys.

*The control.* A labelled, red-tinted button LEADING the navigation bar ahead of Back / Forward / Reload, behind its own divider - the Command Terminal's Stop position. Three properties, each settled against a rejected alternative on a live preview:
- PLACEMENT by slip risk. Beside Send it read as a slip away from Send; at the bottom-left it crowded the note input; the trailing end sits beside pop-out, a high-traffic control, so a slip there costs the page's state often. The leading cluster is low-traffic once people use the mouse back button, so a slip lands on something cheap.
- TREATMENT by discoverability. Stop terminal is icon-only and works because nothing beside it looks like it; here the same glyph sat in a row of three grey nav icons at a similar size and the eye filed it as a fourth nav button (tried at 14 and 18px). The destructive tint is the kebab's destructive language, so it reads as consequential before the word is read. The stop-loading worry that argues against a red mark here is weak: Chrome's stop-loading is an X in Reload's slot during a load, not a persistent tinted button, and this pane has no stop-loading control at all.
- LABEL by object. The pane has three plausible things to "stop" - the agent driving the page, the page load, and the browser - so the bare verbs ("Stop", "Close") leave the object to inference and two of the three readings are wrong. Naming it also fails safe: a user who expected the pill's hide loses a page reload, where one who expected to halt the agent would lose the tab and their model of the app. For the same reason the glyph does NOT swap to the working activity ring while the agent drives: spinner-plus-Stop reads as "cancel this operation", the wrong reading at the moment it is most likely. The pane already says "Agent typing here" and takes the accent border. The task kebab carries the same words whenever a guest exists, which is the only reach while the pane is hidden; a parked guest is reached by opening the task. No confirmation, like Stop terminal.

*The sequence* (`components/browser/close-browser.ts`): main is told FIRST (`BROWSER_PANE_USER_CLOSE` retires the handle with reason `user-closed`, which the hand-off allowlist does not include, so no lane re-spends the memory behind the user's back), then the open flag clears without a hold so the pane unmounts and the guest dies with its node. The saved URL stays, so Show reopens the same page as a fresh document.

*The indicators.* `browserGuestTasks` (session store, taskId -> guest id, published by the pane on register / unregister) is the renderer's "a browser is running" fact. The pill carries a green pulsing dot whenever a guest is running (showing, hidden, or parked), the way the Command Terminal toggle shows a live PTY. The card carries a solid green globe at the far right of its title row, after the ticket number, at the badge's scale (12). The asymmetry is the point: the pill is always rendered, so it needs a marker to say whether a guest is behind it, while the card's globe renders only while a guest runs, so its presence is the signal - and at 12px a dot there was a smudge rather than a second reading. Rejected on a live board, the three compared side by side in a temporary A/B strip: a pulsing green globe (motion on every such card, for a fact that is steady), a muted globe with a pulsing dot (the dot unreadable at that size), and 16px (read as a second status mark rather than a tag). Green is safe here only because of the PLACEMENT: beside the activity mark it both competed with the ring's green and shifted every title's start, and past the title and the ticket number it does neither. Whether the agent is DRIVING is shown only in the pane; an empty-state pane has no guest, so no indicator and no Close.

*The agent's view.* `list_panes` / `open_pane` carry `visibility` (showing / hidden / parked / offscreen), published by the renderer over `BROWSER_PANE_VISIBILITY` because only it knows. After a user close the handle answers `surface-gone: the user closed the browser`, and `open_pane` may reopen (the reopened window is agent-stamped).

## 38. An agent chooses its viewport, and the mechanism follows the surface

the pane is as wide as the task window's split leaves it (740px in the case that prompted this), which is under every desktop breakpoint, so an agent verifying a responsive layout measured the mobile rendering and reported it as the desktop one. `kangentic_browser_set_viewport` picks between three mechanisms rather than exposing them, because two of the three choices are silently wrong for a given surface. A LANE and a POPPED-OUT pane get a real `setContentSize`; a DOCKED pane gets `Emulation.setDeviceMetricsOverride`, the only lever that exists for a `<webview>` sized by CSS whose element cannot move without killing the guest. `entry.kind` does not separate the first two (a detached pane is still `kind: 'pane'`), so the dispatch also asks the pop-out registry; `withGuest` hands the resolved entry to the body for exactly this.

*Measured on Electron 41 / Chromium 146, against a live guest, because four of these decide the design:*
- An override DOES change the guest's layout viewport (1920x1080 from a 740px widget) and media queries fire at it.
- A guest's screenshot holds no more pixels than its widget, and asking for more TILES it. This bullet first read "`Page.captureScreenshot` returns the FULL emulated surface", on the strength of a capture that came back 1920x1079. That checked the decoded size, never the pixels, and the pixels were the page repeated in 740px strips. The mechanism, read from `page_handler.cc` and then measured: `CaptureScreenshot` works out a `requested_image_size` (the emulated view, or the clip, times the widget's scale factor, the emulated factor over the widget's, and the clip scale), then asks the view to grow to it. A tab's view grows; a `<webview>` guest's cannot. `ScreenshotCaptured` then "crops" the widget-sized bitmap to the requested size with `SkBitmapOperations::CreateTiledBitmap`, which repeats a source smaller than its target. The fix is a planner (`cdp/capture-bounds.ts`) that never asks a guest for more than `widget x display scale`: an override is sent at the display's own factor rather than 1/zoom, and anything still too big (a pinned `zoom: 1`, a fit clamped at the 0.25 minimum, an element or full page larger than the pane, a hidpi ratio) is captured through a clip scaled down to fit. It was measured with a standalone Electron 41 probe, a `<webview>` guest driven over CDP, at display scales 1, 1.25, 1.5, 1.75 and 2 and pane sizes from 400x600 to 1200x800. There, every request inside the bound came back clean and every one past it tiled, with the decoded size matching the formula to within the clip's own rounding. Three unit facts came with it: a clip is in DIP (CSS pixels times the zoom) and document-relative, while `DOM.getBoxModel` is CSS pixels relative to the viewport, so element screenshots had been capturing the wrong region on any zoomed or scrolled page; off-viewport content is only painted with `captureBeyondViewport`; and a clip scale above 1 re-rasterizes sharp. So a screenshot shows the WHOLE viewport at the pane's resolution, whatever the user's pane shows; `visibleFraction` stays a statement about the user's screen. The display's own factor is also the better default for the page itself. On the web demo, xterm's WebGL terminals rendered normally under the fit at that factor. They went black once an emulated ratio was sent, because the addon sizes its canvas from a device-pixel `ResizeObserver` that emulation misreports. The old 1/zoom default emulated a ratio on every call.
- **`scale` is never sent.** It is Chromium's own fit-to-widget control and it is the one configuration where CDP mouse coordinates stop matching `DOM.getBoxModel`: at `scale: 0.385` a click on a box-model centroid landed on `<html>` instead of the target and still reported success. That is the worst shape a bug can take here, and it is why the fit shrinks the layout with the zoom factor, which clicks survive, rather than with `scale`.
- **Zoom multiplies an override rather than fitting it.** A 1920 override at zoom 0.4 laid out at 4800, because the page uses override divided by zoom. The tool therefore scales the override by the zoom factor, which put 1920x1080 back in `innerWidth` from a 768x432 override with the click still landing. The visible cost is that a screenshot shrinks by the same factor. That is the honest size, not a bug to compensate: raising the scale factor to 1/zoom to undo it is what produced the tiled captures above. `screenshot_element` is the way to detail, since it re-renders a region at up to 1:1.
- An offscreen window has no frame, so a lane built at 1280x800 already laid out at 1280x800 and `useContentSize` changes nothing there; `setContentSize(5000, 4000)` was honored exactly, so a lane is not clamped to the display. A framed pop-out is the case that needs the measure-correct-measure pass, since its title bar and the pane's own chrome come out of the viewport.
- A lane is created with `offscreen: { deviceScaleFactor }` set to the primary display's factor, because Electron 42 changed the offscreen default to a fixed 1.0. Measured on Electron 44.5.1 with a forced 2x display: Electron 41 rendered a lane at `devicePixelRatio` 2 (2560x1392 screenshots), 44 rendered it at 1 (1280x696) without the option, and at 2 again with it. Left at 1.0, a page's `devicePixelRatio` would change whenever its surface moved between the pane and its offscreen form.

*Honesty.* Every path ends by measuring the page's own `innerWidth` and `innerHeight` (with `Page.getLayoutMetrics` only as a fallback, since its `clientWidth` drops the scrollbar) and reports what it read, never the request: `exact: false` says the surface gave something else. Echoing the request would hand an agent a measurement taken at a width the page never had, which is the failure the whole tool exists to remove.

*Who cleans up.* An override is CDP-session scoped, so it survives a navigation (deliberate) and is cleared by a debugger detach (confirmed). Neither covers the case that matters: the agent's session ends while the user's pane lives on. `markRecordExited` clears the overrides that session owned, beside the lane teardown; ownership is stamped when the override is applied rather than read back from the registry, because `register()` rotates `ownerSessionId` in place on a `/clear` and a registry-keyed clear would let the departing session wipe the incoming one's. The user's own way out is a chip in the pane's toolbar showing the measured size with a reset, since session end can be hours away.

*The drive cue moved onto the page, and its timing is measured rather than tuned.* Separate change, same pass. The old cue dimmed the TERMINAL to 40% and put a blue spinner reading "Agent typing here" in the pane's toolbar. Both were aimed at the wrong half of the split: main intercepts every keyDown at the guest and writes it to the terminal, so the terminal is the surface that still takes your typing and the PAGE is the one that cannot. The toolbar span also cost ~110px of URL bar, shifting the row every time it mounted. Now the terminal is untouched (no dim, no strip, no label - it stays unobstructed), and the pane carries a veil, a breathing accent ring and a static "Agent is driving" label, all absolutely positioned over the guest so none of them can move the toolbar or resize it.

Three results shaped it, each after a wrong first attempt. **Timing:** a 27-call agent verification measured one call holding the guest 253-929ms (median 272) with 1060-4428ms between calls, because the gap is the model thinking rather than the tool running. So the 400ms burst window never bridges it and every call is its own burst; a per-burst envelope either flashes 27 times or, with the 700ms grace tried first, suppressed 26 of 27 calls and showed nothing at all. The unit is now the RUN: bursts chained within 5000ms, opening on the second, closing on the last. **Legibility:** the veil was reported as not coming through on a white page; it was applied, but a static tint has no baseline, so motion (not a stronger tint) is the primary cue. **Input:** the veil swallows the pointer, which also closes a hole - clicking into the page disarmed the renderer's focus guard while main kept blocking keys, so keystrokes reached neither the page nor the terminal. A stop bypasses the envelope entirely and releases in the same render, because the veil blocking the pointer makes a slow release a lockout.

*Detaching is a relocation, not a viewport control.* `kangentic_browser_pop_out` / `_dock` reuse the existing pop-out surface unchanged, so the window is the same one the pop-out button produces: the shared frameless chrome titled with the task, and the same `BrowserPane` inside it. Two differences from the user's own path, both deliberate: it is opened with `showInactive` so an agent never takes the keyboard, and the size it applies is kept out of `popOutBounds`, which is keyed per KIND and would otherwise overwrite the window size the user chose for every task. The page RELOADS and the handle is replaced, because a `<webview>` guest dies when its node moves between documents; both tools wait for the successor guest and return its handle, and say what was lost.

## 39. A task has exactly ONE browser surface, and an agent cannot ask for a second

decision 27 gave a caller its own offscreen lane on request (`open_pane { isolated: true }`, capped at four per task). That comes out. The failure that ended it was reported from live use and is the whole argument: the user closed the Browser pane, re-prompted, and the agent completed an entire verification run with no browser anywhere on screen. Nothing in the UI could say otherwise - the card globe and the task-detail Browser pill both read `browserGuestTasks`, written in exactly one place (`BrowserPane.tsx`, on the `<webview>`'s `dom-ready`), which a main-process offscreen `BrowserWindow` never touches. So a lane was unseeable, unclosable, held the project's identity cookies, and bypassed every supervision guard decision 38 had just built, all of which live on the pane.

*The concurrency it bought was not real.* Parallel callers already contend for a single guest and are serialized by `guest-drive-queue` with a 30s timeout, so four lanes were a queue with four heads rather than four workers. Removing them trades a four-way invisible free-for-all for one visible surface with a queue: slower in a case that barely occurs, and supervisable in every case.

*What a surface IS, after the change.* One per task, in one of two forms. Normally the visible `<webview>` pane. OFFSCREEN when no pane can mount, which is exactly one situation: the caller's project is not the one currently open, and the board window layer renders only the open project's tasks. That fallback stays because removing it recreates a documented dead end - every drive returns `no-pane-open`, whose hint says to call `open_pane`, which used to refuse `project-not-open`, and the two composed into a loop. `openLane` refuses a second surface for a task outright (`surface-exists`), so the invariant is structural rather than a convention the callers keep.

*Three things make the offscreen form honest.* Main pushes the set of tasks holding one to the renderer (`BROWSER_OFFSCREEN_SURFACES`, the whole set on every change so a missed push self-corrects), and the card globe and the Browser pill read it alongside `browserGuestTasks` - so an offscreen surface looks exactly like a pane from the board. "Close browser" in the task menu destroys it (`BROWSER_OFFSCREEN_CLOSE`), because the ordinary close path retires a guest id and clears a pane flag, and an offscreen surface has neither, so without it the control said Close and did nothing. And opening the Browser pill RECLAIMS it: the pane mounts, and the pane's registration destroys the offscreen one (the same `onPaneRegistered` hook that already stood down a hand-off lane).

*The reclaim's URL is read from the live guest, not from the sidecar.* `browserUrlStore` is written by the PANE on its own `did-navigate`, and an offscreen surface has no renderer to write it - main's guest-side `did-navigate` bridge is gated on `getType() === 'webview'`, so it never fires for one either. Left alone, the reclaim would mount a pane on whatever page the task last had a VISIBLE pane on, which can be many navigations behind the agent. `BROWSER_URL_GET` therefore answers with the offscreen surface's live URL when one exists.

*Mechanically a re-create, not a move*, for the reason `pop_out` and `dock` already accept: a `webContents` cannot migrate from a `BrowserWindow` into a `<webview>` tag. The page reloads and `sessionStorage` is lost; cookies and localStorage survive (same partition); the agent's old handle answers `surface-gone` naming the replacement.

*Two gaps, stated rather than left to be found.* An offscreen surface is in its bookkeeping map before it loads its first URL and in the registry only after, so for up to the load deadline it is neither driveable nor absent; an `open_pane` landing in that window answers `surface-opening` and says to retry, rather than naming a handle whose every drive would answer `no-pane-open`. And the fallback does not consult the project's `browser.enabled` override, because reading it needs the project's path and the whole reason the fallback exists is that the project is not the open one - so a project that turned the Browser pane off still gets an offscreen surface while backgrounded. The cold pane path does enforce the gate, so the pane it would reclaim into never appears. The `isolated` branch had the same hole; the difference is that it was opt-in and this is automatic.

*`resolveMechanism` still forks three ways, and that is not an oversight.* The POLICY collapsed to one surface per task; the SUBSTRATES did not. An offscreen window is still a window that takes `setContentSize`, a pop-out is still a window, and a docked `<webview>` still has only emulation. Collapsing the dispatch would send an offscreen surface down the emulation path with a real resize sitting right there.

## 40. Seven tools added after measuring the family against the reference implementations

#697's live agent run was asked to scroll 600px and could not, which prompted an inventory against [chrome-devtools-mcp](https://github.com/ChromeDevTools/chrome-devtools-mcp) and [playwright-mcp](https://github.com/microsoft/playwright-mcp). Six capabilities both of them ship were missing here, and one primitive was already built and simply had no tool. The family goes 19 to 26.

*The one that was a RISK rather than a gap: JavaScript dialogs.* Nothing in the subsystem handled `alert` / `confirm` / `prompt` / `beforeunload`. A dialog blocks the renderer, so an agent clicking a Delete button on the user's dev app wedged the pane: every later CDP command queued behind the dialog and `pane-busy` fired after 30s, with no agent path to recovery and only the user's own dismissal to unblock it. That is the same unrecoverable shape as the non-composited capture hang, which was judged serious enough to need a hard timeout, and this one had no backstop at all. Now `Page.enable` is on and the message listener answers EVERY dialog - dismiss by default, which is the safe direction for all four types - records it, and exposes it through `kangentic_browser_handle_dialog`. Enabling `Page` is what moves dialogs onto the debugger, so the handler is not a feature beside it; it is the thing that makes enabling it safe.

The response is ARMED before the action, not chosen after it, and that is forced by the mechanism: a pending dialog blocks the renderer, so the call that would answer it could never run. An agent arms `accept`, then clicks.

*Two things only a live agent found, both after the first version looked correct.* A drive could OUTRUN the interceptor: `attachDebugger` is synchronous and its domain enables are fire-and-forget, so the first drive on a guest ran while `Page.enable` was still in flight, and a click that opened a `confirm()` in that window went native and wedged the pane. Every later call was fine, which is exactly why a sweep that calls a dozen tools before clicking never reproduces it. `withGuest` now awaits `waitForDialogInterception` before running any body. And Electron draws its OWN dialog regardless: enabling `Page` and answering `javascriptDialogOpening` does not stop Electron delegate, so BOTH fired - the page took the CDP answer and carried on while a native box stayed on screen whose buttons did nothing, one to dismiss per dialog. The guest is therefore created with `disableDialogs: true` in `will-attach-webview`; verified afterwards that accept and dismiss both still work, so the box cost nothing to remove. `prompt()` is unimplemented in Electron and throws in the page rather than opening a dialog, so `promptText` is unreachable for a `<webview>` guest.

*Scroll was unreachable, and the primitive was already proven.* `eval` (`window.scrollBy`) is gated off by default and `keypress` moved a line at a time, so "scroll down 600px" was fifteen calls. `Input.dispatchMouseEvent` with `type: mouseWheel` is the answer, and decision 27's lane spike had already MEASURED it working against a guest - it simply never got a caller. Two details bite. A wheel event carrying `button: 'left'` is rejected outright by Chromium, so it takes the pressless defaults a `mouseMoved` gets. And the keys are NOT an alternative: `SPECIAL_KEY_MAP` had no PageUp / PageDown / Home / End / Delete, which is worth fixing on its own so a page that handles them can be driven, but measured against a live guest they deliver the key WITHOUT the browser default action - two PageDowns on a focused document left `scrollY` at 0. The wheel is the only thing that scrolls, and the keypress description claimed otherwise for one commit.

*`<select>` could not be driven at all,* because the list it opens is OS chrome outside the page: a synthesized press reaches the control and then has nothing to aim at. `selectOptionOnSelector` sets the value through `Runtime.callFunctionOn` against the resolved node and fires `input` + `change`. Scoped to one element with a caller-supplied value rather than caller-supplied code, so it does NOT take the `eval` gate - the same line `typeText` already sits on.

*`drop_files` existed and was unreachable.* `dropFilesOnSelector` has been in the shipped driver since the drag work; only the dev-only `kangentic_devtools_drop_files` ever called it. Registering the browser tool was the whole change.

The rest close ordinary holes: `hover` (a hover menu could be clicked but never merely opened and photographed), `network` (the console only shows what the page chose to log, so "did that POST return 500" was unanswerable), and `history` (the pane's own arrows had no tool equivalent). Network reports a request still IN FLIGHT rather than hiding it, because a dev server that accepted the connection and went quiet is usually the answer being looked for.

*Deliberately not adopted.* Both references lead with an accessibility-tree snapshot as the primary interaction model; this family uses CSS selectors and keeps doing so. Heap snapshots, extensions, PWA install, PDF export, video capture and Lighthouse are out of scope for verifying a dev server, and the performance half already exists as `kangentic_devtools_capture_trace`.

## 41. The pane drops the `Electron/` token from its user agent

some web application firewalls reject any user agent containing `Electron/` as a bot. A firewall like that answers a stylesheet or script request with an HTML block page, and Chromium's Opaque Response Blocking discards it (`net::ERR_BLOCKED_BY_ORB` in the pane's network log). Any page that loads its assets from such a host renders as unstyled HTML in the pane while Chrome shows it correctly. Measured on 2026-09-22 with curl against one such host, changing only the user agent: the pane's default and `Electron/41.10.7` alone both got the block page, while `Kangentic/0.43.0` without the token and plain Chrome both got the CSS. The handshake completed, and curl sent no cookies, client hints or `Sec-Fetch` headers, so the token was the one trigger.

`applyBrowserUserAgent` (`src/main/browser/browser-user-agent.ts`) removes that one token with a regex and keeps everything else, `Kangentic/<version>` included. It sets the guest's `Session` and the guest itself, and neither call alone is enough, which was measured against a real guest in the E2E build. With the `Session` call alone, the guest's `navigator.userAgent` still carried `Electron/41.10.7`, because a WebContents takes the session's value when it is created and the guest already exists by the time the hook runs. With the guest call alone, the guest was clean and the popup it opened carried the token, because a popup inherits from the `Session` and not from its opener. `browser-popup-window.spec.ts` fails in each of those two states. It runs in two places. One is the webview branch of `web-contents-created`, which fires at guest construction and so before `did-attach` loads the first `src`. The other is the offscreen lane, which is not a `<webview>`, never passes through that hook, and can open before any pane has set its task's jar in this run. Popups get no call of their own and inherit from the `Session`. `app.userAgentFallback` is deliberately left alone, so Kangentic's own window and the default session still carry the token. Client hints (`Sec-CH-UA`) carry no Electron brand, so the string was the only thing to change.

*This reverses decision 15, which gave three reasons, and answers two of them.* The app still names itself to every site, because the `Kangentic/` token stays. There is no token list to maintain: one token comes out and nothing goes in. Google's anti-phishing reason stands, and it is accepted knowingly. Firewalls reject Electron because automation tools are built on it. The pane is agent-driven, and this change makes it look less like a bot. Google's OAuth popup may stop answering `disallowed_useragent` as a result. The refusal detector and its dialog stay in place for whatever Google still refuses.

*What else a firewall could key on, checked on 2026-09-22 and left alone.* Workers inherit the fix: a dedicated worker in the pane reported the stripped string in `navigator.userAgent` and sent it on its own `fetch`. The client hints name `Chromium` and `Not-A.Brand` at the same major version as the `Chrome/146` token, which is the pairing any Chromium-based browser sends, and adding a `Google Chrome` brand would claim a product the pane is not. The debugger an agent attaches enables `Runtime`. That was a common bot tell until Chromium M137 stopped the console preview from running page getters. Electron 44.5.1 ships Chromium 152, well past it, so turning those domains off buys nothing measurable. The line this change holds is to remove the one token that names an automation runtime, not to impersonate Chrome. If a firewall blocks the pane again, compare its request headers with Chrome's before changing anything else.
