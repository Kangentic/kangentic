# Process reaping

A process still running inside a worktree blocks its removal on Windows, which will not delete a directory that is a live process's current directory. That leaves a husk with no git admin entry, and the next worktree creation on that path hangs. Two mechanisms clear it, and they cover different failure modes.

**At a terminal transition (`src/main/pty/process-tag/`).** This is the one that catches the common case: an agent backgrounds a dev server, the task moves on, and the server keeps running. Every session's PTY is spawned with `KANGENTIC_TASK_ID=<taskId>` (a Command Terminal's made-up task id, or a workflow agent's workflow id, which no task shares), and every process the agent starts inherits it, however it detached: `nohup`, `Start-Process`, `cmd /c start`, `setsid`, a launcher that exited before anything could observe it. A terminal transition (move to Done, move to To Do or Backlog, unarchive into To Do, task delete, project delete) calls `reapTaskLeftovers` once the task's sessions have exited (the reap itself also waits, up to 3 s, for a young session's PTY still parked on its exit grace, since the host protects a PTY it holds and everything under it), and the pty host kills what the task left running: every process carrying the task's tag and working inside the task's project or worktree, minus anything shared or visible (see "What the reap kills" below). Pressing Stop or parking a task in an auto-spawn-off column (including a Code Review entry, which suspends the task agent) does not reap, so a dev server stays up for manual testing until the task finishes. Before that reap, the same transitions close the task's pop-out windows and destroy its offscreen browser lane (`closeTaskWindows`, `src/main/ipc/helpers/task-windows.ts`), so a closing Browser window does not stand up a lane for an agent that is still stopping. A Command Terminal is tagged and reaped the same way when it ends (see [command-terminal.md](../renderer/command-terminal.md#leftover-processes)).

The tag replaced a per-session snapshot of the PTY's descendant pids, which missed most of what it was built for. The snapshot was deleted at every suspend, so a task that passed through Code Review reached Done with no record of the agent that started the server; it never contained a process whose launcher exited inside one 2 s watcher cycle; and it died with the app. The tag is the same value across every session a task runs and lives in the processes themselves, so it survives all three: a task parked across a restart is still reaped at its later Done. This is the mechanism Jenkins' ProcessTreeKiller has used since 1.260 (`BUILD_ID`), including its opt-out: a process started with the tag cleared (`KANGENTIC_TASK_ID= npm run dev`) no longer belongs to the task. One kept that way and running inside the worktree still holds it, so on Windows the Done move leaves the directory for the startup retry, as a preview run showed.

**How each platform reads it.** Each platform reads the tag and the working directory differently, all in the pty host. Linux reads `/proc/<pid>/environ` and `/proc/<pid>/cwd`. macOS reads everything from the kernel through koffi: the process list, parents and start times from libproc (`proc_listallpids`, `proc_pidinfo`), each same-user process's `KERN_PROCARGS2` record, and the working directory (`PROC_PIDVNODEPATHINFO`, the call `lsof -d cwd` makes); only `lsappinfo` is still spawned, once, when a scan finds a tagged process. When it cannot start, exits with an error, or times out, the scan fails and the reap stops before its next kill, because its window list is the only protection a dev-built app outside an Applications folder has. A test on both macOS runners checks those reads against `ps` and `lsof` on the same processes. Windows, which has no API for another process's environment, reads both out of the target's PEB through koffi, and only for processes in the caller's own Windows session and owned by the caller's user. A Windows scan that cannot read the caller's own session or user fails, so the reap reports it rather than finding nothing. A reader matches the tag inside the raw buffer and returns only its value: environment contents, which hold other applications' secrets, never leave it.

After each of the reap's two planning scans the reader also reads which local processes hold a TCP connection to a port the task's processes listen on (`connections`, paired in `local-connections.ts`), and returns pids only. Windows reads the machine's TCP table with `GetExtendedTcpTable` (IPv4 and IPv6, each socket's owning pid, no process handle). Linux reads `/proc/net/tcp` and `tcp6` and maps each socket's inode to its process through `/proc/<pid>/fd`. macOS has no such table, so it reads each process's sockets from libproc (`PROC_PIDLISTFDS`, then `PROC_PIDFDSOCKETINFO`, the calls `lsof -i` makes). Linux and macOS read the listeners' sockets first and a client's only while a connection's peer is still missing. A connection pairs through the socket the listener accepted, not by address, and a v4-mapped address reads as IPv4, so an IPv4 client of a dual-stack listener pairs across the two tables (measured on all four runners against `ss`, `lsof` and `netstat`).

**What it costs.** The reap is meant to cost almost nothing: no polling, no spawned process on the Done path except `lsappinfo` on macOS (once, and only when a scan finds a tagged process) and the WSL in-distro reap (only for a WSL shell), one scan per terminal transition. A bulk delete reaps task by task, because each task's cleanup waits for its own sessions to exit first; the host merges reaps that arrive while one is running and the delete works on two tasks at a time, so batching the reaps was not worth splitting every cleanup into phases. A scan costs ~30 ms for ~460 processes on Windows and yields to the event loop as it goes, because the host carries every terminal byte; the Toolhelp snapshot it starts from is one 5.7 ms native call, so it runs on the thread pool. The connection read after it measured 1.3 ms on Windows, 0.3 to 0.4 ms on macOS and 12.7 ms on Linux for three listeners and two clients on GitHub's runners, and 2 to 27 ms with every process on the machine asked about (3.1 ms over 540 processes on a developer's Windows machine). It is skipped when no unprotected process carries a reaped task's tag (a macOS withheld orphan in a reaped worktree also counts).

**How long a batch may take.** The host runs one reap batch at a time, so main's budget for a reap (`TASK_REAP_TIMEOUT_MS`, 30 s) is one batch's, counted from when that batch starts. The host posts `batch-started` as each batch or Stop starts, and the transport gives every request of that method still waiting its full budget again. Measured on a developer's Windows machine (445 processes, ten runs each) with the real reader: a reap with nothing to kill took 27 ms and a batch that killed three processes 1.07 s; with every core busy, 0.3 s and 3.2 s at the median, 6.6 s at most; pinned to one core beside three busy threads, 1.3 s and 7.3 s, 8.5 s at most. That last case stands in for the throttled low-end machine behind Sentry DESKTOP-1X. There a reap with nothing to kill, queued behind a killing batch, waited 7.4 to 8.2 s before its own batch started and got its answer 10.6 s after it was sent. Timed from the send, as it used to be, the wait alone spent 70% of the old 15 s budget, and a queued reap that had processes of its own to kill would have run out. The 30 s budget keeps 3x headroom over the slowest batch measured. A failure that gets no result back reports `host_timeout` (a running host let the budget run out), `host_exited` (the host exited or was down) or `host_error` (anything else), by the transport's error type. A timeout cancels nothing in the host, so a reap main gave up on can still kill. Its answer is still taken when it arrives: it is logged and reported like any other, what it did goes in the toast, and a Done task it stopped something of has its worktree removal tried again (`retryDoneWorktreeRemoval`), since the move went on to that removal while the reap still ran.

**When it fails, and what is counted.** A reap that fails (a reader that would not load, a scan that listed nothing, an error, a host that exited, or a WSL in-distro reap that failed) kills nothing after the failure. A host that is merely slow is the exception: main gives up at the budget, but the host finishes the reap and its answer is reported late (see "How long a batch may take"). One before the first pass kills nothing at all, and one after it skips the force pass and lists what it had asked to exit as not stopped. Main reports it to Sentry once per stage and code per launch with a fixed code, never the failure's text (`task-reap-failure-report.ts`). On macOS a process list the kernel refused and a window list `lsappinfo` could not give each have their own code, a connection read that failed has its own on every platform (`connection_list`), and a failure inside a scan pass also names the pass, which says whether anything had been signalled. A Stop whose scan fails is reported the same way, as stage `stop`; a Stop that refused a process or found it still running after the force kill is an answer and is not reported. What a reap did is counted, not reported: each toast's report sends one `leftover_processes` analytics event with how many processes were stopped, kept and could not be stopped.

**The packaged smoke.** The package smoke (`scripts/package-smoke.mjs`) runs a real reap in the packaged app on Windows, macOS and Linux: a task's terminal leaves a detached node process in the project, the task is deleted, and the process must be gone.

**How it kills.** Before its first scan, a task reap waits up to 8 s (`AGENT_EXIT_WAIT_MS`) for the agent a killed shell left running to exit by itself (`awaitAgentExit`), so the scan does not force-kill an agent still shutting down. The wait returns as soon as that agent is gone. The reap then runs in two passes: ask each target to exit, wait 1 s, rescan, and force-kill what the second plan still holds. A process it asked to exit that a last scan still lists is reported as not stopped, whether or not the second plan held it. Each kill re-checks the target's start time, so a pid reused since the scan is never touched. A startup sweep, once per project per launch, reaps archived and To Do tasks whose transition's reap was cut short by a crash.

**Why koffi.** Reading another process's environment needs native calls on Windows (the PEB) and macOS (`KERN_PROCARGS2`), and Node has none. koffi is an FFI built on Node-API with a prebuilt binary per platform, so no contributor needs a C++ toolchain and an Electron upgrade needs no rebuild. Each alternative cost more. An addon of our own needs a compiler on every Windows machine or a prebuild pipeline the repo does not have. PowerShell `Add-Type` compiles for 1 to 3 seconds, and PowerShell reading process memory trips security software. `node:ffi` is experimental and exists only in Node 26. `@vscode/windows-process-tree` reads neither environments nor directories. koffi has one maintainer and is developed in the author's monorepo on Codeberg (`Koromix/rygel`, `src/koffi`); the GitHub repository `Koromix/koffi` is a front with no code, which is why its star count is low. npm counted about 4.4 million downloads a week in late September 2026. The exposure is bounded: koffi is pinned exactly with lockfile integrity hashes, loads only in the pty host, and a failure to load stops nothing and reports `reader_load`. A bump re-runs the real-process reap on all four platforms (`task-reap-real-processes.yml` watches `package.json` and the lockfile) and the packaged smoke on three.

## What the reap kills

The tag alone over-reaches. A shared, long-lived process that a task's agent happened to start first inherits it too, and then serves the user's other work. A probe run on GitHub's Linux, macOS and Windows runners started the candidates with a tag from inside a fake worktree and recorded what came up tagged and where it worked. So the reap (`reap-plan.ts`) kills a process only on all of these:

- **It carries the task's tag, and its working directory is inside the task's project or worktree.** The project holds `.kangentic/worktrees/`, so it outlives a deleted worktree for the startup sweep. Each directory is compared as stored and as its native real path (a junction, `/tmp` against `/private/tmp`, and an 8.3 `RUNNER~1` name all differ from the stored string). A filesystem root, a drive root and the home directory are never roots; home is matched as stored and as its real path, so a home reached through a link (`/home` linked to `/var/home`) is refused in both forms. A process whose directory cannot be read is never killed. Measured, this spares the Gradle daemon (it moves to `~/.gradle/daemon`), git's credential cache (its socket directory), `ssh-agent` on macOS (`/`), Chrome on Windows (its install directory), an app opened with `open` (its sandbox container), and any daemon that moves to `/` or home when it detaches. `ssh-agent` and `gpg-agent` never read as tagged on Linux.
- **Nothing under it shows it is shared.** A descendant whose environment reads without this task's tag (untagged, cleared, another task's), or whose directory lies outside the task's, spares the process and everything under it, the task's own processes included. Measured: pm2's daemon stays in the worktree, and an app the user starts later from an untagged shell runs under it untagged, so the daemon survives with all its apps. It follows that a child started with the tag cleared (the documented opt-out) is never killed through its parent: it saves the parent. A Windows console host (every console process has one, in the Windows directory) and a descendant whose directory cannot be read (a zombie, a setuid helper) are no evidence.
- **No other Kangentic work holds a TCP connection to it.** A shared server is not always a parent. The adb server keeps the working directory of the client that started it, carries that client's tag and has no children (measured on Linux, macOS and Windows), and every other client reaches it over TCP on 5037. A process that listens on a port is spared with everything under it when a client connected to that port runs under a live session's PTY (another task's agent, the user's Command Terminal), carries a tag no task of this reap owns (another task's, or a cleared one), or is spared as shared itself. That last case is the emulator: the adb server holds a connection to the emulator's adb port, so a headless emulator another task drives through adb is spared through the server. The connection spares only the listener. What started it stays only under the next rule, when the listener is all it has left running. No evidence: the reaped task's own processes (its agent's browser on its dev server), Kangentic's own processes outside its sessions (the network service behind a Browser pane, found by walking up to main without passing a live PTY), and, by decision, an untagged process outside Kangentic, since a dev server open in the user's browser must still stop at Done. What the first pass kept, the second keeps, so a client command that ends inside the one-second grace does not let the force pass kill the server it used.
- **It is not merely the launcher of what is kept.** A process whose every child is protected or spared is kept too, with the reason of what is under it, unless it listens on a port itself. The emulator launcher holds no socket and its only child is qemu, which owns the window (measured on Windows). Killing the launcher frees nothing while qemu runs, and the report would call a running emulator stopped. A dev server that opened a window listens on its port, so it still stops and the window is kept. A console host is not a child for this, and a child that survives for any other reason (an unreadable directory) does not keep its parent. A process the first pass already asked to exit is never kept this way, so a shell that ignored SIGTERM, with only a spared server left under it, still gets the force kill.
- **It is not protected.** Never killed, with everything under them: Kangentic's own process tree, every PTY the host still holds, a visible app, and a tmux server. A visible app is one that owns a visible top-level window with area on Windows (`EnumWindows`, `GetWindowRect`; Character Map and Chrome on the runner), maps a GUI toolkit on Linux (xterm and Chrome under xvfb), or is a UI app on macOS (`lsappinfo` Foreground or UIElement, or the main executable of an app in an Applications folder; not merely an app bundle, since `/usr/bin/python3` runs from inside one). A tmux server keeps the worktree as its directory and copies the environment it started with into every later session, including one opened later from an untagged shell in `/` (measured on Linux and macOS), so under a tmux server the tag stops naming a task. On every platform these roles are read for the task's processes and what runs under them, never for their parents: a desktop shell or a terminal emulator maps a GUI toolkit too, and reading one as a visible app would protect everything under it. An app or tmux server the agent started carries the tag, so it is read. Windows Terminal is the Windows case, twice over, and it is why the window must also have area. Terminal owns a real window and is the parent of every tab's shell, and it shows a pseudo console window for each tab that `GetWindowThreadProcessId` attributes to the tab's shell, at 0 by 0 (measured on Terminal 1.24: owned by Terminal's own window, `WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE`). The Windows reader used to read every process's window, so both counted, and together they protected a `/preview`'s `cmd` tab, its dev server and its Electron from a Done move. A minimized window keeps its area (160 by 28 at -32000), and so does a classic console window, so a program in its own console window is still a visible app. Kangentic's own node-pty shells have the same pseudo console window, never shown (measured: `IsWindowVisible` false for every one, with no owner), so only a real Windows Terminal reproduces the tab case; CI's Windows runner has none, and the real-process workflow unpacks a portable one for it.

What that leaves running, by design: a visible app the agent opened (the user sees it and closes it), a task's own tmux sessions, a task's pm2 apps once anything else runs under the daemon, a process the agent started outside the project (`cd /tmp && nohup ...`), an `env -i` child that saves its tagged parent, a server another task is connected to, and the launcher of a kept window or server. On Windows a kept adb server or emulator works in the task's worktree, so the worktree's removal fails until it exits, as it does for any kept window there. A program the agent started in a Windows Terminal tab is not on this list: neither Terminal nor the tab's shell is a visible app, so the tab's shell and what it runs are reaped like any other process (measured: a `cmd /c ping -t` tab, reported as one stopped process). Terminal then keeps the tab open as "[process exited with code 1]". That is a decision, not an oversight. Measured on Terminal 1.24, a tab whose shell is terminated with exit code 0 closes and one terminated with 1 stays. But the reap terminates a tree's processes all at once, and with exit code 0 a `cmd /c "a && b"` whose `a` was reaped first would start `b` before its own kill landed. Exit code 1, what `taskkill /F` uses, stops the chain, so the reap keeps it and leaves a dead tab.

**A conversation in Claude Code's own background session.** `/bg` moves a task's conversation into a background session that Claude Code's supervisor runs outside the task's PTY, tagged and working in the task's folder, so the reap would kill it with no exit of its own. Before anything else, `reapTaskLeftovers` stops it through the agent CLI's own stop (`AgentAdapter.stopBackgroundSession`, `claude stop <id>`, measured to run its SessionEnd hook) for each task whose newest records' own events file shows the conversation started there. That stop is not gated on "Stop leftover processes": it ends the task's own agent, which every terminal transition ends. A Command Terminal has no session record, so its end stops one on the agent's own transcripts instead (`AgentAdapter.isInBackgroundSession`, no CLI): `CommandTerminalLeftoverReaper` starts the stop at the removal and its reap waits for it. See [Claude Code background sessions](../../integrations/agents/session-history.md#claude-code-background-sessions-bg).

**A `/preview` in the worktree (dev builds).** A `/preview` is a terminal running `scripts/dev.js`, which runs Vite and a preview Electron. Reaped like the rest, it fares badly: on Windows `dev.js` gets a hard terminate and never runs its stop path, and its Electron, kept for its window, sits on a dead Vite and holds the worktree. So in a dev build, with stopping on, `reapTaskLeftovers` first stops every preview in each task's worktree through the same stop file `node scripts/worktree-preview.js --stop` writes (`src/devtools/main/worktree-preview-stop.ts`), but it waits only 15 s and never force-kills. It writes `<worktree>/.kangentic/preview-<port>.stop` for each live pid file. `dev.js` polls for it every 500 ms and acknowledges with `preview-<port>.stopping`, then asks Electron to quit through its real quit path (at most 8 s), cleans up and exits 0, and the terminal tab closes itself. A preview that has not acknowledged within 1.5 s is a stale pid file whose pid was reused (or an old `dev.js` with no watcher), and is left to the reap, as is one whose stop file could not be written, which returns at once; one still running at 15 s is too. Every preview is stopped at once, so N previews cost one wait. It reads pid files, not tags, so it also covers macOS and Linux, where the preview's terminal probably never carries the tag (not measured).

`dev.js` exiting is not the preview being gone, and the reap used to scan as if it were. Captured on Windows 40 ms after `dev.js` stopped answering: the tab's `cmd` was still running, Toolhelp still listed `dev.js` under it while it finished terminating (its exit code, which the liveness check reads, is set first), and under that sat the detached deleter `dev.js` starts on its way out to delete the clones its ephemeral cleanup moved into `.kangentic/trash-*`. The deleter carries the task's tag and works in the temp folder, so the plan read the tab's `cmd` as shared and the list said it was still running. The `cmd` was gone about 110 ms later, and the deleter, still deleting inside the worktree for about three seconds, is what a `git worktree remove` right after it trips over. So the reap's stop file says why it was written (`worktree-removal`, where `--stop` writes a timestamp), and `dev.js` then skips its ephemeral cleanup: the worktree removal that follows deletes all of it, and a worktree that survives has its data folder cleared by the next preview's boot. Before writing it, the stop records `dev.js`, everything under it, and the launcher's `cmd` above it from the pty host's process listing (pid, parent and name, no process opened), and once `dev.js` has exited it waits up to 2 s for every one of them to leave the listing, adopting a child that appears during the quit. Measured after the change: the tree was gone 71 ms after `dev.js`, and the scan at that moment held nothing of the preview.

What the connection signal misses. It sees only what is connected at the scan. An adb server with no command in flight is killed when the task that started it ends, and the next `adb` command restarts it; a headless emulator whose only client is that idle server goes with it. A command running at the scan is safe, which is the harm the signal was added for: in the incident another task's `adb install` failed with "daemon not running" mid-flight. It also misses Unix-domain sockets and named pipes, a client on another host, an untagged client outside Kangentic (the user's own Android Studio, by decision), and anything the in-distro WSL reap kills, since that script cannot read connections.

## Parent pids Windows reuses

A Windows process keeps its parent's pid after the parent exits, and Windows hands that pid to new processes. A tree kill that follows recorded parent pids without comparing creation times therefore ends a stranger's tree as soon as a process in the tree it was asked for holds such a pid. A tree kill in another tool ended a developer's whole terminal window this way. Two runs of `scripts/probe-taskkill-stale-parent.mjs` on Windows 11 Pro build 26200 (2026-10-21) planted an orphan whose launcher exited, started pings until Windows handed one the launcher's pid (after 359 and 1,035 starts, 12 and 11 s), and tree-killed that new owner. Both times `taskkill /PID <new owner> /T /F` killed it and its console host and left the older orphan running: taskkill adds a process to the tree only when it was created after the parent it names. `taskkill-stale-parent.test.ts` reruns the probe on Windows in `task-reap-real-processes.yml`.

That covers what a tree kill finds under a pid. The pid itself must still name the process meant, because `taskkill /PID X` ends whatever holds X when it opens it, about 550 ms after the spawn (median of 10). How each path that ends a process keeps both:

| Path | Selected by | What it walks | The pid it ends |
|---|---|---|---|
| Task reap (`planReapDetailed`) | tag and directory | children created after their parent, never through a process with no identity | the reader re-checks the creation time on the handle it terminates through |
| Stop from the leftover list (`subtreeOf`) | the report's pid and start key | the same | the same |
| Dead-shell orphan cleanup | children created inside the shell's own lifetime | children created after their parent | creation time re-checked on the terminating handle |
| Removal-failure reap (`reapProcessesForWorktree`) | path needle and orphan gate | the Stop's walk | on Windows, the pty host's Stop by the `CreationDate` its scan read (a Stop that cannot answer leaves the holder running and named, never killed by pid) |
| CLI runs, init script, run-script, project search | Node's own child | `taskkill /T` | only while Node has not handled the child's exit, so its handle still pins the pid; the pty host also pins its runs' pids until taskkill exits |
| PTY shells (node-pty's kill) | the session | none | pinned by the pty host from its pid to its exit (`pinRoot`) |
| Quit failsafe | this process | `taskkill /T` | this running process |

The orphan cleanup's window used to run from a clock read a second before the spawn to the moment the host handled the exit, which node-pty reports about a second late. A process the pid's earlier owner started just before the shell, or a child of a newcomer that took the pid in that second, fell inside it. Now the pty host holds a handle on every Windows PTY root from the moment node-pty sets its pid until it handles the exit, and reads the exact creation and exit times off it; without both the cleanup does not run. The handle also covers node-pty's own kill, which closes its handle on the shell before it records the exit and kills the shell's pid by number in between. It is released as the exit is handled, not later: a dead shell held open stays in the process listing, where the reap's protection walk from main would reach the leftovers under it. Measured on a real ConPTY spawn, the shell's parent is the spawning process and it is created 28 to 127 ms after the clock read before the spawn, which is what `pinRoot` checks.

The removal-failure reap's scan is cached up to 5 s, so its candidates are pids from the past. On Windows it stops each one through the host's Stop (registered at startup, `setIdentityTreeStop`), which matches the pid and the creation time the `Win32_Process` scan read (`CreationDate` landed on the reader's millisecond for 483 of 483 processes measured), so a pid that changed hands since is answered as ended and left alone. One stop costs about 1.1 s, most of it the reap's 1 s grace, against about 0.55 s for the bare-pid taskkill it replaced. The removal waits for its stops inside its project's git queue, so main gives each 5 s, not a reap's 30 s, and posts them all at once. The host runs stops one at a time, and each waiting stop gets its budget back as the one before it starts, so a free host finishes every one. A stop that hangs times the rest out with it, so a hung host holds the project's worktree operations 5 s, not 5 s per holder. A stop that times out still finishes in the host, and the removal goes on to name its holders. Its failures stay in the local log rather than reaching Sentry as a failed Stop, since nobody asked for it from the list. A scan row with no creation time is skipped and logged, never stopped by pid. The dev-build boot sweep runs after `register-all.ts` registers the Stop, so on Windows it stops its candidates by identity the same way.

None of this arises on Linux or macOS: an orphan is handed to init, a subreaper or launchd, so a parent pid always names a live parent.

What still names a bare pid, and why it stays:

- After a pty host crash, main stops each lost PTY's tree, and each run the host was running, by pid (`stopLostPtyTree`, the `RemoteCliProcess` orphan stop), and at quit it stops every CLI run's tree by pid (`stopAllCliRuns`). The host that held their handles is gone or going, and main loads no Windows process API to pin with.
- A local child's taskkill (a CLI run in main when no host is registered, the init script, a run-script, the project search's git) starts while Node still pins the pid, but taskkill opens it about 550 ms later. The child would have to exit by itself inside that window and Windows hand its pid to another process inside it too, where reusing one given pid took 359 to 1,035 process starts in the probe.
- The in-process host that takes over after five host crashes has no Windows process API, so it pins no PTY root and runs no orphan cleanup.
- The E2E leak janitor kills its candidates by pid, and so would the removal-failure reap on Windows where no identity Stop is registered (`endCandidates` falls back to `killProcess`). Registration runs at startup, so a running app does not reach that fallback.
- The removal-failure reap off Windows signals one pid from a scan up to 5 s old. Linux and macOS hand out pids in order.

`process-kill-sites.test.ts` keeps this list closed: a terminate primitive outside its classified files, a taskkill that is not `/T /F` of one pid, or a tree-kill package fails it.

## What the user is told, and the setting

Every reap reports back (`planReapDetailed`, `reapTaggedOnce`): the top of each tree it stopped, anything that outlived even the force pass (a last scan 500 ms after it), and the task's own windows, tmux servers and shared roots it left running, and the launcher of a kept window or server, reported in its place on purpose, top only, so a pane or a pm2 app that may be the user's is never listed. Daemons that moved out of the project are not listed: they serve all the user's work, and listing them would put a toast on most Done moves. Main gathers the results of one burst of transitions into one report (`leftover-process-reports.ts`: once no reap is running and 400 ms have passed with no new result, at most 8 s after the first), so a bulk delete or a project delete is one toast, and pushes it on `leftoverProcesses:report`. Waiting for quiet alone was not enough: the host runs a request that arrives during a reap in its next batch, after the first batch's one-second grace, and a preview run showed two tasks reset together toasting a second apart. The renderer's toast gives counts only and, with stopping on, stays until closed while something is still running or could not be stopped, since its Review link is the only way into the list. A toast that stays leads with that reason ("2 processes from "Fix login" are still running.", or "Couldn't stop 1 process from "Fix login", and 1 more is still running.") and leaves what stopped to the list; one where everything stopped says so ("Stopped 3 leftover processes from "Fix login".") and closes on its own. A toast that stays also shows how long ago its report came ("37 minutes ago", from the report's `reportedAt`, ticking while it is up), as does the list under its title, with the exact time on hover: a sticky toast once sat on screen for 37 minutes and read as a reap that ran late. With stopping off it is an ordinary timed toast, and Review still opens the list. The renderer keeps the last 20 reports, and the one the list shows while it is open, and a toast whose report it drops closes with it, since its Review link would open nothing. When the stack passes the visible-toast limit (`notifications.toasts.maxCount`, 5 by default), toasts that close on their own are trimmed first (`withinToastLimit`), so routine toasts never push it out; only more toasts that also wait to be closed can. The startup sweep reports only what it stopped or failed to stop, and does not scan at all while stopping is off: what it leaves running was reported when its task ended, and naming it again would repeat the toast on every launch. The list names each process, says why one kept running ("Has an open window.", "A tmux server. Stopping it ends all your tmux sessions.", "Other work uses it too. Stopping it can break that work."), and gives each a Stop button. Once the user stops one, its row says where it ran, like any stopped row, since the reason and its warning no longer apply. A Stop that runs past its budget first reads "Couldn't stop it", and the row corrects itself to the real outcome when the host finishes (`leftoverProcesses:stopSettled`). A Stop names the process by an id the report minted, never by pid; main resolves it to the pid and start key the scan saw, and the host stops that process and everything under it after re-checking its identity (`stopProcessTree`). It stops the tree its first scan saw. A child the process starts in the moment between that scan and the kill is not adopted afterwards: once its parent is gone, on Linux nothing shows whether a process naming that parent's pid is its child or a stranger that reused the pid. Such a child still carries the task's tag, unless it cleared it, so the task's next terminal transition reaps it. Kangentic's own tree and every held PTY stay out of reach exactly as in a reap. Once a stopped process is gone, main retries the removal of its task's worktree when the task is in Done and the worktree is still on disk (`retryDoneWorktreeRemoval`): on Windows a window or server kept in the worktree is what made the Done move's removal fail, and otherwise it waits for the next project open. Nothing is reported when nothing was left running, so most Done moves look as they did.

A process the reap kept can exit on its own, and a row that still says it is running then holds a toast open for as long as the app runs. So while a row that claims a live process (kept, or not stopped) is on screen, through its toast or its open list, the renderer asks main which have ended (`leftoverProcesses:check`, by report id), every 5 s while the report is under a minute old, every 30 s after that, and at once when the list opens. Main resolves each id to the pid and start key the scan saw, and the pty host reads only that identity (`isRunning` on the reader: one limited handle on Windows, creation time and exit code; one `stat` read on Linux; one libproc row on macOS), never a scan of every process's environment. A process counts as ended only on evidence: a changed start time, an exit code, a zombie, or a pid the listing no longer has. A read that fails answers unknown and changes nothing. The row then reads Ended in its place, an ended process retries its Done task's worktree removal as a Stop does, and a toast whose report no longer names anything running closes. Nothing is asked while no leftover toast or list is up. The reap's log names what it left running too, one `[TASK-REAP]` line per process it kept, could not stop, or left running with stopping off, with its label, pid, short task id and place, the reason, and what the reason rests on (its own role, the descendant or the client that made it shared, labeled the way a reported process is, or children that were all kept), so a kept process can be explained from the log alone.

Windows sets a process's exit code before the process leaves the Toolhelp listing: a terminating process stays listed, creation time and all, until its last thread is gone, and the capture above found `dev.js` still listed at least 75 ms after its exit code was set. (One that has finished exiting is not listed, even while another process holds a handle to it; checked by holding one open from PowerShell.) The Windows reader marks a listed process whose exit code is set as `exited` (on the limited handle it already opens) and reads nothing more from it, so it is no longer counted as an unreadable environment. It stays in the scan, so a parent link through it still reaches what runs under it for the protection walks, but every check that asks whether a process is still there counts it as gone: a kill that landed is reported stopped rather than "Couldn't stop it", and a Stop of a process that already exited answers ended. And a Done move whose own worktree removal fails tries once more 10 s later (`scheduleDoneWorktreeRemovalRetry`) before leaving the worktree to the next project open, since a holder already on its way out (the preview's cleanup helper above) is gone within seconds.

A process is named by its program and, for an interpreter, its script: "node (vite)", "python3 (http.server)" (`process-label.ts`). A command line can carry a token, so the reader parses it in place and returns only that label: the script's package or file name when it is an existing file, the module after `-m`, or the first word of a title the process set itself (npm's title holds its arguments). The command line is read only for the few processes a report names.

"Stop leftover processes" (`stopLeftoverProcesses`, Settings > Behavior, on by default) turns the killing off, not the reporting. Off, the reap still scans and plans, kills nothing, and the toast lists what kept running; the WSL in-distro reap, which reports nothing back by name, does not run.

**At removal failure (`reapProcessesForWorktree`).** The backstop for a holder the tag cannot see: a process Kangentic never started, or one that rebuilt its environment. It scans every process image for the worktree path in the command line or the executable path, and retries the removal once. On Windows, with the pty host up, each holder is stopped there by the creation time the scan read, never by bare pid (see "Parent pids Windows reuses"). Lazy by design: a clean Done-move never runs the OS process scan, so the ~900ms cost lands only on a delete a held handle actually blocked. Skipped under `NODE_ENV=test`, where the E2E leak janitor owns process sweeps instead.

This path keeps the orphan gate: it can reach processes Kangentic never spawned (a terminal the user left `cd`'d into the worktree, an editor), and killing a supervised process would be wrong. It can afford that caution only because the task reap above already ends what a task's agents started. A supervised holder is named rather than killed: `describeWorktreeHolders` puts it in the error `createWorktree` surfaces, so the user gets `Held by node.exe (pid 12345)` instead of generic advice to close anything using the path. The holder scan reuses the reap's cached process list, so it costs nothing, and it applies the same needles as the reap so it can never see less than the reap would kill.

`Win32_Process` exposes no current-directory property at all, so neither the removal-time scan nor the holder scan can see a process that references the worktree only through its cwd. Matching cwd on POSIX alone was tried and dropped: it bought little once the task reap covered agent-spawned processes, and it made behavior diverge by platform in a subsystem whose whole problem is a Windows limitation. The task reap reads working directories itself, on every platform including Windows (from the PEB), but only as a second signal beside the tag, never as a reason to kill on its own; the macOS withheld-orphan match below is the one narrow exception. That is exactly the shape of the incident this was built for, and it is why the task reap is the primary mechanism rather than the hardening. An empty holder list therefore means "no holder we can see", not "no holder".

The tag misses a process that rebuilds its environment from scratch: `env -i`, `sudo`, `systemd-run`, launchctl, `Start-Process -UseNewEnvironment`, a service, or a Task Scheduler or WMI launch. An agent CLI that can narrow what its tool shells inherit is covered where Kangentic can reach it: Codex's `shell_environment_policy` (`inherit = "core"`, `include_only`) would strip the tag, so the Codex adapter re-injects it with `-c shell_environment_policy.set.KANGENTIC_TASK_ID=<id>`, which wins over the policy's filters and adds to a user's own `set` entries (measured with `codex sandbox` on codex-cli 0.154.0). An `env -i` child of a live tagged parent reads as untagged, so it saves the parent rather than being caught through it. It also cannot read a non-dumpable Linux process or an elevated Windows process; each reader counts a same-user process it could not read, and the reap logs that count. The Windows reader reads the live environment block, where Linux and macOS read the one the process was exec'd with, so a process that deletes the tag from its own environment after it starts escapes on Windows only. The documented opt-out clears the tag at exec and behaves the same everywhere.

macOS needs two more things. First, the tag is read from the kernel record directly, not from `ps -E`: a process that sets its title (npm itself, Next's `next-server`, pm2) rewrites its argument area, `ps` stops reading at the first double NUL, and its environment vanishes from `ps -E` while the record still holds it intact (measured on macOS 15 and 26). The reader searches the whole record for an exact `KANGENTIC_TASK_ID=` entry. Second, a membership source for what the kernel hides. XNU's `sysctl_procargsx` leaves the environment out of that record when the target is `CS_RESTRICT` and System Integrity Protection is on, unless the caller holds Apple's private `com.apple.private.read-environment-variables` entitlement. A probe run on every GitHub macOS image (14.8, 15.7 and 26.6 on Apple silicon and Intel, and 27.0) measured the inputs to that rule. `/bin/ps` does not hold the entitlement. Apple's `/bin` and `/usr/bin` tools (`sleep`, `sh`, which is bash, `zsh`, `perl`) are `CS_RESTRICT`. The nodejs.org Node build (hardened runtime, six entitlements), Homebrew's Node and Python, Xcode's `python3`, and anything a developer builds are not. So on an ordinary Mac a tagged Node or Python process, and everything below it while it lives, is found by its tag, and an orphaned Apple tool is not: `nohup sleep 300 &`, or a `nohup sh -c 'while :; do ...; done' &` supervisor loop that would respawn a killed server. Every image runs with SIP off, so the redaction itself was never observed; it follows from the kernel source plus those measured flags. macOS 27.0 still returned every unrestricted process's environment with SIP off, so a report that it withholds everyone's is not true there.

`proc_pidinfo` gates a working directory on the uid alone, with no code-signing or SIP check in the same kernel source, and `lsof -d cwd` read every probed process's. So the macOS reader flags a same-user process whose record holds nothing after its arguments as withheld (and counts it as unreadable), reads the working directory of each withheld orphan, and the reap also kills a withheld orphan whose working directory is inside the task's worktree (the worktree, not the project: with no tag, the directory must be the task's alone), with its descendants there. The match needs all four: environment withheld, parent `launchd`, same user, directory inside the worktree. Apple's `/bin/sh` (bash 3.2) keeps the subshell of `cd <dir> && cmd &` alive as the command's parent, so the orphan `launchd` adopts is often that shell rather than the command, and the command goes with it as a descendant (measured on every image). A readable environment wins, so an untagged or cleared-tag Node process in the worktree survives, a descendant whose readable environment cleared the tag saves the orphan above it as it saves a tagged parent, and the user's own shell `cd`'d into the worktree survives because its parent is alive. What it costs: a cleared-tag Apple tool orphaned inside the worktree is killed, since its environment cannot be read to see the opt-out, and so is anything started there under `env -i`. What it still misses: a withheld orphan working outside the worktree, and every withheld orphan of a task without one. `env -i` is also how the tests reach this branch on SIP-off runners, because an empty environment reads exactly like a withheld one.

**The WSL reap.** A WSL agent is reaped inside its distro (`wsl-reap.ts`) while the distro is running. It runs in the configured shell's distro when that shell is WSL, and in each distro a task's CLI ran in: a CLI path into a distro gives its session a WSL shell whatever shell is configured, and the session record keeps that distro (`sessions.cli_target`), so the reap finds it after the session, and after a restart, from the records (`listCliTargetsOfTasks`). A Command Terminal names its distro from its own shell when its reap runs. Each distro runs once (`wslReapSpecs`). Measured in a preview before the change: a Claude installed in Ubuntu, under a PowerShell shell setting, left a tagged `nohup sleep` running in its worktree after Done. The tag crosses into the distro because a task spawn on a WSL shell lists `KANGENTIC_TASK_ID/u` in `WSLENV`, which is how Windows hands a variable to a WSL process. The distro's script cannot tell which processes run under a PTY Kangentic holds, which the pty host protects, so it leaves out any task that has a live or starting session, checked after the host reap and again just before the script runs (the `wsl.exe` listings before it can take seconds), and logs how many it left out. Every transition has already waited for its task's sessions to exit, so that only matters for the startup sweep, which takes no task lock: a To Do task dragged back into a running column while the sweep ran keeps its new agent, unless the agent starts during the script's own run, which is about a second. Locking every archived and To Do task for the sweep was rejected, since a slow host and a wedged `wsl.exe` would then hold every drag of them for up to 35 s, plus up to 3 s for a PTY still parked on its exit grace.

**Its bounds.** The two `wsl.exe` listings are bounded at 5 s each and the script runs share 10 s (measured: about 40 ms per listing, 1.06 s for a one-task script with its 1 s grace, and about 2 ms more per task when there is nothing to kill), so a wedged `wsl.exe` adds at most 20 s to a Done move, or to each task of a bulk delete, which has a 60 s per-task deadline. When the bound terminates `wsl.exe`, the script inside the distro ends with it (measured on WSL 2). The sweep passes every archived and To Do task, so the tasks reach the script in batches that fit one command line: CreateProcess caps it at 32,767 characters, and 210 tasks with a worktree each passed that.

**What it misses.** The shell setting is read at reap time, not recorded per session, so a task that ran under a WSL shell setting is not reaped in the distro once the user has switched the shell away from WSL; that only misses, it never kills the wrong process. A task whose CLI path pointed into a distro is not affected, since its records name the distro. Reaping every running distro regardless of the setting was weighed and rejected: it would spawn `wsl.exe` on every Windows user's Done move, and on a machine without WSL that `wsl.exe` is an installer stub whose output is not a distro list.

**The in-distro script.** The in-distro script applies the tag and the directory (each task directory translated with `wslpath -u`, passed as arguments so a path never enters the script text) but not the shared, connection, visible-app or tmux rules. It finds tagged processes with one `grep -z` per task, which took 8 ms over 140 processes in Ubuntu where the per-process loop it replaced took 280 ms, and it compares a drive-letter directory without case, as the Windows drive does: `/proc` reports a working directory as the agent typed it, so `cd /mnt/c/users/...` would otherwise hide a process from a `C:\Users\...` task. A distro whose `grep` has no `-z` (an old BusyBox) fails the reap, which reports `wsl_error`, rather than quietly finding nothing.

**Why more than the tag.** Jenkins' ProcessTreeKiller and the GitHub Actions runner (`RUNNER_TRACKING_ID`) use the tag alone and exempt no process by name; they run on machines a job owns. A desktop user's editor, browser and tmux sessions live beside the task, which is why this reap adds the directory, the shared-subtree test, the connection test and the protections, and exempts nothing by name either: tmux is protected for a measured mechanism (it copies its environment into later sessions), not for being on a list. And path matching in the removal backstop compares normalized strings, so a holder Windows reports under an 8.3 short name or a `\\?\` long-path prefix does not match the needle and is neither killed nor named.
