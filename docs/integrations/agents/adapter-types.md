# Adapter types and capability discovery

## `AgentCapabilities`

`src/shared/types.ts`

Adapter-discovered capabilities surfaced to the renderer (returned by `discoverCapabilities`). All fields are optional - adapters that cannot discover a capability leave it undefined and the corresponding UI control is not rendered. Nothing is hardcoded in Kangentic; values come from the live CLI.

| Field | Type | Purpose |
|-------|------|---------|
| `effortLevels?` | `string[]` | Effort/reasoning levels accepted by the CLI's `--effort` (or equivalent) flag. Claude parses these from the `--help` output. Drives the Effort dropdown on `EditColumnDialog`. |
| `effortLevelsByModel?` | `Record<string, string[]>` | Effort levels per model id, for a CLI whose levels depend on the model. A model listed here takes its own levels in place of `effortLevels`. Read only through `effortLevelsForModel` (`src/shared/effort-levels.ts`), which the Knowledge Graph and Automation agent rows (`answer-agent-rows.tsx`) and the runs that check a level before passing it (`answer-run.ts`, `automation-agent.ts`) share. Droid reports it from the "Model details:" block of `droid exec --help` and leaves `effortLevels` empty, so no column offers a level some model refuses. |
| `supportsModelOverride?` | `boolean` | True when the CLI accepts a model override flag (e.g. Claude `--model <alias>`). When true and `models` has entries, the renderer shows a dropdown; when true and `models` is empty/undefined, the renderer falls back to a free-form text input. |
| `models?` | `string[]` | Model identifiers the user can pick from. Discovered from agent-specific sources: Claude scans `~/.claude/projects/<slug>/<sessionId>.jsonl` for assistant `message.model` values, and merges the CLI's own list. That list comes first from the `initialize` control request of its stream-json mode (`model-list-handshake.ts`, what the Agent SDK's `supportedModels()` reads): `-p --input-format stream-json --output-format stream-json --verbose --no-session-persistence --safe-mode`, one line on stdin, no user message, so no turn runs. It answers in about a second, signed out included, and `--print` needs no trust entry. Every row is validated, because the wire format under the SDK's public type is undocumented. When the handshake fails, the list comes from the CLI's `/model` picker driven through a hidden short-lived PTY (`model-picker-probe.ts`). The result is cached for 12 hours, and a failure is retried after 10 minutes. A scan in hand is served at once. On a cold cache discovery waits for the first scan up to 8 s, because the inventory `agents.list` builds has no TTL and a list built without the scan would keep the pickers without their aliases. A wait that runs out leaves the read going. When that read lands, `onCapabilitiesChanged` drops the inventory, so main's readers rebuild on their next call and the renderer picks it up on the rescan a dropdown fires on open. That rescan also fires on focus with nothing to list, so a first read that failed gets retried for a user with no history. Any failure falls back silently to the transcript scan. The user sees nothing, but the log does. A failed handshake writes one `[model-picker-probe]` warning naming the failure, never the payload, which holds the account. Each failed or partial PTY run writes one `[model-picker-probe]` warning to the local log (`<project>/.kangentic/logs/<date>.log`, or `<configDir>/logs/` with no project open) naming the stage it stopped at (`scratch-setup`, `spawn`, `trust-dialog`, `select-dialog`, `no-prompt`, `input-not-echoed`, `picker-not-rendered`, `frame-not-settled`, `no-rows`, `error`, or `scroll-incomplete` for a partial scan) and, when the CLI got as far as drawing, the last six non-blank lines of its screen, with absolute paths, email addresses, a welcome greeting's name and API keys redacted (the "use this API key?" dialog prints the key's last 20 characters; the 2.1.290 header names no one, and a cwd it prints as a `~` path is left as drawn). The tag is not in Sentry's console allowlist, so that screen text never reaches Sentry. The PTY probe sets `TERM=xterm-256color` whatever the app's own environment says, because Claude Code draws its prompt as `❯` only when its Unicode check passes ([Environment Stripping and Defaults](../../platforms/shells-and-paths.md#environment-stripping-and-defaults) says why a packaged Windows launch fails that check). Before `/model` is submitted it types into no dialog. The input box is recognized by its shape (a full-width `─` rule, then `❯` in column 0, measured on 2.1.290), and a `❯` on screen with no input box is a select dialog: no key is sent while one shows. That covers the "use this API key?" dialog, whose options carry no number. Enter goes only to an input box whose own line shows the typed `/model`; the suggestion list under the box repeats `❯ /model` indented and does not count. Once the picker opens, only Arrow Down and Esc reach it. The picker shows ten rows at a time ("… +2 models"), so the probe walks the highlight down with Arrow Down (never Enter, which would change the user's default) until the last row is on screen, and parses every row it saw. A scroll that stops with rows still below is used only until the short failure backoff, and never replaces or overwrites a complete scan. The last good result is kept in `model-picker-last-scan.json` in the app's config directory (per user, never the shared temp directory), so the first discovery after a restart already has the aliases and ids instead of waiting for a read; a scan taken with a different CLI path, or an unreadable file, is ignored. Absent when no curated list is available - the renderer falls back to a free-form text input. |
| `modelDisplayNames?` | `Record<string, string>` | Friendly display name per entry in `models` and per `modelAliases` id (e.g. `claude-opus-4-8` -> "Opus 4.8", `opus` -> "Opus"), computed by the adapter (Claude via `buildModelCapabilityFields`, which humanizes with `humanizeClaudeModelId`) so no agent-naming knowledge lives in shared or renderer code. Claude labels a row from its id, not from the CLI's `displayName`: on Bedrock and Vertex the CLI calls `claude-opus-5-5` just "Opus", so a pinned id would read like the alias. `humanizeClaudeModelId` reads the `claude-...` core of a provider's id, without a `-v1:0` or `@20251001` tail. Only an id with no such core (a custom option, an ARN) takes the CLI's name. Drives the humanized rows in the Model dropdown (`ModelCombobox`), the ContextBar model popover, and the Model cell of the Column Manager's All columns table, which reads the map of the column's own agent so the row and the column's form print the same label; an id absent from the map falls back to showing its raw id. The `agent:list` handler also adds a label for each telemetry-learned id the adapter can name (`modelDisplayName?` in [Optional properties](optional-properties.md)), so a learned-only row such as an old dated pin does not render raw. |
| `modelAliases?` | `ModelAliasOption[]` | Floating selectors that follow the latest release of a model family, each `{ id, resolvesTo? }` (e.g. `{ id: 'opus', resolvesTo: 'claude-opus-5-5' }`), in the CLI's own order. The model pickers list them in a "Latest" group, with `resolvesTo` as a muted second column, above one collapsed "Specific versions" section that holds every entry in `models` (`planModelPickerRows`, `src/shared/model-id.ts`). A stored alias displays as its bare family name; the field's hover names the version it runs. Claude's handshake reports them as rows (`mapSupportedModels`): a row whose `value` is a bare lowercase word, with or without `[1m]`, whose `resolvedModel` contains `claude-<word>-`, which holds for every provider's shape and rejects `opusplan` and a gateway's model with no list of names. A bare word with no `resolvedModel` is an alias with no `resolvesTo`. On Bedrock, Vertex and Foundry most rows are full ids and only `haiku` is an alias, so those users see few Latest rows. The PTY fallback derives them in `parseModelPickerScreen`: one alias per model family whose own name labels a `/model` picker row, spelled as the lowercased family word (the CLI's documented "alias for the latest model"), resolving to that family's highest listed version. The picker never prints an alias spelling, so no list of family names exists anywhere. The same scan decides the spawn spelling: `toClaudeModelArgument` turns a stored single word (`"Opus"`) into `opus` only when it is one of these aliases (`peekModelPickerAliasIds`, which reads the cache and never starts a probe), and passes any other word through as written. An alias's other forms (`sonnet[1m]`) stay listed under "Specific versions"; only the exact alias id folds into its Latest row. Absent when neither source has answered or neither lists an alias; the pickers then show exactly the `models` list. |

`AgentDetectionInfo.capabilities?: AgentCapabilities` - populated at detection time; absent for adapters that do not implement `discoverCapabilities`.

## Per-Adapter Capability Discovery

Beyond Claude (detailed above), twelve adapters each ship their own `src/main/agent/adapters/<name>/capability-discovery.ts`. Most of those that probe the CLI share a common shape built on the bounded session-history scan helpers in `src/main/agent/shared/history-scan.ts` (`listMostRecentDirs` / `listMostRecentFiles` / `readHeadBytes` / `readTailBytes` / `parseJsonlRecords`, all capped so discovery stays fast on a heavily-used install):

1. **Model-override flag** - run `<cli> --help` and regex for a `--model` / `-m` flag to set `supportsModelOverride`.
2. **Model list** - when that flag is present, scan the agent's own on-disk session history for the distinct model ids the user has actually used, sorted ascending so families cluster. An empty result leaves `models` undefined and the renderer falls back to a free-form text input.
3. **Effort levels** - Copilot parses these from `--help`, Antigravity reads the levels its `--help` lists for `--effort` (`low|medium|high|xhigh|max` on 1.4.12, the documented `low`, `medium` and `high` when the line lists none), Grok reads a real ladder (`low`..`xhigh`) from its models cache, Codex reads each model's `supportedReasoningEfforts` from its app-server's `model/list`, Droid reads each model's own levels from `droid exec --help` into `effortLevelsByModel`, Ollama parses its `--think` levels from `ollama run --help`, and Kimi reads each model's `support_efforts` from `config.toml`; every other non-Claude adapter reports `effortLevels: []` (no CLI effort concept).

All implementations are best-effort and never throw: a help-read or history-scan failure yields conservative defaults so the rest of detection still succeeds. **No adapter keeps a list of model names or ids.** Per `.claude/rules/cli-features-over-custom-layers.md`, a model list is either discovered (from the CLI or from the CLI's own cache) or derived from the id, and a discovery failure reports no list rather than a guess - the renderer then shows a free-form model input. Five adapters deviate from the history-scan probe shape: Aider reads only `--help`, because its history files live in each project and name no model list; Droid reads its model list from `droid exec --help` and keeps `supportsModelOverride: false`, since only its headless run takes `--model`; Grok discovers everything (models, display names, effort ladders) from `~/.grok/models_cache.json`, the CLI's own maintained cache, with a `--help` parse as its fresh-install fallback; Antigravity reads `--help` for its flags and fetches its model list from the CLI's own `agy models` listing; and Cursor does the same through `cursor-agent --list-models`.

## Agent inventory cache

`agents.list()` builds one inventory per set of configured CLI paths (`src/main/agent/agent-list.ts`: detect, the auth probe and `discoverCapabilities` for every registered adapter) and keeps up to eight of them, the least recently used going first. The cache has no TTL. Three things clear it. A config write that changes agent settings does (`invalidateAgentListCache`, called from the `config:set` handler). So does a forced refresh, which is a model dropdown opening or the Re-detect button. The third is an adapter's `onCapabilitiesChanged` listener, which the build registers once per adapter: Claude fires it when a model list lands after its cold wait ran out, so main's own readers rebuild on their next call and the renderer picks the list up on the rescan a dropdown fires when it opens. `nameLearnedModels` labels the telemetry-learned ids on top of the cached inventory on each call and never writes into it.

## `CommandOptions` - new spawn knobs

`src/main/agent/agent-adapter.ts`

Twelve recently-added optional fields drive per-spawn overrides. Adapters consume them in `buildCommand` to emit the appropriate CLI flag (or branch) when the value is present:

| Field | Type | Purpose |
|-------|------|---------|
| `model?` | `string` | Adapter-specific model identifier (e.g. Claude `--model opus`). Empty/undefined leaves the agent default in place. Sourced from `swimlane.model_override` at spawn time by `prepare-spawn.ts`. |
| `effort?` | `string` | Adapter-specific effort/reasoning level (e.g. Claude `--effort xhigh`). Empty/undefined leaves the agent default in place. Sourced from `swimlane.effort_override` at spawn time by `prepare-spawn.ts`. |
| `executionTarget?` | `ResolvedExecutionTarget` | Present only when this project's execution mode for the agent is `remote` (see [Remote Execution](opencode.md#remote-execution) and [Remote Execution](../../settings/app-config.md#remote-execution)). Adapters that declare `remoteExecution` read this instead of spawning the CLI locally; `undefined` unambiguously means local. Resolved by `resolveExecutionTarget()` and populated at both spawn chokepoints (`transition-engine.ts`, `session-startup/prepare-spawn.ts`). |
| `cliTarget?` | `CliTarget \| null` | Present when the agent's CLI is installed in a WSL distro and configured by its `\\wsl.localhost\<distro>\...` path (see [WSL Support](../../platforms/shells-and-paths.md#wsl-support)). Resolved once per spawn by `resolveCliTarget()` at the spawn chokepoints; the builder starts the CLI by `linuxCliPath`, converts every path argument with `cliPathForTarget`, and writes hooks and MCP config in the distro's form. `null` or absent means this machine. |
| `launchOptions?` | `Record<string, boolean>` | Fully-defaulted boolean launch-option values for this agent, keyed by `AgentLaunchOptionInfo.id` (e.g. Codex's `disableApps` -> `--disable apps`). `undefined` for adapters that declare no launch options. Resolved by `resolveLaunchOptions()` and populated at both spawn chokepoints (`transition-engine.ts`, `session-startup/prepare-spawn.ts`). |
| `taskProcessTag?` | `string` | The task's `KANGENTIC_TASK_ID` value, the tag a terminal transition reaps by (see [Process reaping](../../architecture/worktrees/process-reaping.md)). The PTY env already carries it; an adapter whose CLI can strip inherited variables from its tool shells re-injects it (Codex: `-c shell_environment_policy.set.KANGENTIC_TASK_ID=<id>`). Populated at both task spawn chokepoints, and by a Command Terminal's start with the terminal's own made-up task id. |
| `ptySessionId?` | `string` | Kangentic's id for the session this command is built for: the `id` the build site then hands `sessionManager.spawn` (not the agent's own `sessionId`). An adapter that writes a file every session in a folder shares holds it under this id, and the session layer releases it with `removeHooks(directory, ptySessionId)`. Set by all four build sites (`transition-engine.ts`, `session-startup/prepare-spawn.ts`, a Command Terminal's start, a workflow's agent); `spawn-entry-point-parity.test.ts` fails a build site without it. A built command that never becomes a session releases its hold through `releaseCommandHold`. |
| `bypassAvailable?` | `boolean` | Launch with the bypass permission mode available but not on, so a plan Kangentic approves can continue in it. Set only for a plan-mode spawn whose approved plan would continue in `bypassPermissions` (`planApprovalModeForSpawn`), at both task spawn chokepoints, and only for an adapter that declares `supportsPlanAutoApproval`. Claude maps it to `--allow-dangerously-skip-permissions`: measured on 2.1.302, the approval's mode switch reaches bypass only in a session launched with it. Adapters without such a launch option ignore it. |
| `capturePromptText?` | `boolean` | Carry the submitted prompt's text in the Prompt event's `detail`. Set only by a Command Terminal's start, whose namer (`command-terminal-namer.ts`) names the terminal from its first prompt; a task spawn never sets it, so task sessions' events keep no prompt text. An adapter whose prompt hook carries no text ignores it. |
| `readOnly?` | `boolean` | Launch with no tool that edits a file or runs a shell command, and with Kangentic's MCP server as the only one. Set only for a workflow's own agent, and only on an adapter that declares `supportsReadOnlyLaunch`. Claude maps it to `--tools Read,Grep,Glob,ToolSearch`, `--strict-mcp-config` and `--no-chrome` (`READ_ONLY_TOOLS` in `adapters/claude/command-builder.ts`). |
| `readableDirectories?` | `readonly string[]` | More directories the agent may read beyond its `cwd`: other projects' checkouts, for a workflow agent planning tasks on their boards. Set only on an adapter that declares `supportsReadableDirectories`. Claude emits one `--add-dir` per directory, Gemini one `--include-directories`. |
| `browserAutomationEnabled?` | `boolean` | The Agent Browser switch (`AppConfig.browserAutomation.enabled`, resolved) when the command is built. While on, an adapter that takes system prompt text gets the browser policy: Claude gets `--append-system-prompt` with `BROWSER_POLICY_PROMPT`, and `--no-chrome` unless `readOnly` already added it. Droid gets the same `--append-system-prompt`. Every `buildCommand` site sets it (`transition-engine.ts`, `session-startup/prepare-spawn.ts`, `ipc/helpers/agent-spawn.ts`, `ipc/handlers/transient-sessions.ts`, `workflows/workflow-agent.ts`); `spawn-entry-point-parity.test.ts` fails a site without it. See [Browser panes](../mcp-server/browser-panes.md#the-only-browser-an-agent-drives). |

A task session never switches model or effort live: any change to a concrete value restarts it with the new launch flags (see [Command Injection](../../architecture/automations/command-injection.md)). Only the Command Terminal, which has no session to `--resume`, switches live, through `getInjectionSequence` in the [Optional properties](optional-properties.md) table. The adapter declares the slash-command writes and `TerminalSubmitScheduler.scheduleKeystrokes` delivers them via `TerminalSubmit.submitKeystrokes`, unverified (a transient session has no task row for the verifier to resolve). `getSubmissionVerifier('command-injection')` confirms a task's column message instead.

## `AdapterRuntimeStrategy`

`src/shared/types.ts`

One scannable block per adapter for activity-state derivation and session ID capture:

| Field | Type | Purpose |
|-------|------|---------|
| `activity` | `ActivityDetectionStrategy` | How thinking-vs-idle is detected. See [Activity engine](../../architecture/activity/activity-engine.md#activitydetectionstrategy-variants) for the discriminated union variants and the `ActivityDetection.hooks() / pty() / hooksAndPty()` factories. |
| `reportsTurnEnd` | `boolean` | Required. Whether the agent says when its turn ended, through a hook or its wire protocol, so the activity engine gets a real `Idle` event and the session manager emits `'turn-ended'`. That event is what runs a column's On agent turn end automations. Omit `sessionId` entirely for agents that use caller-owned IDs (Claude and Grok via `--session-id`, Aider via the `--chat-history-file` the id names) or that have no resume mechanism (Ollama, Warp). Omit `sessionHistory` for agents without a native session log file. Omit `statusFile` for agents that don't emit hook-driven `status.json` / `events.jsonl` (Claude, Codex, Gemini, Qwen, Copilot, Grok, Antigravity, Droid, OpenCode and Cursor declare it today; all but Claude, Antigravity and OpenCode have a `parseStatus` that returns null because the CLI has no usable statusline, and ride on their hook-driven `parseEvent`; OpenCode's `status.json` is written by its own plugin; Antigravity's status line, passed per session through `--settings`, feeds both `parseStatus` and `parseStatusEvents`). Omit `streamOutput` for agents that don't emit machine-readable NDJSON to PTY stdout (everyone except Cursor today). Omit `backgroundShells` for agents that don't write a per-shell output file or expose a transcript-based termination signal (everyone except Claude today). Omit `permissionPrompts` for agents whose hook protocol already reports a denial directly, or whose transcript carries no such signal (everyone except Claude today).
