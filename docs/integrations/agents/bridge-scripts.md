# Bridge scripts

Four standalone Node.js scripts in `src/main/agent/`:

## `status-bridge.js`

- **Hook point:** `statusLine` (not a hook - uses Claude Code's status line feature)
- **Output:** `status.json` (overwritten on each invocation)
- **Data:** Token usage, cost, model, context window percentage
- **Watched by:** SessionManager with 100ms debounce
- **Supported by:** Claude Code, Gemini CLI (via status parser)

## `event-bridge.js`

- **Hook point:** All registered hooks
- **Output:** `events.jsonl` (append-only, one JSON line per event)
- **Data:** Timestamps, event types, tool names, file paths
- **Appended events:** `appendBackgroundLaunch` and `appendBackgroundStop` write a `background_shell_start` or `background_shell_end` line beside the hook's own event, from the adapter's `BackgroundCommandSpec` (see [Background commands](background-commands.md#background-commands)). They are new kinds rather than flags on an old one, so a stale bridge copy rejects them through its unknown-directive branch instead of misreading them. A suppressed main event still lets an appended line land.
- **The kind of a wait:** `setWaitKind` tags the event `waitKind: 'question' | 'approval'`, and `setWaitKindWhen({ path, equals, to })` overrides that default when the stdin value at `path` matches (Claude's `tool_name` is `AskUserQuestion`; Gemini's `details.type` is `ask_user`). `appendPermissionWaitForTool({ toolPath, tool, waitKind })` writes an `idle:permission` line AFTER the hook's own event when the tool at `toolPath` is `tool`: a CLI whose question tool raises no permission hook (Codex's `request_user_input`) reports the wait from the tool's own pre-tool hook, and one process writing both lines in order is what keeps the tool start, which clears any wait, from landing after it on a CLI that runs one event's hooks concurrently. The bridge accepts only those two kinds and logs anything else. Each is its own kind, so a stale copy leaves the wait untagged (drawn as unknown) rather than mis-tagged. See [The kind of a wait](../../architecture/activity/activity-engine.md#the-kind-of-a-wait).
- **A call that starts a subagent:** `markSubagentLaunch({ tools })` sets `launchesSubagent: true` on the event when `tool_name` is one of `tools`, the agent's own subagent tools. Claude's `PreToolUse` entry names `Agent` and the older `Task`. The engine closes a permission prompt on a `subagent_start` only when the call the prompt awaited carries the flag, so a parallel subagent's start leaves the prompt open (see [Permission flag](../../architecture/activity/predicate.md#permission-flag)). Built by `markSubagentLaunch` in `src/main/agent/shared/directive-builders.ts`. It is its own kind, so a stale copy logs it and never sets the flag, and an approved subagent call then reads as a permission prompt until its own end.
- **A reply on stdout:** the bridge mutes its stdout, because Gemini rejects any hook output that is not its strict JSON. `replyJson({ ... })` is the one exception: the process writes that JSON to stdout, through the writer it saved before muting, before it touches the events file and whatever the events path, so a CLI waiting on the answer gets it even when the append fails. Antigravity's `ask_question` PreToolUse is the one user: agy denies a tool whose PreToolUse answers without a `decision`, and `{ "decision": "allow" }` defers to its own dialog. Never put it on a Gemini entry. A stale copy writes no reply and logs the directive.
- **Watched by:** SessionManager with 50ms debounce, incremental byte-offset reads
- **Supported by:** Claude Code (18 hook points), Codex CLI (via `-c hooks.*` overrides and a per-spawn workspace copy, `<cwd>/.kangentic/codex-event-bridge.cjs`, with the `env:KANGENTIC_EVENTS_PATH` sentinel - see [Codex Hook Integration](codex-cli.md#hook-integration)), Gemini CLI (via .gemini/settings.json hooks), Qwen Code (on Windows via a per-spawn workspace copy, `<cwd>/.kangentic/qwen-event-bridge.cjs`, and the `env:KANGENTIC_EVENTS_PATH` sentinel - see [Paths in hook commands](claude-code.md#paths-in-hook-commands)), Aider, GitHub Copilot CLI, Grok Build (via `.grok/hooks/kangentic.json`, with the events path resolved through the `env:KANGENTIC_EVENTS_PATH` sentinel - see [Grok Build](grok-build.md#grok-build)), Antigravity CLI (via a per-spawn workspace copy, `<cwd>/.kangentic/agy-event-bridge.cjs` - see [Antigravity](antigravity.md#antigravity)), and Factory Droid (via a per-session `--settings` file - see [Droid](droid.md#droid))

## `plan-approval-bridge.js`

- **Hook point:** a second `PermissionRequest` entry, matcher exactly `ExitPlanMode`, beside the event bridge's catch-all one. Registered on every spawn of an adapter that declares `supportsPlanAutoApproval`, whatever the column says, so a column or workflow task switched to Automatic while the agent plans needs no hook reload. A question the agent asks (`AskUserQuestion`) never reaches it.
- **Input:** the session's decision file, `.kangentic/sessions/<ptySessionId>/plan-approval.json` (`{ approve, mode, detail }`), and a base64 spec (`PlanApprovalHookSpec` in `src/main/agent/shared/plan-approval-hook.ts`) naming the tool, where its input sits, and the reply the CLI expects. The tool approval entry carries a `PlanToolApprovalHookSpec` instead (the allowed tools, the excluded ones, the input-judged tools, the modes it answers in, a bare reply). All agent knowledge is in the spec, never in the script.
- **Output:** to approve, the reply on stdout, after one `plan_approval_sent` line appended to `events.jsonl` (`tool_approval_sent` for the tool entry). Claude's reply (`CLAUDE_PLAN_APPROVAL_SPEC` in `adapters/claude/hook-manager.ts`) is `{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow","updatedInput":<tool_input>,"updatedPermissions":[{"type":"setMode","mode":<mode>,"destination":"session"}]}}}`. The input is echoed exactly, since Claude 2.1.300 and later deny a call whose input changed. `setMode` is needed because a hook approval otherwise restores the mode the session had before plan mode, and a session launched in plan mode has none.
- **Allowed tools while planning (task #870):** Claude's plan mode prompts for every tool that is not read-only. An MCP tool whose server does not annotate it `readOnlyHint` is not read-only, and an allow rule does not reach it there, so an unattended Planning session stopped at that prompt. When the session's allow rules name such a tool, or a built-in it judges by input (next item) is not excluded, the builder registers the same bridge a second time (a third `PermissionRequest` entry), matcher `mcp__.*|Artifact`, with a `PlanToolApprovalHookSpec`: the tools and server prefixes the rules allow, the ones a deny or ask rule names, and Kangentic's own server, always excluded so its mutating tools keep prompting ([How the MCP server works](../mcp-server/how-it-works.md#permissions)). It answers a bare allow, after one `tool_approval_sent` line naming the tool, only in plan mode (`permission_mode`) and only while the decision file says `approve: true`. The rules are read from the session's merged settings (project, project local, worktree local) and the user's `~/.claude/settings.json`, in `adapters/claude/plan-tool-approval.ts`. Measured on Claude 2.1.306 by `scripts/probe-claude-plan-tool-approval.js`, in `-p` and the interactive TUI: the hook's allow ran the call, a subagent's included, and outranked an ask rule, which is why the builder leaves an asked tool out. An ask or deny rule it cannot read as one of the MCP forms (a partial wildcard such as `mcp__docs__get_*`, or a specifier) excludes every tool its text before the `*` or `(` begins. Managed settings are not read, so a managed ask rule for a tool a project or user rule allows is answered anyway. The captured requests are in `tests/fixtures/plan-exit/claude-2.1.306-permission-request-mcp-tool*.json`.
- **Built-in calls judged by input (task #952):** Claude's own `Artifact` tool also prompts in plan mode, and an overnight workflow's Planning agents waited 2 to 9 minutes each on an `Artifact` read. The spec's `inputJudgedTools` (`CLAUDE_PLAN_INPUT_JUDGED_TOOLS` in `adapters/claude/plan-tool-approval.ts`) names a tool, the stdin field holding its input, the input field that says what the call does, the values the bridge answers, and what a call with the field absent does. `Artifact` is answered when `tool_input.action` is `read`, `list` or `publish`, and when it is absent, since the tool publishes by default. A `delete`, any other value, or an input that is not an object prints nothing, so it keeps its prompt. No allow rule is needed, because the hook's answer is the consent. A deny or ask rule naming `Artifact`, bare or with a specifier, takes the tool out of the spec, since the hook's allow would outrank it. No tool that edits files or runs commands is in the table. Measured on Claude 2.1.316 on Windows with the probe's built-in mode (`--tool Write --matcher "mcp__.*|Write"`, no allow rule): plan mode refused the call with no hook ("Cannot write ... while in plan mode.") and ran it when the hook answered allow, 29 ms after the catch-all `PermissionRequest`. `Artifact` itself needs a claude.ai account, which the probe's local API stand-in cannot provide, so it is unmeasured.
- **Fails closed:** another tool, no decision file, `approve: false`, or any error prints nothing and exits 0, so the CLI shows its own dialog and the user decides. Diagnostics go to `plan-approval-bridge.error.log` beside the decision file, never to stdout.
- **Decision writer:** `PlanApprovalWriter` (`src/main/plan-approval/plan-approval-writer.ts`) writes the file through `safeWriteJson` (source `plan_approval`) when a task session first appears, and rewrites every live session's file, coalesced at 100 ms, on any board change and on a Board Profile edit, a settings change or a `kangentic.json` apply (`refreshPlanApprovals`). The decision comes from `resolvePlanApprovalDecision` (`src/main/plan-approval/resolve-decision.ts`): a workflow task's plan approval (its own, else what the plan columns on its route give, whatever state its workflow is in), else the column's own while it runs in plan mode, and never an approval where the session's agent cannot approve plans or the task's automations are disabled (`canTaskRunAutomations`). `mode` is the destination's effective permission mode (the After Plan Mode target, or the next column on a workflow task's route); where that is `plan`, or `bypassPermissions` in a session launched without bypass available, it falls back to the task's own mode, then the global mode, then `default`. A plan-mode spawn whose approval would continue in `bypassPermissions` launches with `CommandOptions.bypassAvailable`. Transient sessions (a Command Terminal, a workflow's own agent) get no decision file, so their plans always wait.
- **Supported by:** Claude Code (measured on 2.1.302: `acceptEdits` and `auto` apply through `setMode`; `bypassPermissions` applies only to a session launched with bypass available)

## `background-shell-hint-bridge.js`

- **Hook point:** a second post-tool entry beside the event bridge's catch-all one, matcher-scoped to the launch tools where the CLI has matchers (Claude's `Bash|PowerShell`). Registered only for a session whose MCP URL names it as the caller (`urlNamesTaskSessionCaller`), because the hint points at `kangentic_mark_background_service`, which the server offers only to such a session. A Command Terminal, or a session with the MCP server off, gets none.
- **Input:** the hook payload on stdin, and a base64 spec (`src/main/agent/shared/background-shell-hint-hook.ts`) naming the tools, where the command and the shell id sit, the opt-out flag, and the reply. All agent knowledge is in the spec, never in the script. Claude sends the v1 shape (`BackgroundShellHintSpec`), which its replay fixtures pin. Every other agent sends v2 (`BackgroundShellHintSpecV2`, `{ launch, reply }`), whose `launch` is the same match its `appendBackgroundLaunch` directive carries. A stale bridge prints nothing for v2, since it requires the v1 fields.
- **Output:** for a result carrying an id-shaped background shell id, from a command without `--kangentic-no-activity-hold`, the reply on stdout, with the one hint text `BACKGROUND_SHELL_HINT_TEXT` in the CLI's own envelope. Claude's (`CLAUDE_BACKGROUND_SHELL_HINT_SPEC` in `adapters/claude/hook-manager.ts`) is `{"hookSpecificOutput":{"hookEventName":"PostToolUse","additionalContext":<hint>}}`: the shell keeps the task working and holds the column's turn-end automations until it exits, and a server or watcher can be marked with the tool. See "Opting a background shell out of the hold" in [Background shells](../../architecture/activity/background-shells.md#opting-a-background-shell-out-of-the-hold).
- **Prints nothing** for a foreground call, another tool, a flagged command, stdin over 1 MiB, or any error, and exits 0, so it never fails or blocks a tool.
- **Supported by:** Claude Code (probed headless on 2026-10-20: the context reached the model for a Bash and a PowerShell `run_in_background` launch, both results carried `tool_response.backgroundTaskId`, and Claude runs one event's hooks in parallel, so the hint adds no wall time to a tool call), Qwen Code 0.25.3, Gemini CLI 0.64.0 and GitHub Copilot CLI 1.0.100 (each probed headless against a local stand-in for its model API, with a nonce in the reply found in the next model request)

All four scripts are stateless (no persistent process), read JSON from stdin, and exit. All writes are try/catch wrapped for non-fatal failures.
