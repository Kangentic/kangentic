# Capability verbs

## Capability Verbs

`packages/protocol/src/capabilities/verbs.ts` defines the complete allowlist a paired device can be granted:

- `read-stream` - live scrollback, terminal output, activity/usage telemetry, and transcript deltas for one session.
- `read-board` - a project's columns and tasks, or (with no `projectId`) the machine's project list; live updates via the board-changed bus. The `view` field picks the projection: `'sessions'` (what an agent feed draws across every project: session-bearing tasks, any task with a spawn-progress label in flight or a `resumable` pause, and whole-column counts) or `'full'` (every task, for the one board the user has open). Either way the backlog stays home; only a pre-0.9.0 request that names no `view` still gets it.
- `read-diff` - a task's diff file list or a single file's content, via `DiffService` (a binary file answers with empty content, since its list entry already says it is binary and a UTF-8 read would only garble its bytes; that includes an SVG `.gitattributes` marks binary, which the desktop still previews as an image); live "something changed, re-fetch" pushes via a bridge-owned `DiffWatcher`. From 0.20.0 a request with no `taskId` diffs the PROJECT FOLDER against the project's effective default base, exactly as a Command Terminal window's Changes panel does; its pings carry `projectId` instead of `taskId`. A file's content is served only for a path in that diff's own file list, so a gitignored or out-of-repo path is never readable.
- `send-user-message` - deliver text to a running session via the same bracketed-paste path (`TerminalSubmit.submitContent`) the renderer's Browser-pane Send affordance uses. From 0.26.0 a task's session that is not writable (paused, queued or exited) holds the text for the task's next agent instead ([Held messages](../../architecture/sessions/held-messages.md)) and answers `delivered: true`, which is how the phone's chat to a paused task reaches the agent that resumes it. A hold the desktop refuses (a task in Done, a message too long to hold) answers with the refusal and code it sent before, its text the reason. A Command Terminal, which has no task, is refused as before.
- `move-task` - move a task between columns, optionally placing it at a `targetPosition` within the destination column, via `handleTaskMove` (respects `withTaskLock` and the transition engine). It passes the `'mobile'` origin, which selects the renderer push `handleTaskMove` sends for the move: a quiet `task:movedByMobile` push reloads the desktop board, at the move's commit point and again when it settles. The `board-changed` bus emit is unconditional for every origin and reaches every paired phone subscribed to that project's board, the originating one included (`read-board`'s listener filters on `projectId` alone, and phones already tolerate duplicate board events), plus the Agent Monitor. The verb itself fans out nothing - keeping the notifications inside `handleTaskMove` is why a phone move can no longer land in the DB and tell nobody. The verb answers when the move COMMITS, not when it settles: `handleTaskMove` fires its `onCommitted` option the moment the board row is on disk (early in its locked Phase 1), and the handler resolves `{ ok: true }` on that signal while the tail of the move (the PTY suspend, leftover reap and worktree removal of a Done move, or the worktree creation and spawn of an auto-spawn column) finishes behind the response. The phone gives every verb 10s and 9% of measured desktop moves ran past that, so awaiting the whole move reported an already-landed move as "Move failed". A failure BEFORE the commit (task not found, a throw before `tasks.move`) still rejects the verb and reaches the phone as `ok: false`. That includes the workflow lock: a task in a running workflow moves only by its workflow, its column automations and its own agent, unless its own automations are paused (a held task moves by hand to any column but To Do, and its `lock_reason` reads null), so the verb answers `ok: false` with the desktop's own sentence ("#414 is locked while Usage budgets runs."). The phone counts as a hand: it may move a card out of a column no agent can judge into the next column on its route (`workflow.gate_target_id` on the board task), and may move a paused workflow's cards, never into To Do. A failure AFTER it is logged desktop-side (`failed after commit`), never escapes the bridge's request loop, and is corrected on the phone by the settle-time board event that follows `handleTaskMove`'s own rollback, which is the same contract the desktop's own drag has.
- `start-session` - spawn or resume a task's session in the column the task is already in, keyed by `taskId` + `projectId` (an ended task has no live session id to name). This is the phone's way back from its "Session ended" state without a `move-task`, and it is the bridge twin of the desktop's Resume button. The handler calls `startTaskSession` (`src/main/ipc/handlers/session-start.ts`). It first refuses a task whose row already shows it in To Do or Done, or archived, before it takes the task lock (`resumeRefusalBeforeLock`, which lets a task with a live session through to the idempotent answer below): a move to Done holds that lock through its worktree removal, which can outlast the phone's 10s budget. Under the task lock it then runs `reconcileTaskSessionRef` (a natural agent exit leaves `task.session_id` pointing at an exited registry row, and the spawn chokepoint bails on any `session_id`), returns without spawning when a live session already exists (the phone's view can be stale; idempotent), refuses a To Do or Done column and an archived task with the same copy the desktop's Resume shows (`resumeBlockMessage`), and then, with the lock released, takes one of two paths. A task in a paused workflow is not refused: a person may bring one task back to work it, as the desktop's Resume and a hand move do, and the workflow itself stays paused and starts nothing else. From 0.16.0 a PAUSED task (a `suspended` registry row) gets `resumeTaskSession` (`handlers/session-resume.ts`), the very body of the desktop's `SESSION_RESUME`: the same lock, reconcile, gate, worktree ensure, "Resuming session..." label and engine resume, with no enter automations and no column message, so a phone Resume on a paused task in Code Review does not resend `/code-review`. A task moved into its column while paused is the exception, on the phone as on the desktop: the Resume starts the column as that move would have (a fresh Code Review conversation, then `/code-review`), see [Resume](../../architecture/sessions/resume.md#where-resume-is-refused). It answers on that body's `onAccepted` (its own Phase 1 decides `live` or `starting`), and it cancels a resume already in flight for the task as a second desktop Resume click does, by decision: the phone mirrors the desktop. A refused one cancels nothing, since the refusal comes before the abort. The read-stream feed's `resumable` is what promises the phone this path. Every other task (no session, or an exited one: the "Session ended" state) routes through `autoSpawnForTask` -> `spawnAgent` with `explicitStart: true`. That is the chokepoint a move INTO the column uses, so the column's whole enter list runs (scripts, webhooks, notifications, the column message) with the column's model / effort / permission, and the flag lifts exactly the two guards the desktop's Resume also ignores: the column's `auto_spawn` default and a pause the user set on the desktop. Nothing is ever stopped. The verb answers when the start is ACCEPTED, not when the agent is up: the worktree ensure (a git fetch), branch checkout, PTY spawn and automations run behind the response, for the same 10s-budget reason `move-task` answers on its commit signal. The response carries the outcome (`{ ok, outcome: 'starting' | 'live' }`, narrowed phone-side by `parseStartSessionResponsePayload`) because the two accepted shapes ask different things of the phone: on `starting` the successor's arrival reaches it as the board / stream event `SessionLifecycleBoardFeed` emits on every `session-changed` (the registry edge `SessionManager.spawn` fires at PTY creation, the same one a desktop Resume rides, so this fan-out has no origin to be keyed on and cannot go silent per caller the way a move's once did); on `live` nothing was spawned and no event is coming, so a phone that tapped Start from a stale screen refreshes its board and stream itself. Three contract notes for the phone: `live` also covers a session that is `queued` at the desktop's concurrency limit (`isLiveSession` includes it), so it means "coming", not "running"; a post-accept failure is reported desktop-side only, by `autoSpawnForTask` (log, Sentry counter, spawn-blocked notice) or, for a resume, by the same spawn-blocked notice through `resumeTaskSession`'s `onFailed` hook (a worktree or engine failure; a refusal after the git phase stays silent, as `autoSpawnForTask`'s does), and the handler's `failed after accept` log, never as a phone event, and `SpawnStallWatcher`'s push fires only while the worktree phase is in flight, so the waiting screen needs its own timeout and a retry; and a Start in a column whose "Start an agent here" is off DOES start one, by the Resume-parity decision. A second Start that lands while the first is still spawning is a no-op: `autoSpawnForTask` re-checks the registry under the task lock, both before its git phase and again as the compare-and-swap before its spawn, and returns when a live session already exists, so the column message is never typed twice. That lock is split, not held across the fetch: a Start cannot make a desktop Pause or move on the same task wait behind a slow worktree ensure, and a desktop Pause, Reset, or Resume on the task cancels an in-flight Start's git phase through the same per-task abort registry a desktop resume uses (a cancelled Start is logged, not reported as a failed one). The reverse never holds for a Start: it registers its controller without aborting one already in flight, so it never cancels desktop work. (A Resume of a paused task is the deliberate exception above.) Nothing on this path escapes the bridge's request loop. Cross-version notes: an OLDER desktop that predates the verb rejects it at decode (`framing.ts`'s `isCapabilityVerb` check). A desktop from the build that carries the unsupported-verb refusal (see [Capability Verbs](#capability-verbs-1)) answers `{ ok: false, error: 'Unsupported verb: start-session', code: 'unsupported-verb' }` without running any handler, so the phone can show "update your desktop" instead of a timeout; a desktop older than that surfaces the frame only as `frameRejected` and sends nothing, so the phone times out, and never sees the router's "No handler registered" error either way; and because the package is still 0.x, a consumer pinned to `^0.14.0` does not resolve 0.15.0, so the phone's client method and its "Start again" action land as a coordinated bump on the mobile board once `/release-protocol` publishes this version.
- `pause-session` - pause a task's live session in place, keyed by `taskId` + `projectId` (a pause clears the task's `session_id`, and a stale phone view could name a session that already ended). From 0.18.0. It is the bridge twin of the desktop's Pause button: the handler calls `pauseTaskSession` (`src/main/ipc/handlers/session-pause.ts`), the very body of the desktop's `SESSION_SUSPEND`, so the two cannot drift. That body cancels a resume in flight for the task before queueing on the task lock, then under the lock runs `reconcileTaskSessionRef`, records the suspend as the user's (`applySuspendDbWrites(..., 'user')`, which keeps an auto-spawn column from starting the task again by itself), and suspends the PTY. A pause never reaps the task's leftover processes: the task is parked, not finished. A task with no live session is refused with `ok: false` ("This task has no running session to pause."), where the desktop's own Pause is a silent no-op; the shared body reports which happened and each caller decides. There is no column or archive gate, matching the task view, whose Pause stays available in Done and on an archived task because it is the only stop for an agent a failed Done-move suspend left running. The verb answers when the pause is ACCEPTED, once the DB records it and before the PTY shutdown, which takes about 3 s (a 1.5 s grace and 1.5 s of kill propagation) and can pass the phone's 10 s budget (a 2 s scrollback scan, a 10 s spawn settle). The response is `{ ok: true }` (`parsePauseSessionResponsePayload` narrows it phone-side), and the suspend's own `session-changed` reaches the phone as a `task-updated` board event, the same one a desktop Pause sends; the snapshot the phone re-reads on it carries `paused: true`. A post-accept failure is logged desktop-side (`failed after accept`) and never escapes the bridge's request loop. Gate a phone's Pause control on `BoardTaskWire.pausable` (see `read-board` in [Data feeds](data-feeds.md)). A 0.15.0 to 0.17.0 desktop refuses the verb with the `unsupported-verb` code.
- `command-terminal` - start or stop a Command Terminal, the agent the desktop's Ctrl+Shift+P layer runs at a project's root with no task. From 0.20.0. The name is deliberate: logs, refusals and a future devices panel say "Command Terminal", never a generic session start. A `start` names only the `projectId`; there is no branch, model or effort parameter, and the parser drops any such key. The handler runs `startCommandTerminal` (`src/main/ipc/handlers/transient-sessions.ts`), the very function the desktop's New terminal runs, so the cap (four per project), the slot, the agent, its model and effort and the default-branch checkout are the desktop's. Main owns the cap and the slot allocation, with a synchronous reservation so a phone start and a desktop New in flight together cannot share a slot. A phone start is UNATTENDED, which makes the desktop's steps unable to block a user who is away from the desk: the fetch runs non-interactively (`nonInteractiveGitEnv()`, so no credential dialog waits on an empty desk) with a 5 s abort, the whole git phase has one 6 s budget after which the remaining steps are skipped, and the start never moves HEAD under another live session in the project folder (a sibling terminal or a task with no worktree; paths compared after `resolveProjectRoot` and case-folded on Windows). Every one of those fallbacks still launches, on the branch already checked out. It works for any known project, open on the desktop or not. The verb answers once the session exists, before the agent draws anything, with `{ ok: true, sessionId, slot, name }` (`slot` 1 to 4, `name` the terminal's own name or "Command Terminal N"). A `stop` names the session and ends it through `SessionManager.endCommandTerminal`, the desktop Stop's own call, answering `{ ok: true }`. Refusals carry a typed `code` and the phone shows one plain line per code: `command-terminal-limit`, `unknown-project`, `agent-unavailable`, `command-terminal-start-failed` (anything else; `error` keeps the text), `not-command-terminal` (stop named a task's session; nothing stopped) and `unknown-session` (the terminal already ended; the phone treats it as stopped). The handler returns each refusal itself, because the router keeps only `error.message` from a throw. A phone gates its Terminals button on the snapshot's `commandTerminalsOffered` (see `read-board` in [Data feeds](data-feeds.md)).

  From 0.24.0 the verb also reads and resumes the conversations of terminals that ended, the desktop panel's Earlier list. `list-earlier` names the `projectId` and answers `{ ok: true, projectId, conversations }`, each `{ agentSessionId, name, endedAt }` (`name` is the terminal's name, else the conversation's first prompt on one line, and null when it has neither), newest first, from the same `CommandTerminalHistory.list` the rail reads: only conversations that can still be resumed, and none a live terminal holds. `resume` names the `projectId` and one `agentSessionId`, runs the same unattended `startCommandTerminal` with `resumeAgentSessionId`, and answers like a `start`. Two refusals are its own: `conversation-gone` (the record is gone or its agent cannot resume by id; the phone drops the row) and `conversation-open` (a live terminal holds it, or another resume is starting it). A phone sends either action only when the snapshot carries `earlierConversationsOffered: true`, because an older desktop's parser refuses an action it does not know as a malformed request.
- `answer-permission-prompt` - the most sensitive verb; binds a phone's raw keystrokes to a specific outstanding permission-prompt id before writing them to the PTY.
- `interactive-terminal` - raw PTY write-path parity (full desktop-terminal keystroke control). Three actions ride the one grant: `write` (the default; an action-less payload from a pre-0.4.0 phone parses as a write), `resize` (fit-to-phone: sets the PTY grid so the TUI redraws phone-shaped), and `release-size` (give the grid back). Resize deliberately shares the write grant - a device trusted to type raw bytes into the PTY gains nothing new from resizing it. While a phone holds a session's grid, a per-device guard (`handlers/terminal-size-guard.ts`) registered in the same `SubscriptionRegistry` restores the desktop's last dimensions on EVERY release path: explicit `release-size`, device disconnect, roster revoke, or bridge shutdown; it disarms without restoring when the session exits. Contention is latest-writer-wins - a desktop resize while a phone holds simply wins and becomes the new restore target; with two phones, either one's release restores desktop dims (documented limitation).
- `board-tool-read` / `board-tool-write` - the long-tail task/backlog CRUD surface (create, edit, delete, link PR, ...) that has no dedicated verb, split by read vs mutate access so the grant granularity matches the rest of the model. **Not MCP** - no agent, LLM, or JSON-RPC round-trip is involved; see [Board Tool Surface](#board-tool-surface) below.
- `register-push` - register (or unregister) the device for E2E-encrypted push notifications: the phone hands over its Expo push token plus a device-generated 32-byte push-envelope key, keyed by the requesting session's authenticated roster identity, never by payload content. See [Push Notifications](push-notifications.md).

A refusal for a session that is gone carries `code: 'unknown-session'` beside the `error` text older phones show (`handlers/session-refusals.ts`). `read-stream` answers it when no registry row has the id (including a row that vanishes while a terminal seed is being re-taken), or, for a `transcript-window` read, when no project has the id on record; a subscribe to a suspended row still succeeds, so the session screen can offer Resume. The two input verbs `answer-permission-prompt` and `interactive-terminal` answer it for a missing row and also for a `suspended` or `exited` row, which has no PTY to write to. For `interactive-terminal` that covers `resize` as well as `write`, so a resize from a suspended session's terminal view gets this code too. `release-size` needs no PTY and is answered `ok` for a suspended or exited row. A `queued` row has no PTY yet either, but it is still coming, and a `running` row whose PTY a kill just closed has not ended as far as its row says, so those two refuse both without the code. `send-user-message` holds the text for a task session with no PTY instead of refusing it (see its entry above). For a session it cannot hold (a Command Terminal, a workflow's own agent, or a hold the desktop refuses), the code is set only when the row is `suspended` or `exited`, as `notAcceptingInputRefusal` decides. A paste is never attempted into a session with no PTY, so no send waits out the paste engine's evidence wait. `answer-permission-prompt` checks it before the prompt binding, because a suspend drops the session's activity state and the binding would otherwise answer "no prompt outstanding" with no code.

There is **deliberately no shell, file-read, or arbitrary-command verb** - absent from the protocol entirely, not filtered at runtime. This mirrors the lesson from SSH forced-command escapes and is the counter-example to Chrome Remote Desktop / VS Code tunnels, which are identity-gated but capability-unscoped. Adding a verb to this list is a protocol change; it does not by itself grant anything to a device - a device's roster entry still has to include the verb in its `CapabilitySet`, and the desktop's `CapabilityRouter` still has to have a handler registered for it.

`command-terminal` is the one verb whose name passes through the protocol tests' shell/file/command filter, and it does so on a reviewed allowlist (`REVIEWED_VERB_NAMES` in `tests/unit/protocol/capabilities.test.ts`). It starts the project's agent CLI, not a shell, and the phone names no command. What keeps the promise is that a Command Terminal ENDS when its agent exits: the agent-absence sweep judges Command Terminals, and the agent's own SessionEnd hook asks it to look at once, so a `/exit` ends the terminal in about 4 s (see `docs/architecture/sessions/index.md`), so no bare shell is left for `interactive-terminal` to type into. Under WSL, or with the background-shell watcher off, the sweep cannot read the process tree, so the SessionEnd itself ends the terminal after a 5 s settle; an agent with no SessionEnd hook there keeps its shell until the PTY exits. Two short windows remain and are shared with every task session: the moment after spawn before the agent starts (the phone keeps its input disabled until the terminal's first activity event), and the seconds between an agent exiting and the sweep confirming it. The agent's own `!` bash mode is equivalent shell reach on any session, so neither window adds a capability a paired phone lacks.

`src/main/mobile-bridge/capability-router.ts` is the desktop-side dispatch point: it checks the requesting session's `CapabilitySet` (bound at pairing time) before even looking up a handler, so an unauthorized verb is rejected before any handler code runs. Every verb has a registered handler (`src/main/mobile-bridge/handlers/`, wired once by `MobileBridgeService.attachContext()`); an authorized-but-unregistered verb would still fail closed with an explicit "no handler registered" error rather than doing nothing silently - that guarantee stays load-bearing even though nothing exercises it in production today. The check itself is unconditional infrastructure, independent of what a device happens to be granted - see [Full access on pair](pairing-and-roster.md#full-access-on-pair) for what changed there.

A verb the desktop's protocol build does not know at all never reaches the router: `decodeMessage` rejects it. It used to be rejected the way a garbled frame is (`BridgeSession` emitted `frameRejected` and sent nothing), so a NEWER phone sending a verb to an OLDER desktop timed out after its per-verb budget, unable to tell "desktop is old" from "desktop is unreachable". Now `decodeMessage` throws a typed `UnsupportedVerbError` (`packages/protocol/src/wire/framing.ts`) that carries the request's `requestId` and `verb`, and `BridgeSession` answers it directly with `{ ok: false, error: 'Unsupported verb: <name>', code: 'unsupported-verb' }` (`refuseUnsupportedVerb`), then emits `unsupportedVerb`, which the service logs. Deny-by-default holds: the reply is a fixed refusal keyed on nothing but the verb's name, no capability check runs and no handler can, and the typed error is thrown only for a well-formed request (a string `requestId`, a string `verb`, a JSON `payload`) - a malformed frame is still dropped silently, because there is nothing to answer and replying to unstructured input would hand the sender a probe. `code` is a new optional field on `CapabilityResponseMessage` (`CapabilityErrorCode`; `response-too-large`, the second member, is described in the log table under [Reading the log](relay-transport.md#reading-the-log)); it is what a phone keys its "update your desktop" copy on, and an older phone's decoder drops the unknown key and still shows `error`. The refusal helps only for verbs added AFTER the desktop build that carries it: a desktop older than that still drops the frame.

### Permission-prompt id binding

There is no dedicated permission-prompt object in the desktop app - a prompt is just the agent's own TUI prompt, and the activity engine tracks only that one is pending (`ActivityStatsSnapshot.permissionPending`) plus which tool it is for (`permissionAwaitedToolId`, the `tool_use_id` - added in Phase 2, kept in sync between the engine-internal and IPC copies of `ActivityStatsSnapshot` per `activity-stats-snapshot-parity.test.ts`). `answer-permission-prompt`'s handler synthesizes a prompt id (`${sessionId}:${permissionAwaitedToolId}`), reports it in `read-stream`'s snapshot as `awaitedPromptId`, and rejects an answer whose `promptId` does not match the CURRENT live value - the safety property that makes this verb meaningfully different from a plain `interactive-terminal` write. The phone sends raw keystrokes; no agent-specific interpretation happens in the bridge (per `agent-adapters-boundary.md`).

A prompt that appears (or clears) AFTER the subscribe snapshot is pushed live as the `permission` activity payload (`{type: 'permission', promptId, pending, options?}`): `read-stream`'s subscription re-derives the awaited id on every activity/session-event emission and pushes only on change (pending `false` carries the id that just cleared). Without this, a phone could answer only prompts already outstanding at subscribe time or blindly re-subscribe to discover new ones.

The phone answers with raw keystrokes either way, but since 0.6.0 it no longer has to LABEL its buttons blind: `src/main/mobile-bridge/prompt-options-probe.ts` (`extractPromptOptions`, pure) parses the pending dialog's numbered option rows (`❯ 1. Yes`, `2. Yes, and don't ask again...`, box border tolerated; last complete 1..n run wins, minimum two options) out of the same serialized frame the mobile seed uses, rendered through the shared `VirtualScreen` VT-grid (`src/main/pty/virtual-screen.ts`, extracted from the Claude model-picker probe; its widths come from `wcwidthV11`, the same Unicode 11 table the serializing headless parser runs, so the probe's grid wraps where the frame assumes). The subscribe snapshot reports the labels as `awaitedPromptOptions` (probed from the frame already fetched for `scrollback`), and the live pending push attaches them as `options`, probing when the prompt appears with one short retry in case the activity emission beat the TUI's dialog paint. Both fields are additive and best-effort: absent or null means "unknown", and the phone falls back to its blind approve/deny keystrokes. `answer-permission-prompt` is untouched - keystrokes remain the answer transport, and no agent-specific parsing enters the bridge (any TUI that draws a numbered dialog parses; anything else yields null).

**A phone's Deny now clears on its own (task #640).** `answer-permission-prompt` only writes keystrokes; it never learns which option the user picked, and a manual deny fires no hook of any kind (Claude does not re-invoke the model, so no `ToolStart`/`ToolEnd`/`Stop` follows). Before the fix, `permissionPending` stayed stuck until a human typed something new at the desk - the exact case a paired phone cannot satisfy (answer from the phone, put it down). `SessionTelemetry` now polls the durable transcript for the rejection every 2s while any session is `permissionPending` (see "Permission flag" in `docs/architecture/activity/predicate.md`); once it observes the deny, the desktop's own `permission` activity payload clears the same way an approval always did, and the phone's card drops with no further action from the user. The probed `options` above are unrelated and unaffected - they only ever labeled the buttons, never read which one was pressed.

## Board Tool Surface

`board-tool-read` / `board-tool-write` are **not the MCP protocol** - despite the `{tool, params}` shape, no agent, LLM, or JSON-RPC round-trip happens anywhere in this path. `handleBoardTool` (`src/main/mobile-bridge/handlers/board-tool.ts`) is a plain function call straight into `commandHandlers` (`src/main/agent/commands/index.ts` - the same registry the in-process MCP HTTP server also happens to dispatch into), reusing the exact handlers and board-mutation side-effect fan-out without re-deriving the `register*Tools` layer's zod schemas, defaulting, rate limiting, or LLM-facing prose formatting. This is the same kind of direct reuse `read-board`/`move-task` do against their own repositories/`handleTaskMove` - a thin authorization + routing wrapper over the existing engine, not a second protocol surface. It exists for the long tail of task/backlog CRUD (create, edit, delete, link PR, backlog promote/update/delete, stats, transcript, handoff) that would be tedious to give each its own bespoke verb. The `tool` field a request names is the **internal `commandHandlers` key** (e.g. `'create_task'`), not a public MCP tool name.

`src/main/mobile-bridge/handlers/board-tool-allowlist.ts` classifies every `commandHandlers` key as `'read'` or `'mutate'`, building the table from the protocol package's `BOARD_TOOL_READ_NAMES` / `BOARD_TOOL_WRITE_NAMES` tuples (`packages/protocol/src/capabilities/board-tools.ts`) so the phone's typed tool-name unions and the desktop's enforcement cannot drift (`board-tool-allowlist.test.ts` fails if a new registry entry ships unclassified, or if the protocol tuples drift from the registry's actual key set). Excluded from both verbs:
- `query_db` (raw SQL escape hatch).
- `create_column`, `delete_column` - board **structure**, not the task CRUD this path exists for, and the worst fit for a surface that skips the `register*Tools` zod layer: `board-tool.ts` validates only that `params` is an object, so `delete_column`'s `params.column as string` and `create_column`'s dozen-plus `String()`/`Number()`/`Boolean()` coercions would take arbitrary JSON with no narrowing. Reshaping a board from a phone is not a capability anyone has asked for; if it is ever wanted it should get a bespoke verb with its own schema, not arrive by omission here.
- `move_task`, `reorder_tasks`, `list_tasks`, `list_columns`, `list_backlog` - real, safe `commandHandlers` entries, but **duplicates** of the dedicated `move-task` and `read-board` verbs, which give a cleaner contract (swimlaneId not column-name resolution; full `Task`/`Swimlane` objects; `read-board` also has a live subscription these one-shot tools lack). `move-task` already carries a `targetPosition`, so single-task within-column placement is a phone capability today; `reorder_tasks` would be a second contract for that same action, differing only in doing a whole column at once. If bulk re-sequencing from a phone is ever wanted it belongs in `move-task`'s verb family with a real schema, not reached by omission here. Excluding them keeps exactly one path per capability instead of two competing ones.
- `reserve_dev_ports`, `check_dev_ports` - real `commandHandlers` entries, excluded by name because a dev-server port reservation is about processes on the DEVELOPER'S machine. An agent asks for ports it is about to bind, and the answer is only meaningful next to the dev servers themselves; there is nothing for a phone to do with one, and reserving from a phone would take a port out of the pool with nothing ever binding it. Excluding rather than classifying also keeps both names out of the published protocol tuples, so neither implicates a `@kangentic/protocol` release.
- `list_automations`, `set_automations`, `get_automation_runs`, `run_automation` - a column's automations are board configuration, and `set_automations` can author a script the desktop runs on the next move into that column, which is the code-execution line `query_db` already draws. Nothing on a phone renders an automation.
- The workflow tools other than `list_workflows` and `get_workflow` (reads) and `pause_workflow` and `resume_workflow` (writes). Planning a workflow (`save_workflow`, `add_workflow_task`, `link_workflow_tasks`, `unlink_workflow_tasks`, `set_task_route`, `remove_from_workflow`, `request_project_access`) is the workflow agent's job beside the desktop canvas, where the plan is seen whole. `start_workflow` is the plan's approval and `delete_workflow` cannot be undone, so both stay with the desktop's Workflows view and its confirms.
- Everything not in `commandHandlers` at all: the `kangentic_browser_*` family, the dev-only `kangentic_devtools_*` family, the diagnostics tools (`tail_logs`, `get_recent_crashes`, ...), and the remaining cross-project tools (`list_projects`, unified `search`, `move_task_to_project`) are registered through entirely separate registries, so building the allowlist from `commandHandlers`'s keys excludes them for free, with no separate name-matching needed.

A phone bootstraps its project list through `read-board` with no `projectId`, since `commandHandlers` has no `list_projects` entry.

A phone opening a completed task reads its full report with `get_task_report` (`{ taskId, project }`). The result is typed by the protocol's `TaskReportWire` and narrowed with `parseTaskReportWire`: the route, the span, every linked commit and the per-file changes the desktop's completed view shows. The desktop caps its files, commits and stays and sends their counts, so the result stays small on the relay. See [kangentic_get_task_report](../mcp-server/task-read-tools.md#kangentic_get_task_report) for what each section holds.
