# Data feeds

Each `read-*` handler subscribes to a live main-process source and pushes `BridgeEvent`s (`packages/protocol/src/events/event.ts`: `transcript` / `activity` / `terminal` / `terminal-resize` / `board` / `diff`) over the established `BridgeSession`, tracked per-device in a `SubscriptionRegistry` so a device's live subscriptions tear down together on disconnect or revocation:

- **`read-stream`** taps `SessionManager`'s **unfiltered `data-tap` event** (`src/main/pty/session-manager.ts`), added specifically for this feed: SessionManager's pre-existing `data` event is gated to `focusedSessionIds` (the renderer's active tab), so a background session's output never reached a listener that isn't the focused renderer tab. `data-tap` fires for every byte of a session someone has subscribed to with `subscribeDataTap` (reference counted; the pty host sends a session's output as `tap` only while a subscription holds, and `read-stream.ts` subscribes for each session a phone streams and releases on unsubscribe), regardless of focus, and does not feed the renderer's backpressure accounting (that protocol exists only for the focused-tab drain handshake). Bytes a desktop replay drains out of the pending buffer as its double-delivery guard are forwarded to `data-tap` too (the buffer manager's `onDrain` seam), so a desktop terminal mounting or reloading the same session never steals output from the phone stream. The seed and the stream are exactly-once. `read-stream.ts` takes the session's tap BEFORE asking for the seed (`SessionManager.getSeedFrame`). The pty host stamps every `tap` chunk with its cumulative parser offset (`endOffset`), and the seed with the offset its snapshot covers (`barrierOffset`; the serialize is atomic with the parser's write barrier). The subscription then drops chunks ending at or before the barrier, slices the one that straddles it, and stops filtering after the first chunk past it. Bytes that raced the seed go out on the coalesce timer, so none overtake the seed's response. Without the early tap, output produced while the seed is taken would reach the phone in neither the seed nor the stream (the host forwards bytes only while a tap is held), and without the barrier, bytes still pending at the snapshot would arrive twice (`read-stream.test.ts`, "terminal bytes around the seed"). Every exit of the subscribe releases the early tap, a throw included. The seed always fits the wire. A terminal subscribe whose response would be over the frame caps (4 MiB of JSON before compression, 1 MiB after) is answered with a shorter seed and never a refusal, because a phone reads a refused subscribe as the session being gone. The handler checks the exact response with the protocol's `encodeMessageFailure` before it subscribes and, when it does not fit, re-takes the seed with `SessionManager.getSeedFrame(sessionId, scrollbackLines)`: first the history scaled down by how far the frame overshot, then the grid alone (`scrollbackLines` 0), then an empty seed. The grid, the modes and the scroll region are whole on the first two rungs. Each re-take is its own snapshot with its own `barrierOffset`. The subscription filters the tap by the barrier of the frame that is sent. The empty seed keeps the last snapshot's barrier. The prompt-option probe reads the snapshot that was latest when the handler first saw the prompt: the full-depth frame when the prompt was already up, or the re-take after it when the prompt rose during the shrink. The check sits before the subscribe because `SubscriptionRegistry.set` runs the prior teardown on the key, which would take a phone's list-only feed for the session down. Unlike the desktop's replay sampling, the seed drains nothing, so a desktop terminal on the same session keeps every byte. `read-stream.ts` drops any further `data-tap` byte once `SessionManager.isSessionTeardownInFlight(sessionId)` reads true, rather than forwarding it: suspend()/kill() write the adapter's exit sequence (Ctrl+C, `/exit`) straight into the live PTY of an agent that is typed into (Claude on Windows and Linux is closed instead), and the fullscreen TUI's repaint as it leaves the alternate screen would otherwise reach the phone as a near-empty screen (a bare shell prompt) for the seconds-long teardown window. Desktop's own terminal pane is spared this on the `suspend()` path by an accidental race (its tab drops on the `status` flip, which fires before the exit sequence is written), but not on `kill()`, which deliberately leaves `status` at `running` and emits no flip before `writeExitSequence` on a typed-into agent; the mobile subscription has no such race to rely on either way, so it checks explicitly and covers both paths. Raw output is coalesced on a short timer before pushing (`TerminalEvent`), with a small-payload fast path that flushes a keystroke echo immediately instead of waiting out the timer. The subscribe snapshot reports the PTY's grid (`ptyDimensions`), and `SessionManager`'s `pty-resize` emission (fired on every resize of any origin, plus once at spawn) is forwarded as a `terminal-resize` event - after flushing pending old-grid output first - so the phone renders at exactly the grid the bytes were laid out for instead of guessing a width. The seed frame and all live output are laid out under the **Unicode 11 width table** (`@xterm/addon-unicode11` is active on the desktop's headless parser and every desktop xterm - see `.claude/rules/xterm-unicode11-parity.md`), so the phone's replaying terminal must activate unicode11 the same way; a V6-table phone wraps one column early per emoji and every following row of an agent TUI frame drifts. A phone terminal whose `onData` reaches the PTY must also leave capability queries unanswered, as the desktop's does (`.claude/rules/xterm-query-replies.md`): from xterm 6.1 it answers XTVERSION and the color-scheme query by default, and a reply from the phone alone would open Claude Code's sync-output and DECSTBM gate for whichever session the phone happened to stream when that agent booted. `activity`/`usage`/`event` telemetry pushes as `ActivityEvent`. Transcripts never ship wholesale (a long session's full conversation exceeds the 1 MiB frame cap): `handlers/transcript-sync.ts`, run in the retrieval worker with one sync state per subscription (`transcript.mobileSync`), diffs each new `resolveTaskTranscript` revision against exactly what this subscription was last sent (uuid-keyed, with a source-reference serialization cache) and pushes only the changed/new entries as absolute-indexed `TranscriptEvent` delta upserts, split into byte-budgeted chunks - or a `reset` signal when the phone cannot patch (shrink, reorder, degraded/index source). A burst of session events is coalesced into one read 250 ms after it, with one more if an event lands during a read, so a tool burst no longer re-reads the task's transcript once per event per subscription. Subscribing seeds the sync state without pushing; the phone bootstraps its view with the `transcript-window` action (newest `limit` entries before `beforeIndex`, byte-budgeted), and pages older history the same way on scroll-up. The subscribe snapshot also reports `sessionStatus` (`running` / `queued` / `suspended` / `exited`; absent from pre-0.5.0 desktops, which the phone reads as `running`) and `resuming` (the session was spawned as a resume, so the card reads "Resuming agent..." until a model name arrives; from 0.16.0). Both come from a registry read taken AFTER the seed await (`getSeedFrame`), because a queue promotion inside that await replaces the row. It also reports `resumable` (from 0.16.0), the streamed session's copy of `BoardTaskWire.resumable` (see `read-board` below). The board row is the copy a phone gates Resume on: a desktop pause clears the task's `session_id`, so a phone holds no stream on a paused session once its board refreshes, and this copy only keeps a session screen that is open during the suspend current. When the streamed session's PTY exits the subscription's last word - pushed between the final terminal flush and its own teardown - is a `session-ended` activity payload whose `intentional` flag distinguishes a deliberate stop from a crash.

  From 0.16.0 the subscription also listens for lifecycle changes:

  - **Status.** It listens to `SessionManager`'s `session-changed` and pushes a `status` activity payload (`{ type: 'status', status, resuming, resumable }`) whenever its own session's status, `resuming`, or `resumable` actually changes. `resumable` is recomputed on every edge (it reads the task's column and the registry only for a suspended session, and answers false while the task also holds a queued or running row, as the board row does). A move to Done or an archive of a paused task is no edge of its row, so this copy can stay true after the board row's turns false, which is one more reason a phone gates Resume on the board row. That covers a queue promotion, a suspend (pushed before the PTY's exit, so it precedes `session-ended`), and the agent-absence sweep's `exited`, which does not end the feed because the PTY's `exit` still follows.
  - **Successor hop.** A resume never arrives as a status change. It spawns a NEW session id and the spawn flow drops the paused row without an event (`session-spawn-flow.ts`), so a feed held on a paused session ends instead, with `session-ended { intentional: true, successorSessionId }` when another session of the same task appears after its row is gone. The check is "this row is gone", not the newcomer's status, because a full queue first shows the newcomer as `queued` while the paused row still exists.
  - **No successor.** A removed paused row (`session-removed`) and a successor whose own spawn failed (its exited placeholder arrives on `session-changed`, then `exit`) end the feed with no successor to name. Before this, a list-only subscription on a paused session was never torn down.

Feed payload CONTENTS are typed by the wire mirrors in `packages/protocol/src/events/payloads.ts` (`TranscriptEntryWire`, `ActivityStateWire`/`ActivityReasonWire`, `SessionUsageWire`, `BoardColumnWire`/`BoardTaskWire`/`BacklogItemWire`, `DiffFileListWire`/`DiffFileContentWire`), which deliberately MIRROR the desktop shapes rather than import them - the protocol package is a dependency-light leaf shared with the phone. `src/main/mobile-bridge/handlers/wire-mappers.ts` is the one place each mirror meets its desktop source type, replacing the Phase-2-era `as unknown as JsonValue` casts, so a desktop-type change that would break the wire surfaces there as a compile error. The protocol package also ships the phone-side runtime guards (`isBridgeEvent`, `parseTranscriptEntriesWire`, `parseReadStreamResponsePayload`, ...) that narrow a decoded payload before the phone trusts a field. From 0.26.0 a `permission` reason carries `waitKind` (`question` or `approval`) when the agent said what it waits for: `toActivityReasonWire` adds it only then, and `parseActivityReasonWire`, which every protocol parse of a reason goes through, drops a kind it does not know rather than failing the event.
- **`read-board`** subscribes to `IpcContext.boardEvents` (below), filtered by `projectId`, and to the bridge's `SpawnProgressFeed` (below the bus section). Every snapshot stamps each task's in-flight spawn-progress label onto `BoardTaskWire.spawn_progress` from one `getInFlightSpawnProgress()` read, and from 0.16.0 stamps `BoardTaskWire.resumable` from one `listSessions()` read: true when the task has a paused registry row and no live one (`pausedTaskIdsOf`, which applies `isPausedTaskSession`: `suspended` and not transient, so neither a Command Terminal nor a workflow's own agent; the same scan `startTaskSession` runs to pick the resume path) and `isResumeOffered` (both in `src/shared/session-resume-eligibility.ts`) clears it, which is the resume direction of `sessionToggleOffer`, the one rule the task detail's Pause / Resume control reads too, and the card menu's row reads it as well, enabling Resume under the same conditions and showing it disabled otherwise (not To Do, not Done, not archived). A respawn queued behind the concurrency limit leaves the task holding `[suspended, queued]` until promotion. The desktop shows the queued session there and `startTaskSession` answers `live`, so that task is not reported paused. That is the desktop's promise that `start-session` resumes the session the way the Resume button does rather than starting the column. It is explicit because every 0.15.0 desktop answers `start-session` by starting the column, and absent (parsed as null) on those desktops, which a phone reads as "offer no Resume". A pause, a resume, a move and an archive each already reach the phone as a board event, so the next snapshot carries the new value. From 0.17.0 the same scan also stamps `BoardTaskWire.paused`, which is the `pausedTaskIdsOf` answer on its own with no column or archive gate, the fact the desktop card's "Paused" footer reads. A paused task in Done or on the archived page therefore reads `paused: true, resumable: false`. The desktop draws an archived task as a compact card with no footer (`TaskCard`'s `compact` branch, which only `DoneSwimlane`'s Completed list passes; `CompletedTasksDialog` renders no card status either), so a client that matches the desktop card draws "Paused" only when `archived_at` is null. A move from another column into Done archives the task in the same step (`task-move.ts`), so only a task that sits in Done unarchived gets the full card and its "Paused" footer. `read-board` feeds one paused answer to both fields (from 0.27.0 the paused row's id, from which `toBoardTaskWire` derives `paused`), so `resumable` is never true while `paused` is false. The `'sessions'` projection still keeps only a resumable paused task. From 0.18.0 the scan is `taskSessionStatesOf`, which returns the live set beside the paused one, and `BoardTaskWire.pausable` is `isPauseOffered`: the task has a `running` or `queued` registry row (the predicate `findLiveSessionByTaskId` uses, which is how `pauseTaskSession` finds the session it suspends) and is not in To Do. Done and archived do not clear it, matching the desktop. A move into Done suspends the session in the same step, so a task there reads true only when that suspend failed. One scan yields both sets, so `pausable` and `paused` are never both true. It departs from the task view in one state on purpose: while a spawn label is up and no session is live, the desktop card shows a Pause control whose click only cancels an in-flight resume or start, and `pause-session` refuses a task with no live session, so `pausable` reads false there. From 0.27.0 the same scan also stamps `BoardTaskWire.paused_session_id`, the registry id of the task's paused row (`pausedSessionIdByTaskId`), and `toBoardTaskWire` derives `paused` from it, so the id is set exactly while `paused` is true, with no column or archive gate. It is the id a phone names in `send-user-message` for a paused task, whose `session_id` a pause cleared; that verb looks the id up in the registry and holds the message for the task's next agent. A task holding two paused rows gets the later one in registry order. The id is the registry's, never the DB record's, because a restart re-registers each paused session under a fresh id (`registerSuspendedPlaceholder`). That registration emits `session-changed`, which `SessionLifecycleBoardFeed` turns into `task-updated`, so the snapshot the phone re-reads already carries the new id and no extra wiring is needed.

  From 0.20.0 every snapshot, full or `'sessions'`, also carries `commandTerminals`: the project's live Command Terminals by slot, each `{ sessionId, projectId, slot, name, named, activity }`. `name` is `commandTerminalDisplayName` (the derived name, else "Command Terminal N"), `named` says the terminal has its own name, and `activity` is the raw `{ state, reason }` pair `read-stream` reports, so the phone formats the line with the formatter it already uses for a task's agent. The list is built from `listSessions()`, keeping the project's Command Terminal rows (`isCommandTerminalSession`, so a workflow's own agent is never listed) that are `running` or `queued` (a terminal started while the desktop's concurrency limit was full already holds its slot against the cap); a terminal's row leaves the registry when it ends, so this is exactly the live set. The activity is a seed for a first paint: a phone subscribes `read-stream` for each terminal's `sessionId` and reads the live state and reason there, as it does for every task agent in the Agents feed. `commandTerminalsOffered` is `session.capabilities.has('command-terminal')`, true when this desktop serves the verb and the device holds it; the phone keeps no grant list and shows its Terminals button on this flag, as `pausable` gates Pause. From 0.24.0 `earlierConversationsOffered` is the same grant, sent by a desktop that serves the verb's `list-earlier` and `resume` actions. A phone offers its Earlier list on it, and an older desktop omits it, which the phone reads as false so it never sends either action there.

  From 0.22.0 every task row carries `automations_disabled`, the task's `automations_disabled` column: true when the user or an agent switched the task's column automations off (no On task enter, On agent turn end or On task exit row runs for it, a move types no column message, and Kangentic approves none of its plans). It is what the desktop card's "Automations paused" strip reads. `toBoardTaskWire` always sends a real boolean (`task.automations_disabled === true`), because the parser reads an absent key as null and the phone reads null as a desktop older than the field, which is its gate for showing the Pause or Resume automations row at all. There is no verb for the write. The phone flips it with its existing `board-tool-write` `update_task` call and the camelCase param `automationsDisabled`, which `handleBoardTool` hands straight to the same `commandHandlers.update_task` the MCP server runs. On a workflow task the switch is the task's own hold out of its workflow (`applyAutomationsHoldChange`), and every workflow fact carries `automations_pausable: true` (protocol 0.25.0) so the phone offers the row on a workflow task only where the desktop honours it; an older desktop refused `true` for one. A held task's `lock_reason` is null, since a hand may move its card. The desktop clears the switch by itself only when the task joins a workflow (`setWorkflowMembership`, which does not bump `updated_at`). A move out of Done or a restore from the archive keeps it. That join, and every flip by any hand, is followed by a `task-updated` board event, so the snapshot the phone re-reads carries the new value: a desktop flip through the IPC write announce below, an MCP or phone flip through `onTaskUpdated`, and a workflow join through `announceBoardChange`.
- **`read-diff`** subscribes a **bridge-owned `DiffWatcher`** instance (`MobileBridgeService`'s own `diffWatcher` field), never `IpcContext.diffWatcher` - that instance is shared with the renderer's Changes panel and is single-watch-per-path, so a bridge teardown would kill the renderer's live watch on the same worktree (and vice versa). A project-folder diff (no `taskId`) watches the project root under its own subscription key (`diff:project:<projectId>`), so it never collides with a task's.

## Consolidated board-changed bus

`src/main/mobile-bridge/board-event-bus.ts`'s `BoardEventBus` (exposed as `IpcContext.boardEvents`, a plain Node `EventEmitter`, not an IPC channel) is a single main-process-internal stream for every board mutation, whatever caused it: an agent tool call, a session lifecycle edge, or a plain desktop drag. `read-board` subscribes once instead of listening to each ad-hoc `IPC.*_BY_AGENT` renderer-push channel individually. It is fed **additively**, right next to the existing `sendToRenderer(...)` calls in each board-mutating callback of `buildCommandContextForProject` (`src/main/agent/mcp-project-context.ts`) and the PR-linking push (`src/main/pr/pr-linking.ts`). `onTaskMove` delegates the whole fan-out (the bus emit plus an origin-keyed renderer push) to `handleTaskMove`, so that every caller of it announces identically instead of each remembering to. The board.ts swimlane handlers (`SWIMLANE_CREATE` / `UPDATE` / `DELETE` / `REORDER`) are a fourth, simpler feed: they emit directly, with no accompanying `sendToRenderer` push, because the renderer that triggered the edit already has its own synchronous IPC result and needs no separate notification - only OTHER listeners (a paired phone, the Agent Monitor) need telling. Before this, only an agent/MCP-driven column edit reached the bus, so a user's own column edit in the Board Manager left those listeners' board snapshots stale until an unrelated change happened to fire. Desktop task writes over IPC are another feed, for the same reason. A backlog label rename or delete rewrites task labels but does not announce, so a phone sees it on its next board event. Every task-write handler on `ANNOUNCED_TASK_WRITE_CHANNELS` (`src/main/ipc/helpers/task-write-announce.ts`: create, update, delete, bulk delete, restore from the archive and its bulk form, branch switch, update from base, a model or effort pin, a PR resolve, and a backlog demote) calls `announceTaskWrite(context, event, projectId, boardChange)` once from its `finally`, which emits `boardChange` on the bus for every sender, the main window included, and then sends the other-window push to the main window. `boardChange` is a required parameter, so each handler states what it changed (`task-created`, `task-updated` or `task-deleted` with the task ids). `TASK_MOVE` passes `null`, because `handleTaskMove` already emits on the bus at commit and at settle. `TASK_RESOLVE_PR` announces even though `linkPR`'s `onLinked` emits for a changed or cleared link, because a write of the head SHA or pushed branch alone reaches no `onLinked`. `BACKLOG_PROMOTE`, which is not a project-scoped channel, calls the bus half (`announceTaskBoardChange`) with the ids it created. `WORKFLOW_DELETE` is the other exception: a workflow delete that takes its never-started tasks (`deleteNeverStartedTasks`, `src/main/workflows/workflow-service.ts`) calls `announceTaskBoardChange` once per board with `change: 'task-deleted'` and the ids of the deletes it ran, failed ones included. Before this, no desktop IPC task write reached the bus, so a card's Pause automations, a rename, a restore into a column that starts no agent, or a delete left a paired phone's board stale until something unrelated fired. `tests/unit/task-write-announce.test.ts` pins each handler's board change. A task move emits on the bus TWICE: once at the commit point inside Phase 1, before any of the slow work, and once from the settle-time `finally` after the whole move (and any rollback) has run. The first is what lets a paired phone settle an optimistic move without waiting out the desktop's tail; the second is what corrects a committed-then-rolled-back move. The renderer hears twice too, for every origin but `renderer`: a quiet board reload at the commit point (`MOVE_COMMIT_PUSH_BY_ORIGIN`), so the card leaves its column before a Done move's teardown, and the origin-keyed push at settle. A `TASK_MOVE` from another window (the detached Agent Monitor) also sends `task:changedInOtherWindow` at the commit point, through the `onCommitted` option calling `announceToMainWindow`, and the settle-time `announceTaskWrite` sends it again because a move can commit and then roll back. The `agent` and `auto-move` channels each raise a toast per push, so they fire only at settle and the commit point reloads through `task:sessionResync`. The renderer's existing `*_BY_AGENT` pushes and `useAgentDrivenInvalidation` are untouched. The bus raises its listener cap to 100 (`setMaxListeners`): one Agent Monitor listener plus one `read-board` subscription per paired device per project it streams is `1 + devices x projects`, which crosses Node's default of 10 on any machine with a phone and more than nine projects.

Session lifecycle edges feed the same bus: `src/main/mobile-bridge/session-lifecycle-feed.ts`'s `SessionLifecycleBoardFeed` (started in `attachContext()`, disposed with the service) subscribes `SessionManager`'s `session-changed`, `session-removed`, and `exit` emissions and emits a `task-updated` board change per edge - immediately, plus one settle re-emit after ~1s coalesced per task, because several lifecycle edges land before their follow-up DB writes settle. Without it, a phone's board view kept showing a stale "running" badge until the next agent-driven mutation happened to fire.

A Command Terminal never emits `task-updated`: its task id is made up and names no board row, and those events reached phones, the retrieval worker's task-record sweep and the Agent Monitor as a phantom task. From 0.20.0 it emits `command-terminals-changed` instead, with its session id in `ids` and no `taskId` on the envelope, on three edges only: its start (its first `session-changed` that is not already `exited`; a terminal whose shell never started reaches phones only through its removal), its rename (a `session-changed` that carries a new `commandTerminalLabel`), and its end (`session-removed`). Its activity is not an edge here, because a phone already streams each terminal's activity on `read-stream` and a thinking/idle flip would otherwise cost every subscribed phone a board re-read. The retrieval sweep skips the kind. The `BoardEventPayload.change` union is closed, so an older phone's `isBridgeEvent` drops the event and keeps the rest of its feed.

Spawn-progress labels deliberately do NOT feed the bus. `src/main/mobile-bridge/spawn-progress-feed.ts`'s `SpawnProgressFeed` (started in `attachContext()`, disposed with the service, handed to the handlers as `CapabilityHandlerDeps.spawnProgressFeed`) subscribes `onSpawnProgressChange` in `spawn-progress.ts`, which fires on every label push, and `read-board` forwards each change as the same `task-updated` board event a row change sends. A label change is not a board mutation, and the bus also wakes the retrieval worker's task-record sweep and the Agent Monitor push, so a git-queue wait's 5s label refresh would re-sweep task records for nothing. The feed throttles per task: the first label emits at once, later changes inside a 1000ms window coalesce into one trailing emit (a spawn can pass through fetching, creating the worktree, the setup script and starting the agent inside one second), an unchanged re-push emits nothing, and the clear always emits. A label reaches the phone only through `toSpawnProgressLabelWire` (`handlers/wire-mappers.ts`), on both `BoardTaskWire.spawn_progress` and `session-ended`: it strips escape sequences, control characters, invisible format characters (bidi controls, the zero-width space, the soft hyphen, the byte order mark) and tag characters outside the England, Scotland and Wales flag emoji, turns line breaks and tabs into spaces, and caps the label at 120 characters. Every git caller passes a named phase, so the one label text the desktop did not write is a column automation's name, which the automation runner shows as `Running "<name>"...` and a team may share in a committed `kangentic.json`. The throttle lives in the feed rather than in each `read-board` subscription because a phone re-reads the board after every event, which replaces the subscription and would reset a per-subscription throttle. The owning project is resolved on a label's first emit by the same project-list scan the spawn-stall push uses, then kept until that label clears, since a task never changes project under one id (`move_task_to_project` re-creates it under a new one). Nothing is resolved while no phone listens.

`read-board` also stamps every project-list entry with a `color` and the board snapshot with a `projectColor`: a deterministic accent (`handlers/project-color.ts` hashes the project id onto a curated 12-tone palette that reads well on the phone's near-black theme), so both sides agree with nothing stored. A future user-set project color overrides through the same wire fields.
