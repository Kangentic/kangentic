# Push notifications

Push payloads transit Expo's push service (and APNs/FCM under it), which must never see notification content. The pipeline keeps every hop blind:

1. **Registration** (`register-push` verb, `handlers/register-push.ts`): the phone sends its Expo push token, its `platform` (`android` or `ios`; absent means `android`), a device-generated 32-byte push key (base64url, length-checked at the protocol parse boundary), optionally its enabled `categories` (absent means every category; an explicit empty list means none), and optionally `acceptsClears: true` (step 6). The desktop stores all of it in `push/push-registration-store.ts`'s `mobile-push-registrations.json` sidecar (config dir, roster-store pattern, tolerant load), keyed by the requesting session's authenticated roster `deviceId` - never by payload content, so one device cannot register or unregister another. Revoking a device also clears its registration, unconditionally. Preferences are enforced **desktop-side**: the phone's category list is checked before a notification is even sealed, so the iOS Notification Service Extension never needs to know about them.
2. **Envelope** (`packages/protocol/src/crypto/push-envelope.ts`): the desktop seals a `PushEnvelopePlaintext` (`category`, `projectId`, `taskId`, `sessionId`, `taskTitle`, `detail`, `sentAt`, from 0.20.0 an optional `sessionKind`, from 0.26.0 an optional `waitKind` and an optional `title` and `body`, step 3, and an optional `clears` list, step 6) with XChaCha20-Poly1305 under the device's push key: a fresh random 24-byte nonce prepended to the ciphertext, the recipient device's static public key as AAD (a blob sealed for one device cannot be replayed at another), base64url without padding. `openPushEnvelope` (run on-device: Android Notifee / iOS Notification Service Extension) rejects tampering, wrong keys, wrong recipients, malformed plaintext, unknown categories, and any `sentAt` older than 24h or more than 5min in the future; every failure degrades to the generic placeholder, never to plaintext. A Command Terminal's alert sets `sessionKind: 'command-terminal'` and puts the terminal's name in `taskTitle` (`resolveTaskContext` in `mobile-bridge-service.ts`, which reads no task DB for one), so the phone routes the tap to that terminal by `sessionId`. A workflow's own agent resolves to no context, so it sends no push at all: the phone has no screen for it. The parser drops a `sessionKind` or `waitKind` it does not know, and a `title` or `body` that is not a string, rather than rejecting the alert. A terminal's deliberate end (Stop, or its agent exiting) sends no `session-failed`: the exit is intentional and the row is already gone. A crash still sends one.
3. **Triggers** (`push/push-notifier.ts`, keyed off `SessionManager`'s `activity`, `exit`, `plan-exit`, `turn-ended` and `session-changed` emissions, plus the spawn-stall watcher and the workflow-complete hook; clears also read the board-changed bus). Six categories, named for cross-vendor task-lifecycle vocabulary (`input-required` mirrors A2A's `TaskState.INPUT_REQUIRED`) rather than any one agent's terms:
   - `input-required` - the session transitioned INTO the `permission` activity state: a question the agent asked, or an approval it wants. The envelope's `waitKind` (`question` or `approval`) says which, read from the activity snapshot when the debounce fires (`permissionWaitKind`), and is absent when the agent did not say. A phone that knows the field titles the push "Agent has a question" or "Agent needs your approval"; one that predates it keeps "Agent needs your input". Also a running workflow task that needs the user (`notifyWorkflowTask`, from `workflows/workflow-recovery.ts`): its agent waits on them, or the workflow stalled on it. That envelope carries the reason as `detail`, no `waitKind`, and an empty `sessionId`, and it cools down and clears per task, so the idle sweep pausing the session after a stall does not clear it. A move of the task clears it.

     A **Notify me** automation row sends one too (`notifyAutomation`, through `showAutomationNotification` in `src/main/automations/shared/`, which every place that builds an automation context wires to `showNotification`). The envelope carries the row's own Title and Body as `title` and `body`, the task's title as `taskTitle`, the Body again as `detail`, and an empty `sessionId`, so a tap opens the task and the phone keys it by task, never replacing a session's own alert. A phone that predates `title` and `body` shows "Agent needs your input" over "task - body". The row is the user's own choice to be told, so it goes to every registered device whatever its categories and whether or not it is connected, with no cooldown, and it is never recorded for clears (step 6). Before sealing, the Title is cut to 200 characters and the Body halved until the blob fits the 3,000-character budget, since both are templated fields that can carry a whole description.
   - `turn-complete` - the session has SETTLED into `idle` (transitioned `thinking` -> `idle` and stayed there for `IDLE_SETTLE_MS`, ~45s). Never for a running workflow task mid-route (`isWorkflowStepSession`), whose step check says when it needs the user. The name is historical: it reports a session going quiet, not a turn ending. Firing on the bare transition made it one alert per reply - every exchange in a conversation ends in idle, so a single trivial task produced 20+ notifications - and the 30s cooldown below never covered it, because real turns sit further apart than that.
   - `session-failed` - the session exited with `intentional` false (a crash; a deliberate stop never notifies).
   - `plan-complete` - the session emitted `plan-exit` (a plan was approved).
   - `spawn-stalled` - a task's spawn (worktree/git prep) has been in flight past the stall threshold; this one has no `sessionId` yet (the session doesn't exist until spawn finishes), so it notifies keyed by `taskId` instead.
   - `workflow-complete` - every task of a workflow reached Done (`workflows/workflow-complete.ts`, the same moment the desktop raises its Workflow Complete toast). A workflow has neither a session nor one task, so the envelope carries the workflow's name as `taskTitle`, an empty `taskId` and `sessionId`, and "All 9 tasks are in Done." as `detail`; it cools down per workflow. Where a tap on it lands (the project's board is the natural target, with no task to open) is the mobile app's follow-up, since its tap router was written for envelopes that name a task. Appended last to `PUSH_CATEGORIES`: a phone that predates it fails to open the envelope's category and shows the generic placeholder, as it does for any envelope it cannot open.
   Permission triggers are debounced 2s and re-checked at fire time, so a prompt answered at the desk within the window never pings the phone. `turn-complete` uses the same pattern with a ~45s window: reaching idle arms a timer, returning to `thinking`/`permission` or exiting cancels it, and the live activity snapshot is re-read when it fires. The phone's `localNotifier.ts` mirrors this - the desktop suppresses push for a device whose bridge session reports `connected`, so during the phone's background keepalive the local notifier is the only producer, and debouncing one side alone would leave the flood intact.
4. **Suppression**: nothing is sent while the Mobile bridge switch is off. Turning it off closes the relay sessions, but a push goes to Expo directly, so the notifier reads the switch itself at every notification. Then a device whose bridge session reports `connected` is never pinged (presence suppression - the user is already watching from it), then the device's category preferences are checked, then each (device, session-or-task, category) tuple has a 30s cooldown. A Notify me push skips all three (step 3). Presence is read from `connectionState`, not the session's raw `isEstablished` flag: on a silent phone death nothing nulls the session's streams, so `isEstablished` stays true for the whole relay keepalive sweep (30 to 60s) after `connectionState` has already concluded `offline`, which would otherwise suppress that device's push for the rest of the turn.
5. **Delivery** (`push/wake-channel.ts`, `push/expo-push-client.ts`): `PushNotifier` talks to a vendor-neutral `WakeChannel` interface, not to Expo directly - the only implementation today, `createExpoWakeChannel`, is a plain injected-fetch POST to the Expo push API (no SDK), one 5s retry on network error, with `mutableContent: true` set on a notification so the iOS Notification Service Extension is invoked. A drop-in replacement (e.g. a small Cloudflare Worker holding the same push credentials) only has to implement `WakeChannel`, honoring each `WakeMessage` field (`dataKey`, `priority`, `mutableContent`, `contentAvailable`). **Only `data.blob` (a notification) or `data.clear` (a clear, step 6) carries real content**, and unit tests assert no plaintext field value appears anywhere else in the POST body. A non-delivery (a thrown send, or a `WakeResult` reporting `delivered: false`) is logged with its reason and detail rather than swallowed, so a shared failure (a network outage, an Expo outage) leaves a trace instead of reading as several unrelated devices going silent. A genuine send failure (a network error, an Expo outage, or a thrown send) also releases that attempt's 30s cooldown stamp via a compare-and-clear that never wipes a fresher stamp a later call already set for the same key, so the device gets a real retry rather than losing the whole cooldown window to a notification that never arrived; `device-not-registered` does not release it, since the registration is dropped outright instead. The failure detail is Expo's own ticket text, which quotes the device's push token back (its not-registered message reads `"ExponentPushToken[...]" is not a registered push notification recipient`), so it passes through `redactPushTokens` on the way to the log and only the short device id identifies the device.

   The OS-visible `title`/`body` are sent to **iOS devices only**, branched on the registration's `platform`. An Android push carrying either is presented by expo-notifications ITSELF, natively, before it runs the app's background task - so every Android alert appeared twice, once as this generic placeholder and once as the notification Notifee posts after decrypting. Omitting both makes it a data-only message, which `ExpoHandlingDelegate.handleNotification` declines to present (it presents a backgrounded notification only when title or text is non-empty) while `runTaskManagerTasks` still runs, so nothing is lost - but only if the message ALSO omits `channelId`: Expo attaches an FCM `android.notification` block to any message carrying a channel id, title/body or not, and that block makes the FCM SDK render the tray item itself and skips `onMessageReceived` entirely, so the background task never runs. Android therefore gets no `channelId` at all, which costs nothing - the channel actually used is chosen on-device from the DECRYPTED category, and only the phone knows that. iOS keeps `title`/`body` because the Notification Service Extension that decrypts the envelope runs only for a push that carries an alert, and the placeholder is what shows when it cannot open one; stripping it would make iOS silent by construction. The iOS title is always `Kangentic` and the body a static per-category placeholder; iOS gets no `channelId` either, since Expo ignores it for APNs. A `DeviceNotRegistered` ticket drops the registration.
6. **Clears** (`packages/protocol/src/crypto/push-clear.ts`, `push/push-notifier.ts`, `push/push-clear-ledger.ts`): a notification goes stale when its condition resolves at the desk, and only the desktop sees that moment, so it tells the phone, which removes the notification from the lock screen without the app being opened. Only a device that registered with `acceptsClears: true` takes part: an older Android app shows the placeholder for any message it cannot open, so a clear would arrive there as a new notification. Every notification dispatched to such a device is recorded in a per-device ledger, and these resolve it:
   - `input-required` - the session leaves `permission`, or exits.
   - `turn-complete` - the session leaves `idle` (back to `thinking`, or into a prompt).
   - `plan-complete` - a turn of the same task that BEGAN after it ends (`turn-ended`, matched by task, since the plan-exit auto-move may respawn the session under a new id). Not "thinking": approving the plan takes the session from `permission` to `thinking` in the same breath as `plan-exit`.
   - `session-failed` - a different session of the task reaches `running`.
   - `spawn-stalled` - a session of the task reaches `running`.
   - any of these - the task changes lane, is archived (Done), or is deleted, read from the board-changed bus against the lane recorded at send time. The plan-exit auto-move (origin `auto-move`) resolves all but `plan-complete`, whose recorded lane moves with the task. A Command Terminal's alert records no lane and is never checked this way.
   - `workflow-complete` - never recorded; the phone clears it when the Board opens.
   - a Notify me push - never recorded. It reports a moment nothing at the desk resolves, and a row on a column's exit fires as its task leaves the lane, so a recorded one would be cleared by the very move that sent it.

   A clear entry (`PushClearEntry`) copies `category`, `projectId`, `taskId`, `sessionId` and `sessionKind` from the envelope it clears, plus `notifiedAt`, the `sentAt` of the newest notification it covers. The phone removes a matching notification only when that notification's own `sentAt` is at or before `notifiedAt`, so a normal-priority clear that Doze held back cannot remove a newer high-priority alert for the same session and category.

   A device connected at the moment of resolution is skipped, since the app is running and reconciles its own notifications. Otherwise the device's clears gather for 5s and go out as one message sealed exactly like an envelope (`sealPushClear`: same key, the recipient's static public key as AAD, the same freshness window) and sized to stay under Expo's 4096-byte payload limit:

   | Message | data key | priority | other keys |
   |---|---|---|---|
   | Android notification | `blob` | high | `mutableContent` |
   | iOS notification | `blob` | high | `mutableContent`, placeholder `title`/`body` |
   | Android clear | `clear` | normal | none |
   | iOS clear | `clear` | normal | `contentAvailable` |

   An Android clear is data-only at NORMAL priority because FCM deprioritizes an app whose high-priority messages show nothing; it arrives when the device leaves Doze, which is when the user looks. An iOS clear is a background push: Expo's docs map `normal` to APNs priority 5 and `contentAvailable` to `aps.content-available`, and call a message with only data and `contentAvailable` a headless background notification, but they do not say which `apns-push-type` Expo sends, so that is proven on a device rather than assumed. Apple asks for no more than two or three background pushes an hour and never delivers one to an app the user force-quit, so the desktop sends at most one per iOS device per 20 minutes (a clear Expo refused does not count against that) and keeps every iOS entry pending after it. Pending clears also ride the device's next notification as its `clears` field, which the phone applies before showing that notification; that is the reliable iOS path, because the extension runs for every alert push. An entry leaves when a message carrying it is delivered (for iOS, only a notification counts) or after 24 hours. The ledger lives in memory, so notifications sent before a desktop restart get no clears; the phone's own reconcile covers them when the app opens.

   The `data.clear` key is what lets a phone tell a clear apart BEFORE decrypting it. It also tells Expo, FCM and APNs that a message is a clear, so they learn the user acted at the desk at that time. That was already inferable from a clear's normal priority and missing alert. One key and one AAD seal both kinds, deliberately: a clear moved into `data.blob` fails the envelope parse (a placeholder, which junk already causes), and an envelope moved into `data.clear` fails or applies clears the desktop really sealed.
