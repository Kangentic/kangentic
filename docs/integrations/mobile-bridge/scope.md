# Scope and protocol history

One section per bridge phase and protocol release, oldest first, each saying what shipped and why. The last two are built but unreleased work and what stays out of scope.

## Bridge Phase 1: protocol, pairing & secure relay transport

- `@kangentic/protocol` package: wire schema, Noise KK + IKpsk0 implementations, secretstream framing, capability verb list, roster signing, QR payload encode/decode, transport interface.
- Device identity (encrypted at rest via Electron `safeStorage`, through its async API; refuses to persist unprotected). A pairing that finds an identity file it cannot read moves that file aside under a dated name before it creates a new identity, so a key a secret store failed to unlock once is never overwritten. The service reads the identity and the secure-storage verdict once per run (`whenStorageReady()`), runs the capability migration before any session opens, and serves its synchronous readers from that cache; the status and device-list IPC handlers await the same warm-up. Concurrent first pairings share one identity creation. On Linux, a Secret Service on any desktop now counts, which is what lets a desktop outside Chromium's list (sway, i3, WSLg) pair a phone; the hardcoded fallback key never does (see [board integration](../boards.md#safestorage-semantics)).
- Signed device roster with revoke-drop (rekey-on-revoke is scaffolded but the full multi-device re-provisioning flow is deferred).
- QR pairing ceremony (token-bound Noise PSK + SAS confirmation) with desktop settings UI.
- The desktop's outbound relay CLIENT connection with reconnect/backoff.
- Mobile Devices settings tab: enable toggle, relay mode (resolved default vs. custom override) with a Test connection probe, pairing flow, paired-device list, revoke.
- **Pairing overhaul (one comparison, one tap):** the pairing-confirm frame (`packages/protocol/src/pairing/confirm.ts`) and desktop auto-enroll on it, replacing the desktop's own "Codes match" / "Codes don't match" question; the emoji half of the SAS display dropped everywhere (digits only); explicit ceremony timeouts on both the `waiting-for-phone` and `sas-pending` phases (there was none before - the pairing token's TTL was only checked lazily); `startPairing()` now supersedes a stale in-progress ceremony instead of throwing, and the settings tab cancels on unmount, so "Pair a device" always reopens a fresh QR. Paired-device cards now show the device's X25519 key fingerprint (`formatKeyFingerprint`, `packages/protocol/src/roster/fingerprint.ts` - matches `kangentic-mobile`'s own display exactly), live per-device connection state, and paired date, with rename added alongside revoke. See [Full access on pair](pairing-and-roster.md#full-access-on-pair) for the paired capability grant.

## Bridge Phase 2: data feeds, interactive control & capabilities

- `interactive-terminal`, `board-tool-read`, `board-tool-write` added to `CAPABILITY_VERBS`; per-verb request/response payload types (`packages/protocol/src/wire/payloads.ts`); `terminal`/`diff` event kinds and a reshaped project-keyed `BoardEvent` (`packages/protocol/src/events/event.ts`); a per-kind `framing.ts` event validator; `deriveSessionSlotId` for the ongoing-session relay slot.
- `MobileBridgeService.attachContext()` + `syncSessions()`: opens one live `BridgeSession` per roster device, routes decoded `capability-request` messages through `CapabilityRouter.dispatch()`.
- The nine Phase 2 capability-verb handlers (`src/main/mobile-bridge/handlers/`; `register-push`, `start-session` and `pause-session` came later), each described under [Data Feeds](data-feeds.md#data-feeds), [Capability Verbs](capability-verbs.md#capability-verbs-1) and [Board Tool Surface](capability-verbs.md#board-tool-surface).
- `SessionManager`'s `data-tap` event and `ActivityStatsSnapshot.permissionAwaitedToolId`. The tap is not focus-gated, but since the PTYs moved to the pty host it flows only for a session someone subscribed to (`subscribeDataTap`, reference counted), which `read-stream.ts` does for each streamed session.
- The consolidated `BoardEventBus` (`IpcContext.boardEvents`).
- ~~Per-device capability-granting UI in the Mobile Devices settings tab (one toggle per verb, driven by `MOBILE_CAPABILITY_VERBS`).~~ Superseded: pairing now grants every verb (see [Full access on pair](pairing-and-roster.md#full-access-on-pair)) and the per-verb toggle UI was removed; the capability CHECK and `setDeviceCapabilities()` surface it depended on stay as the seam for a future narrower preset.
- **Protocol 0.2.0 (typed feed payloads):** wire mirrors + phone-side runtime guards for every feed/response payload that was `JsonValue` in 0.1.x (`packages/protocol/src/events/payloads.ts`, typed `events/event.ts` + `wire/payloads.ts`, `capabilities/board-tools.ts` tool-name tuples), the desktop `wire-mappers.ts` adoption, the subscribe-time transcript seed, and the live `permission` activity event. Wire-compatible with 0.1.x (`PROTOCOL_VERSION` unchanged): it types what was already sent, plus two additive emissions.
- Re-handshaking `BridgeSession` on a transport reconnect: every `'connected'` edge sends a fresh msg1, so a reconnect no longer waits out the ~2-minute rekey tick.

## Bridge Phase 3: session lifecycle honesty & E2E push

- Protocol: the `session-ended` activity payload and read-stream `sessionStatus`, the `register-push` verb + payloads, the E2E push envelope (`crypto/push-envelope.ts`), and optional project accent colors on the read-board payloads. All additive and wire-compatible (absent fields parse as before on older peers).
- Desktop: `SessionLifecycleBoardFeed` (lifecycle edges onto the board-changed bus), the read-stream `session-ended` push + `sessionStatus` snapshot field, the push stack described under [Push Notifications](push-notifications.md), and derived project accent colors in `read-board`.

## Protocol 0.8.0: what a session list actually costs

- Protocol: the read-stream subscribe `terminal` flag and the `message-preview` activity payload. Both additive and wire-compatible - absent means the previous behaviour, so an older phone and an older desktop each keep working against a newer peer.
- Desktop: `resolveTaskTranscript` revalidates a task by `fs.stat` before parsing any session, using file signatures recorded in the stitch memo itself (not read back from the file cache, which is a bounded LRU and goes empty on a busy board); `transcript-cache.ts`'s cap raised 16 -> 64 with a 192MB byte budget; `read-stream` honours `terminal: false` by attaching neither the `data-tap` nor the `pty-resize` listener and returning an empty `scrollback` instead of building a serialized frame; `message-preview.ts` derives the one line a phone's session list renders from the transcript the subscription already resolves. That helper has since moved to `src/main/agent/shared/message-preview.ts` and is no longer mobile-only: the board and Agent Monitor card trail call the same function, and the bridge reads it from the new path.
- Why: measured from a Pixel over a LOOPBACK relay, one Home-feed refresh touched 20 transcript files totalling 319MB (a `--resume` writes a NEW file replaying its parent's whole history, so one task resumed five times owned 267MB across five near-identical files), and individual `transcript-window` requests took 0.7 to 3.8 seconds - the SMALLEST response was the slowest, because the cost was finding the entries rather than sending them. Separately, `event:terminal` streamed continuously to a phone showing no terminal at all (~13MB/hour), because every subscription carried PTY bytes the phone discards by design at its own terminal boundary.

## Protocol 0.9.0: a board projection that matches what a phone draws

- Protocol: the read-board subscribe `view` field (`'full' | 'sessions'`), the `view` echo and `taskCountsByColumnId` on the snapshot response, and an optional `backlog`. Additive in both directions: a pre-0.9.0 phone sends no `view` and gets the old payload verbatim; a 0.9.0 phone against a pre-0.9.0 desktop gets a full board with no `view` echo, which is exactly how it knows the snapshot was not filtered.
- Desktop: `read-board` builds the backlog only for a request that named no `view`, filters `tasks` to session-bearing ones under `'sessions'`, and sends whole-column counts alongside, since a phone appending a card to a column cannot take the column's length from a filtered list.
- Why: measured across a 15-project desktop, the boards were 63kB compressed of a ~96kB cold start. 23kB of that was a backlog no phone build has ever rendered, and another 30kB was tasks with no session on them, which the Agents feed never draws. Worse, a board subscription re-snapshots on every board change, so the whole payload repeated for as long as the phone stayed connected: for the busiest project that is 17.7kB per change against 4.6kB for the projection. The `'sessions'` view is 12kB for the same 15 projects, and the Board tab upgrades the one project the user actually opens to `'full'`.

## Protocol 0.10.0: a phone can open a finished conversation

- Protocol: a read-board `archived` action returning one page of completed tasks, newest first, each carrying its lifetime session summary. Additive, so `PROTOCOL_VERSION` stays '2' and the handshake is unchanged.
- Desktop: `listArchivedPage` is a paging sibling of `listArchivedPreview` (the preview takes no offset, and `listArchived` loads the entire archive - the cost its own comment warns about - to serve one screenful); the summary is `getSummaryForTask`'s existing lifetime aggregate, so a task worked across five `--resume` legs reports all five session rows rather than under-reporting to the final leg, with `toolBreakdown` dropped at the wire mapper for want of a phone counterpart. (That aggregate later stopped summing each leg's running cost and runtime: it now reads each conversation's total once and adds the conversations, so the phone's numbers match the desktop's. The wire shape did not change.) `read-stream`'s `transcript-window` branch moves ABOVE the live-session gate rather than relaxing it, so every other action still demands a running session exactly as before, and resolving the owning project gains a database fallback because the session manager's lookup is backed by the live registry.
- Why: neither 0.9.0 projection carries a completed task, since both are built from the non-archived task list - a phone that only ever subscribed had no way to know the archive existed. The archive is an action rather than a snapshot field on purpose: a board subscription re-snapshots on every board change and the archive only grows, so folding it in would re-send an ever-larger payload for the life of the connection, the exact cost the 0.9.0 projections were added to remove. And because a task is archived only after its agent is suspended and its `session_id` nulled, the live-session gate made a finished conversation permanently unreadable, which is most of what a completed task is worth opening for.

## Protocol 0.11.0: the project list a phone draws is the one the desktop groups

- Protocol: `ReadBoardProjectGroup`, optional `groupId` / `position` on `ReadBoardProjectSummary`, and an optional `groups` array on the project-list response. Additive; `PROTOCOL_VERSION` stays '2'. A malformed group entry is dropped rather than failing the whole listing, since the projects are what the phone cannot work without and grouping degrades to the flat list it rendered before.
- Desktop: `read-board`'s project-list branch includes each project's `group_id` and `position` plus the group list itself. This needed no new plumbing - `ProjectGroupRepository` is already on `IpcContext`, and both fields are already columns on `projects`.
- Why: the phone's switcher was a flat list of every project on the machine, in no order the user recognizes, while the desktop sidebar had grouped them for some time - and that structure is exactly what a small screen needs most. An older phone ignores the new fields; a newer phone against an older desktop receives no groups, puts every project in the ungrouped bucket, and renders the same flat list it always did.

## Protocol 0.11.1: a relay address is parsed, not prefix-matched

- `isSecureRelayAddress` now parses the URL authority instead of prefix-matching it. `ws://127.0.0.1:8080@evil.test` previously returned true, because everything before an `@` in an authority is credentials: that address dials `evil.test`, and since the pairing token WAS the Noise PSK, dialed verbatim as the relay's `?slot=`, one crafted QR field put the PSK on the wire in cleartext to an attacker-chosen host, which `activePairing` then persisted as the trust anchor for every later session. (That particular exposure is closed as of 0.12.0 below, which derives the slot instead - but the address-pinning reason for this fix stands on its own, which is why the rule stays.) The loopback carve-out sits outside any dev gate, so this reached production builds.
- Parsing subsumes the old boundary check (`localhost.evil.com` is simply a different host, not a prefix needing a special case). The IPv6 branch REJECTS trailing garbage after the closing bracket rather than trimming to it: truncating reads `ws://[::1]evil.com` as the host `[::1]`, handing the carve-out to an attacker-controlled name - a narrower hole than the original, but the same kind. The module stays hand-rolled rather than using `new URL()` by contract: the renderer deep-imports it, so pulling in the rest of the package would drag Noise crypto into that bundle, and the mobile app runs the same rules on Hermes, whose URL implementation is partial.

## Protocol 0.12.0: the pairing slot is derived, and an unauthenticated frame cannot end a ceremony

- Protocol: `derivePairingSlotId(token)` (`crypto/slot.ts`), a labeled BLAKE2s hash giving a 16-byte pairing slot. **Breaking**, and the first `PROTOCOL_VERSION` bump since '2': the slot is a zero-negotiation rendezvous value, so peers deriving it differently never meet. Binding the version turns that into a `version-incompatible` result at QR-scan time, before anything dials, instead of a hang until the relay's park timeout. The version is also in the KK prologue, so every already-paired device must re-pair - acceptable only because mobile has not rolled out.
- Why: the 32-byte token was doing three jobs - the single-use pairing token, the Noise `IKpsk0` PSK, and (hex-encoded) the relay slot dialed as a cleartext `?slot=` query parameter. The third published the first two. On a hosted relay, whatever terminates TLS sees the full request URI, so `IKpsk0` degraded to plain `IK` for such an observer and the `psk0` contribution bought nothing against them. Deriving the slot keeps the routing label public and the PSK secret; the token now never leaves the QR. No relay change was needed - its default `SLOT_ID_PATTERN` already accepts a 32-hex slot.
- Desktop: `PairingService` no longer consumes the pairing token before authenticating. It builds a **fresh responder handshake per inbound frame** and commits it only once `readMessage` succeeds, because `readMessage` advances `messageIndex` and mixes the sender's ephemeral into the transcript *before* it authenticates, so a rejected frame would poison a shared `HandshakeState` even after the token survived. Rejected frames are ignored rather than ending the ceremony, in both `waiting-for-phone` and `sas-pending` (safe in the latter because `CipherState` advances its nonce only on a successful decrypt). Message 2 is now sent after every state transition is committed, closing a re-entrancy window that only opens once multiple frames can arrive in one phase, and its send is wrapped so a transport that throws (`RelayClient` rejects a send while not connected) fails the ceremony immediately rather than parking it for the whole SAS timeout.
- Why: the token was marked consumed on the *first frame received*, before any authentication. Since the slot id needed to deliver that frame was the token itself, travelling in cleartext in the relay URL, anyone who could read the request URI - or photograph the QR - could burn a ceremony deterministically with one frame and no key material. The user saw "pairing is broken," not an attack. Guessing stays bounded by the token's 10-minute TTL, the relay's per-IP rate limits, and its cap of two peers per slot; an attempt counter that aborted at N would only have turned a one-frame denial into an N-frame one.
- Residual, not fixed here: an attacker who learns the slot can still squat it (the relay caps a slot at two peers and answers the third with close code 4409), denying the pairing. No desktop change addresses that, and the derived slot makes the slot much harder to learn in the first place.
- Residual, not fixed here: a phone on an older `PROTOCOL_VERSION` that dials anyway is now indistinguishable from a hostile frame. Its message 1 fails `readMessage` on the prologue mismatch and is ignored rather than ending the ceremony, so the desktop sits in `waiting-for-phone` until the token's 10-minute TTL instead of surfacing an error immediately, as it did before. The QR-scan version check is what is meant to catch this, and it lives in the mobile app: there is no desktop-side oracle that could separate "wrong version" from "wrong token" pre-authentication without also handing an attacker a probe.
- Residual, not fixed here: `sas-pending` now accepts unbounded rejected confirm frames where it previously ended on the first, and `openPairingConfirm` runs its AEAD over the whole raw frame before any length check. `RelayClient` bounds only what it SENDS (`maxBytesPerSession`); its `onmessage` path has no size guard, and pairing frames never pass through `decodeMessage`'s `MAX_FRAME_LENGTH`. So an attacker who reaches the slot can spend main-process CPU proportional to frame size for the full 5-minute window. The bound belongs on the transport's receive path rather than in `PairingService`, which is why it is not fixed here.

## Protocol 0.13.0: task and column fields for the phone's board view

- Protocol: `pr_merge_readiness` on `BoardTaskWire` (`ready` / `blocked` / `conflicting` / `unknown` at 0.13.0, or null when the desktop has never judged the PR). Additive; `PROTOCOL_VERSION` stays '3'. An older desktop omits the field and `parseBoardTaskWire` reads that as null, so a newer phone renders the plain open chip it always did. The desktop has since widened the set to `ready` / `blocked` / `conflicting` / `queued` / `running` / `unknown` (`PR_MERGE_READINESS_VALUES` in `src/shared/types.ts`); the wire type stays `string | null` and is never validated against a list, so a value the phone does not know renders as plain open.
- Desktop: `wire-mappers.ts` copies `tasks.pr_merge_readiness` onto the board task, the same column the desktop's own PR pill folds into its state chip (see [PR connector model](../pull-requests/connector-model.md#merge-readiness)). No new verb and no new handler; the field rides every `read-board` snapshot and change event that already carried `pr_state`.
- The phone-side rendering is the mobile app's own change and is gated on this package publishing.

- Protocol: `BoardColumnWire.role` narrowed from a bare `string | null` to `'todo' | 'done' | (string & {}) | null` (`BoardColumnRoleWire`), plus exported `isTodoRole()` / `isDoneRole()` predicates and the `BOARD_COLUMN_ROLES` constant mirroring the desktop's `SWIMLANE_ROLES`. The `(string & {})` escape hatch keeps a future system role from failing to parse on an older client, but does NOT make a typo'd literal comparison a compile error by itself (a string literal is assignable to `string & {}`) - the predicates are what remove the literal from a call site, and are what a client should use instead of `role === 'todo'`.
- Protocol: `BoardColumnWire.spawns_session?: boolean | null` (optional field; `parseBoardColumnWire` always populates it from a real response). Whether moving a task into this column would spawn a successor agent session - INTENT, not a guarantee. `true` means the column intends to spawn, but a board profile, a failed worktree checkout, a shutdown, or a race with a newer move can still suspend the old session with no successor landing, so a client must keep whatever timeout already bounds its wait and use `true` only to skip a redundant one. `false` is only reliable enough to act on when the column's own `role` is 'todo' or 'done'. A profile cannot change a column's role, so those two really do skip the wait, and the phone can recognize them from the `role` on the same object via `isTodoRole` / `isDoneRole`. A `false` that came from `auto_spawn: false` on any other column is intent in the same way `true` is: `resolveColumnStrategy` lets a task's board profile set `autoSpawn: true` for that column, and the move then spawns. Absent (a desktop that predates the field) falls back to that same timeout, unconditionally.
- **Ordering precondition:** `spawns_session` is only consumable because the phone learns a move's destination column before the old session's `session-ended` arrives - true today because `handleTaskMove` emits its board-changed event at the commit point (see the comment above `emitBoardChanged()` in `task-move.ts`, landed by #628's "answer at commit, not settle" change), before the slow suspend/worktree/spawn work later in the same phase. A future change moving that announce to settle time would break this field silently.
- Desktop: `wire-mappers.ts`'s `columnSpawnsSession(swimlane)` derives the field from `auto_spawn` and the same `NEVER_AUTO_SPAWN_ROLES` set (`src/shared/types.ts`) that `auto-spawn-reconcile.ts` already used to gate the MCP `update_column` tool. `SWIMLANE_CREATE` / `UPDATE` / `DELETE` / `REORDER` (`src/main/ipc/handlers/board.ts`) now also emit a `swimlane-updated` board event on every user-driven column edit; previously only an agent/MCP column edit did, so a user toggling auto_spawn in the Board Manager left a paired phone's `spawns_session` stale until an unrelated board change happened to fire.
- Protocol: `pr_merge_readiness` was declared optional (`?: string | null`) after 0.13.0 shipped it required. Required forced every TS consumer that builds a `BoardTaskWire` object literal to list a field the parser already defaults, which broke the mobile repo's fixtures at six sites. `spawns_session` was declared optional from the start to not repeat that, and the two now match. Pure TypeScript surface: `parseBoardTaskWire` still reads an absent key as null and `toBoardTaskWire` still sets it, so no wire behavior moved and `PROTOCOL_VERSION` stays '3'. A client sees the change only once the package publishes; the required shape is on npm through 0.13.0.
- The phone-side rendering, `boardColumnFixture` update, and `isTodoRole`/`isDoneRole` call-site migration are the mobile app's own change, gated on this package publishing.

## Protocol 0.14.0: a respawn shows the phone "Switching", not "Ended"

- Protocol: `spawnProgressLabel?: string` on the `session-ended` activity payload. Additive; `PROTOCOL_VERSION` stays '3'. Presence means the desktop had a respawn in flight for this task when the session ended (a same-column respawn: model switch, agent switch, effort change, isolated-session-track switch) rather than a genuine park - what the desktop believed, not a fact about what happens next. `intentional` cannot carry that distinction on its own, because `SessionManager.suspend()` marks `status = 'suspended'` before the force-kill for every caller. INTENT, not a guarantee, on the same terms `spawns_session` documents: the desktop can suspend without a successor ever landing, so a client keeps whatever timeout already bounds its session-swap wait and uses the label only to skip a redundant one. The string is the desktop's own display text ("Switching model...", a live git-queue wait count) - untrusted display text, not a key to switch on. Absent from pre-0.14.0 desktops, and from any park that clears its label first.
- Desktop: `read-stream.ts`'s `onExit` reads the task's in-flight label via `getInFlightSpawnProgress()` (`src/main/transition-engine/spawn-progress.ts`) and attaches it when present. Ordering already works in its favor: `suspendLiveSessionForRespawn` (`task-move.ts`) emits the label as the first statement of a respawn, well before the `suspend()` that produces this exit; that file's own park branches clear it before suspending. The five parks that never clear a label (a manual pause, the idle-timeout suspend, the `kill_session` action, project-relocate, auto-spawn-reconcile - named in `docs/architecture/sessions/resume.md`) can still send a stale label on a genuine park until the 120s TTL sweeps it, which is what the INTENT-not-a-guarantee framing covers. No new verb, no new handler, no new IPC channel.
- Desktop (#682): the in-place restart `restartSessionForSettingsChange` (`session-reconcile.ts`) also emits before its suspend, through a required `phase`: `switching-model` / `applying-settings` for a ContextBar model pick or a Board Profile propagation, and `resending-command` ("Re-sending command...") for the auto_command escalation restart. That path emitted nothing before, so the phone showed "Session ended" for a swap that was guaranteed a successor. The label is cleared once the resume returns or fails, so it cannot ride a later genuine park's `session-ended`.
- The phone-side rendering (the session screen's swap-window latch, the switching overlay's label display) is the mobile app's own change and is gated on this package publishing.

## Protocol 0.15.0: a phone can start a session again without moving the task

- Protocol: `start-session` appended to `CAPABILITY_VERBS` (append only: the desktop mirrors the tuple by hand and pins it index for index), with `StartSessionRequestPayload` (`taskId` + `projectId`), `StartSessionResponsePayload` (`{ ok, outcome: 'starting' | 'live' }`), `StartSessionOutcome`, and the phone-side guard `parseStartSessionResponsePayload`. Additive; `PROTOCOL_VERSION` stays '3'. A pre-0.15.0 desktop rejects the verb at decode (`isCapabilityVerb`) and sends no response, so a phone times out rather than seeing a router error.
- Protocol: `UnsupportedVerbError` (thrown by `decodeMessage` for a well-formed capability-request whose verb this build does not know, carrying its `requestId` and `verb`), the `isUnsupportedVerbError` predicate (keyed on the error's name and fields, not `instanceof`, since the mobile app resolves the published dist), `UNSUPPORTED_VERB_ERROR_CODE`, and an optional `code?: CapabilityErrorCode` on `CapabilityResponseMessage`, validated by shape only so a code an older peer does not know cannot cost it the `error` text. Additive; `PROTOCOL_VERSION` stays '3'. This is what turns the silent drop above into an answer for every verb added AFTER this one; see [Capability Verbs](capability-verbs.md#capability-verbs-1).
- Desktop: a tenth handler file, `handlers/start-session.ts`, registered on the `CapabilityRouter`. It calls `startTaskSession` (`src/main/ipc/handlers/session-start.ts`), which routes through `autoSpawnForTask` -> `spawnAgent` with the new `explicitStart` option, so the column's enter automations run as they do on a move. (From 0.16.0 a paused task takes the desktop Resume button's path instead; see the 0.16.0 entry below.) The verb's full contract is the `start-session` bullet under [Capability Verbs](capability-verbs.md#capability-verbs-1). `DEFAULT_PAIRING_CAPABILITIES` spreads the tuple, so pairing grants the verb with no desktop change, and `migrateDevicesToFullCapabilityGrant()` re-grants every already-paired device on the next app launch.
- Desktop: `BridgeSession.refuseUnsupportedVerb` answers an `UnsupportedVerbError` from `decodeMessage` with `{ ok: false, error: 'Unsupported verb: <name>', code: 'unsupported-verb' }` and emits `unsupportedVerb` (logged by the service) instead of `frameRejected`; no router, capability check, or handler runs. `autoSpawnForTask` is split-locked and registers an abort controller on the resume registry, so a desktop Pause, Reset, or Resume cancels an in-flight Start's git phase and a Start no longer holds the task lock across its fetch (see the `start-session` bullet under [Capability Verbs](capability-verbs.md#capability-verbs-1)).
- The phone-side client method and its "Start again" action are the mobile app's own change, gated on this package publishing (a consumer pinned to `^0.14.0` does not resolve 0.15.0).

## Protocol 0.16.0: the card's in-between states reach the phone

- Protocol: `BoardTaskWire.spawn_progress?: string | null` (the card's preparing label with its staleness note, sanitized and capped at 120 characters), `ReadStreamResponsePayload.resuming?: boolean`, a `status` activity payload (`{ type: 'status', status, resuming, resumable }`), `successorSessionId?: string` on `session-ended`, and the `isReadStreamSessionStatusWire` guard. All additive; `PROTOCOL_VERSION` stays '3'. Each live signal is an activity payload TYPE rather than a new event KIND on purpose: `decodeMessage` checks only an activity event's ids, so an older phone decodes the frame and its `isBridgeEvent` drops the one event, where an unknown kind fails the whole decode. Precedence, as the desktop card applies it (`task-progress.ts`): a label overrides a `suspended` status, never `running` or `queued`, so a phone reading `status: suspended` during a model switch shows the label rather than "Paused".
- Desktop: `onSpawnProgressChange` in `spawn-progress.ts`; the bridge's `SpawnProgressFeed` and `read-board`'s label stamping and `'sessions'` projection rule (above); `read-stream`'s post-await snapshot read, live `status` push, and successor hop (see the `read-stream` paragraph under [Data Feeds](data-feeds.md#data-feeds)).
- Desktop: the Resume button's path (`SESSION_RESUME`, whose body is now `resumeTaskSession` in `handlers/session-resume.ts`) now labels its resume "Resuming session..." once it knows it will spawn, hands the git phase the same progress callback, and releases the label in one `finally`. The label is a `claimSpawnProgress` claim, so the release clears it only while no other path has labelled the task since: a phone Start runs alongside a desktop resume without aborting it, and a newer resume labels the task before the one it aborted unwinds. The protection runs one way. The phone Start, like every other spawn path, still clears unconditionally, so if it finishes first the resume's card reads "Paused" for the rest of its git phase, as it did before 0.16.0. Before, it ran its worktree and git work with no label, so both the desktop card and a phone read "Paused" through it, and the successor hop's `session-ended` arrived unlabelled. A phone that predates 0.16.0 treats an unlabelled end as a stop (8 s row retention) and a labelled one as a respawn (20 s, with the starting glyph), so the label is what makes a desktop Resume read as a swap there.
- Protocol and desktop: `BoardTaskWire.resumable?: boolean | null`, the field a phone gates Resume on, plus copies on the read-stream snapshot (`resumable?: boolean`) and the `status` payload (always sent there) for an open session screen. The `'sessions'` projection keeps a resumable paused task, whose `session_id` a desktop pause has nulled, so an agent feed can draw a lasting Paused card with Resume. `start-session` on a PAUSED task now runs `resumeTaskSession` (`handlers/session-resume.ts`), the body the `SESSION_RESUME` handler moved into so the two cannot drift, instead of `autoSpawnForTask`: no enter automations, no column message, the "Resuming session..." label, and the successor hop a desktop Resume produces. A task with no session or an exited one still starts the column. `resumable` is the explicit signal that this desktop resumes rather than starts, because a 0.15.0 desktop starts the column for every `start-session`, which re-runs its enter automations and resends its message.
- Why: the mobile app ports the board card's footer 1:1, and three of its inputs never reached the phone. The preparing label appeared only on `session-ended`, and not at all for a first start. `resuming` was not on the wire. `sessionStatus` was sent once at subscribe, so a session queued, paused, or promoted while the phone watched never updated. And the `'sessions'` projection dropped a task the moment a respawn nulled its `session_id`, which is exactly the gap a label describes. The phone's Resume control then needed `start-session` to resume a paused task the way the desktop does, and a field that says when it will.
- The phone-side rendering (preparing label, "Resuming agent...", live Queued and Paused, the successor hop, and a Resume gated on `resumable`) is the mobile app's own change, gated on this package publishing.

## Protocol 0.17.0: the paused fact reaches the phone apart from the Resume gate

- Protocol: `BoardTaskWire.paused?: boolean | null`, parsed with `nullableBoolean` like `resumable`. Additive; `PROTOCOL_VERSION` stays '3'. Null or absent means a pre-0.17.0 desktop, which a phone treats as unknown and reads a paused task from `resumable` alone, as before.
- Desktop: `read-board` stamps `paused` from the `pausedTaskIdsOf` scan it already ran for `resumable` (a `suspended`, non-transient row and no live one), with no column or archive gate, and hands `toBoardTaskWire` both flags as one object so a call site cannot swap them. A queued successor (`[suspended, queued]`) reads false, as the desktop card shows the queued session there. `spawn_progress` still overrides it, as it does `resumable`.
- `'sessions'` is unchanged on purpose. It keeps a resumable paused task and leaves out one that offers no Resume, even though that row now reads `paused: true`, because an agent feed has nothing to act on for it.
- Why: `resumable` is the Resume gate, so a paused task in Done or on the archived page read `resumable: false`, and since a pause nulls `session_id` the phone had no other way to know a suspended session existed. The desktop's full card reads "Paused" from the session row, not from the gate, so a paused task sitting in Done unarchived showed Paused where the phone showed nothing. An archived task gets the compact card, which has no footer.
- To Do is not one of those cases. A move into a todo-role column removes the task's session rows (`task-move.ts` calls `cleanupTaskResources`, which runs `cleanupTaskSession` -> `removeByTaskId`), so a task paused before that move reads `paused: false`, which matches the desktop card. Only a leftover row would read true there.
- The phone-side "Paused" footer for `paused === true` on an unarchived row with no live session and no label, without a Resume, is the mobile app's own change, gated on this package publishing.

## Protocol 0.18.0: a phone can pause a running session

- Protocol: `pause-session` appended to `CAPABILITY_VERBS` after `start-session` (append only), with `PauseSessionRequestPayload` (`taskId` + `projectId`), `PauseSessionResponsePayload` (`{ ok }`), and the phone-side guard `parsePauseSessionResponsePayload`. `BoardTaskWire.pausable?: boolean | null`, parsed with `nullableBoolean`. Additive; `PROTOCOL_VERSION` stays '3'. Null or absent means a pre-0.18.0 desktop, and a phone offers no Pause then.
- Desktop: an eleventh handler file, `handlers/pause-session.ts`. The `SESSION_SUSPEND` body moved into `pauseTaskSession` (`handlers/session-pause.ts`), which both callers run, as the Resume button's body moved into `resumeTaskSession` for `start-session`. It gained an `onAccepted` hook (fired after the DB writes, before the PTY shutdown) and an outcome (`paused` / `not-live`); the desktop handler ignores the outcome and stays a silent no-op on a task with no live session. The verb's full contract is the `pause-session` bullet under [Capability Verbs](capability-verbs.md#capability-verbs-1).
- Desktop: `read-board` stamps `pausable` from `taskSessionStatesOf` and `isPauseOffered` (`src/shared/session-resume-eligibility.ts`); see the `read-board` paragraph under [Data Feeds](data-feeds.md#data-feeds). No new event wiring: a pause, a session's start and its end already reach the phone through `SessionLifecycleBoardFeed`.
- Desktop: `move-task`, `start-session` and `pause-session` now refuse a `projectId` the desktop does not know (`handlers/known-project.ts`), as `read-board` and `read-diff` already did; those two now run the same function instead of their own inline check. Before, `resolveProjectContext` passed any non-empty id through and `getProjectDb` created and migrated a database named after it, so a phone still showing a deleted project recreated that project's database, and an id carrying a path segment reached a file outside the projects directory.
- Desktop: turning a column's auto-spawn off reconciles each task's session pointer before suspending it, as a manual pause does, so an agent that exited by itself is no longer marked paused with a Resume on its card.
- Grants: `DEFAULT_PAIRING_CAPABILITIES` spreads the tuple, and `migrateDevicesToFullCapabilityGrant()` re-grants every already-paired device on the next app launch, the same path `start-session` took. There is no per-verb toggle to add it to (removed with the full-access-on-pair change). Pause adds nothing a paired phone could not already do: `move-task` to Done suspends the session too, and archives the task.
- Why: a phone could Resume a paused task (0.16.0) and see the paused state (0.17.0), but had no way to pause one. Its long-press hub on a running task offered Move, Edit, Archive and Delete, and no Pause.
- The phone-side Pause action, gated on `pausable`, is the mobile app's own change, gated on this package publishing.

## Protocol 0.20.0: Command Terminals on the phone

- Protocol: `command-terminal` appended to `CAPABILITY_VERBS` as the 13th verb (append only), with `CommandTerminalRequestPayload` (`start` with `projectId`, or `stop` with `sessionId`), `CommandTerminalStartResponsePayload` (`{ ok, sessionId, slot, name }`), `CommandTerminalStopResponsePayload`, and the phone-side guard `parseCommandTerminalStartResponsePayload`. `CapabilityErrorCode` gains `unknown-project`, `unknown-session`, `command-terminal-limit`, `not-command-terminal`, `agent-unavailable` and `command-terminal-start-failed`, each with an exported constant. `ReadBoardSnapshotResponsePayload` gains `commandTerminals` (`CommandTerminalWire[]`) and `commandTerminalsOffered`, `BoardEventPayload.change` gains `command-terminals-changed`, `PushEnvelopePlaintext` gains `sessionKind` (`PUSH_SESSION_KINDS`), `ReadDiffRequestPayload.taskId` becomes optional for a project-folder diff, and `DiffEvent` names exactly one of `taskId` and `projectId`. All additive on the wire; `PROTOCOL_VERSION` stays '3'. `DiffEvent.taskId` turning optional is a TypeScript change a consumer sees at its pin bump.
- Desktop: the `SESSION_SPAWN_TRANSIENT` body became `startCommandTerminal`, shared with the new `handlers/command-terminal.ts`. Main owns the cap and the slot allocation, which used to be the renderer's (it counted windows, so a phone start and a desktop New could collide on a slot). Stop and the IPC kill go through `SessionManager.endCommandTerminal`, which refuses a task's session; the IPC kill used to end any id.
- Desktop (C2): a Command Terminal ends when its agent exits, on the desktop too. The agent-absence sweep judges Command Terminals and ends one rather than keeping an exited row; a SessionEnd hook waives the spawn grace and asks the sweep to look at once (`BgShellWatcher.requestAgentAbsenceCheck`); a terminal whose PTY exits on its own ends as well. Its window closes the way Stop closes it, through a removal subscriber in the command layer (`useCloseCommandWindowOnRemoval`). Before, a terminal whose agent exited lingered as a bare shell at the project root, which `interactive-terminal` could have typed into.
- Desktop: a terminal is named in main (`CommandTerminalNamer`) from its first prompt, by its own agent in its own project folder, sharing the summarize rate limit with `AGENT_SUMMARIZE`. It used to be named in the renderer, by the open project's default agent, so a terminal a phone started, or one in a project not open on the desktop, never got a name. The Agent Monitor row now shows the name too. `session:setTransientLabel` is gone. Naming needs the prompt's text on the agent's prompt event, which a Command Terminal now asks Claude Code for (`capturePromptText`, per session) and Kimi always sends; on Claude it had never worked, because its prompt hook carried no text. A Gemini or Qwen Code terminal keeps "Command Terminal N", so a phone sees `named: false` there.
- Desktop: the session lifecycle feed stops sending `task-updated` for a terminal's made-up task id, and terminal push alerts carry the name and `sessionKind`.
- Why: the phone's Board header gets a Terminals button and its Agents feed lists terminals beside task agents. The approved design keeps the phone to the default branch with no branch, model or effort control, and grants the verb on pair like the rest.
- The phone-side Terminals button, sheet, session screen and notification routing are the mobile app's own change, gated on this package publishing.

## Protocol 0.21.0: workflows, linked tasks that run through their boards by themselves

- Protocol: `BoardTaskWire.workflow?: BoardTaskWorkflowWire | null`, the task's workflow as its card draws it: `id`, `title`, the home `project_id` (which may not be the board's), `state` (`running` / `paused` / `draft` / `done`; an unknown value reads as running), `color_slot` (1 to 6, the desktop's categorical chart color), `route` (the column ids it visits, in board order), `waiting_for` (the unfinished tasks it waits for, named as the card's footer names them, "#413"), `lock_reason` (while only its workflow may move the card, the desktop's own sentence for a refused move; null when a hand may move it), and `gate_target_id` (while a running workflow's task waits in a column no agent can judge, the one column a hand may move it to, which is how the person reports the step done). The two never both hold: a gated card is not locked, as on the desktop board, where a locked card drags only within its own column (`isLockedOnBoard`), but it moves only to `gate_target_id`. No card moves into To Do. A card whose own automations are paused (`BoardTaskWire.automations_disabled`) is neither locked nor gated: a hand may move it to any column but To Do, and its `lock_reason` reads null. `automations_pausable` (protocol 0.25.0) is `true` on a desktop that honours that switch on a workflow task, and null or absent on an older one, which refuses `automationsDisabled: true` there, so a phone shows the control only while it is true. Optional, as `pr_merge_readiness` is: `parseBoardTaskWire` reads an absent or malformed value as null (`parseBoardTaskWorkflowWire`), so an older desktop and a broken workflow both cost the card its strip, never the board. Additive; `PROTOCOL_VERSION` stays '3'.
- Protocol: `list_workflows` and `get_workflow` join `BOARD_TOOL_READ_NAMES`, and `pause_workflow` and `resume_workflow` join `BOARD_TOOL_WRITE_NAMES` (see [Board Tool Surface](capability-verbs.md#board-tool-surface) for the workflow tools left off).
- Protocol: `workflow-complete` appended to `PUSH_CATEGORIES` (see [Push Notifications](push-notifications.md)).
- Desktop: `read-board` computes each board's workflow facts once per snapshot (`handlers/workflow-wire.ts`) from the same summaries the desktop board draws its cards from, so the phone's lock and footer cannot disagree with the desktop's. A board with no workflow task reads nothing extra. `move-task` refuses a locked card before it commits and `start-session` refuses a paused workflow's task, both with the desktop's sentence (see [Capability Verbs](capability-verbs.md#capability-verbs-1)). A later desktop change dropped the `start-session` refusal: a person may start one task of a paused workflow, and the workflow stays paused.
- The phone-side rendering (the strip and lock on its cards, explaining or hiding the moves the lock refuses, the Pause and Resume actions, the push's channel) is the mobile app's own change.

## Built, awaiting the next protocol release: a completed task's full report

- Protocol: `get_task_report` joins `BOARD_TOOL_READ_NAMES`. Its result type is `TaskReportWire` (`capabilities/task-report.ts`), with the phone-side guard `parseTaskReportWire`: the route (each working column's total time and stays, with `visitCount`), the span (`startedAt`, `endedAt`), the linked commits with `commitCount`, the per-file changes from git (`DiffFileWire` entries with `fileCount`, and `totals` only when one range holds the whole change), `changesError` when git could not be read, and the summary state. Additive; `PROTOCOL_VERSION` stays '3'.
- Desktop: `handlers/board-tool.ts` needs no change. The new `commandHandlers` entry (`src/main/agent/commands/task-report-commands.ts`) calls the completed task view's own reads through two `CommandContext` callbacks, so the phone and the desktop view show the same route, span and files. Agents read it as `kangentic_get_task_report`. The files, commits and stays are capped (200, 100 and 50 per column) and carry their counts; the Usage tab's ledger is left out.
- Why: `find_task` gives a phone the summary, three commits and eight file paths. The desktop's completed view also shows the route, each file's status and lines, and every commit, and its span comes from the task's moves, which a phone could only approximate from session rows.
- Rendering the Route and the per-file lines in the phone's completed Summary is the mobile app's own change, gated on this package publishing.

## Built, awaiting the next protocol release: a paused task's session id

- Protocol: `BoardTaskWire.paused_session_id?: string | null`, parsed with `nullableString`. It is the id of the task's paused session while `paused` is true, and null otherwise. `SendUserMessageRequestPayload.sessionId`'s doc names it as the id to send to for a paused task. Additive; `PROTOCOL_VERSION` stays '3'. Null or absent also means a pre-0.27.0 desktop.
- Desktop: `taskSessionStatesOf` returns `pausedSessionIdByTaskId` in place of its paused set, from the same loop, and `pausedTaskIdsOf` reads the paused tasks from its keys. A task with two paused rows maps to the later one. `read-board` reads the id from it and `toBoardTaskWire` derives `paused` from the id, so the two cannot disagree. The `'sessions'` projection is unchanged. No new event wiring: a restart's `registerSuspendedPlaceholder` emits `session-changed`, which already reaches the phone as `task-updated` through `SessionLifecycleBoardFeed`.
- `session_id` keeps its meaning and stays null while paused, because phones read it to detect a resume binding to a new session.
- Why: 0.26.0 made `send-user-message` hold a message for a session with no running agent, keyed by the session the phone names. A desktop pause clears `session_id`, and a restart re-registers the paused session under a fresh registry id that no board row, DB record or session list carried, so a phone opening a paused task fresh had no id to name, and one it remembered from before the restart answered `unknown-session`. Only a screen open through the pause, an idle-timeout suspend (its row keeps `session_id`) or a queued session could hold chat.
- Sending chat to any paused task from the phone's composer is the mobile app's own change, gated on this package publishing.
