# Azure DevOps connector

`src/main/pr/adapters/azure-devops/azure-devops-connector.ts`

`azureDevOpsPRConnector` resolves PRs through the `az` CLI (the `azure-devops` extension, plus two `az rest` calls: `pullrequestquery` for the commit tier and, for a PR whose preview merge succeeded, the policy evaluations) and reuses the board importer's `az` client (`AzureDevOpsImporter` from `boards/adapters/azure-devops/client.ts`), exactly as the GitHub connector reuses `GitHubImporter`.

**Ownership and the self-gate.** `azure-remote.ts` parses an Azure git remote into `{ org, project, repo }`, covering the SSH `v3/{org}/{project}/{repo}` form (with `%20` in the project name), `ssh://...:22/v3/...`, `https://dev.azure.com/{org}/{project}/_git/{repo}`, the `{user}@dev.azure.com` variant (the org comes from the PATH, never the userinfo), and legacy `{org}.visualstudio.com` including `DefaultCollection`. A `null` parse is the connector's own provider gate: every resolver returns `null` rather than throwing on a non-Azure remote. That is independent of the registry gate and load-bearing on its own - a throw here would set `degradeStatus` for every GitHub task on any machine without `az`, permanently disabling the confident-not-found clear and reporting a resolver failure for tasks that simply have no PR.

**Detection.** `extract` matches `https://dev.azure.com/{org}/{project}/_git/{repo}/pullrequest/{id}` and the legacy `visualstudio.com` spelling, over a 4096-byte tail window. `_git` is required, so a board or `_workitems` URL never matches, and the `/pullrequestcreate` compose page does not either. It uses the shared `stripAnsiControlCodes` (`src/shared/ansi-strip.ts`), deliberately NOT `stripAnsiEscapes`, whose whitespace normalization can join two lines and fuse a URL to its neighbour.

**Resolution.** All three tiers pass an explicit organization / project / repository plus `--detect false` rather than letting `az` sniff the cwd, so they work from any working directory - including after a task's worktree has been reclaimed.

- `resolveForBranch` and `resolveByNumber` use `az repos pr list --source-branch` and `az repos pr show --id`.
- `resolveByCommit` posts to `_apis/git/repositories/{repo}/pullrequestquery` via `az rest`, because no `az repos pr` verb answers "which PR contains this commit". The repository resolves by NAME; no GUID lookup is needed.
- The browser URL is CONSTRUCTED, not read: Azure returns null for `_links.web.href`, `remoteUrl`, AND `repository.webUrl` on every tier.
- `updatedAt` is `closedDate ?? creationDate`, because Azure exposes no `updatedAt` anywhere. This only breaks ties WITHIN a state bucket, since `disambiguate` scores state first.
- `disambiguate` is ported from the GitHub connector unchanged, INCLUDING the rule that keeps a LONE candidate whose head ref does not match `branchHint` (see the `disambiguate` bullet in [GitHub connector](github.md)). That half is what links a task whose stored branch is a worktree slug rather than the PR's real source branch, which is the common shape once a worktree has been reclaimed. A port that required a hint match would leave such a task blank forever. The only change is the score gate: Azure's `active` covers open and draft, where GitHub's `OPEN` does.
- State maps `completed` to `merged`, `abandoned` to `closed`, and otherwise `isDraft` to `draft` or `open`.
- Merge readiness starts from `mergeStatus` (Azure's `PullRequestAsyncStatus`, projected as `merge:mergeStatus` on the branch and number tiers): `conflicts` is `conflicting`, `rejectedByPolicy` / `failure` are `blocked`, `queued` / `notSet` / null / anything unrecognized are `unknown`, and `succeeded` is decided by the branch policies. `succeeded` on its own cannot claim `ready`: it says the preview merge applied cleanly, and reviewer minimums, required builds, and work-item linking are policies the merge preview never evaluates. The commit tier's projection (`AZ_PR_FIELDS_NO_FORK`) omits `mergeStatus`, since `pullrequestquery` matches completed PRs only, so those items omit the verdict.
- **Branch-policy evaluation** (always on; see [`PRResolveOptions`](connector-model.md#prresolveoptions) for why it is no longer a setting). An active, non-draft PR whose preview merge `succeeded` costs a second call, `AzureDevOpsImporter.resolvePolicyEvaluations`: `GET {org}/{projectGuid}/_apis/policy/evaluations` through `az rest`, with `artifactId=vstfs:///CodeReview/CodeReviewId/{projectGuid}/{prId}` and `api-version=7.0-preview.1` on `--url-parameters` (never in the URL: `execAz` runs through `cmd.exe /c` on Windows, where `&` splits the command). The API rejects `api-version=7.0` (`VssInvalidPreviewVersionException`), so that version is pinned on its own. The project GUID comes off the PR row itself (`projectId:repository.project.id` in `AZ_PR_FIELDS`; the git remote carries only the project name), and it also serves as the URL's project segment, so nothing is encoded. The call is skipped wherever its answer cannot change the verdict: a draft (the chip never renders readiness there), a completed or abandoned PR, any `mergeStatus` other than `succeeded`, and a missing GUID. On the branch tier it runs for the ONE candidate `disambiguate` picked, inside the same `AZ_CONCURRENCY` slot as the row fetch (never a nested slot, which could deadlock two overlapping resolves). Cost: roughly 1 to 1.8 s of `az` cold start per open PR per check. The refresh queue runs one check at a time, so that lengthens a check rather than raising the call rate; the on-open sweep over twenty linked PRs takes about 20 s longer. Tier 6 can pay twice in one resolve when two remote branches share the task's tip.
- The fold (`foldPolicyEvaluations`) counts blocking, enabled, live policies only. Any `rejected` or `broken` is `blocked` (a broken blocking policy disables Complete just as a rejection does); else a non-reviewer evaluation still `running` is `running`, else still `queued` is `queued`, EVEN IF a reviewer policy is also waiting; else a reviewer policy (the "Minimum number of reviewers" and "Required reviewers" types, matched by their fixed type ids, which report `queued` while approvals are outstanding) still waiting is `blocked`; else `ready` (every blocking policy `approved` / `notApplicable`, or none at all). An unrecognized status is `unknown`. `resolvePolicyEvaluations` returns `[]` for a PR with no policy evaluations (nothing blocks it, so `ready`) and `null` when Azure gave no readable answer (`unknown`), and the two are deliberately distinct.
- **A policy-fetch failure is contained, never a degrade.** `resolvePolicyEvaluations` returns `null` on every failure (a missing artifact, a rejected API version, a permission or transport error, unreadable stdout) and logs once per distinct message. It never throws `AzUnavailableError` / `AzTransientError`: a throw from the second call would fail the whole resolve, the ladder remembers a degrade and rethrows it once no tier resolves, and a persistently forbidden policy API (HTTP 403 classifies as transient) would then freeze the task's `pr_state`, so a merged PR would never show merged. A blank readiness chip is the smaller loss, and the linker's hold covers the resulting `unknown`. The residual is that the once-per-message `console.warn` is the only signal that the policy call is failing.
- Concurrency is capped at `AZ_CONCURRENCY = 2`, lower than GitHub's 3: `az` is a Python CLI with a roughly one-second cold start where `gh` is a Go binary that starts in milliseconds.
- Two argument guards mirror `isShaContainedInRef`'s option-shaped-ref rejection: an empty or `-`-leading branch name and a non-hex SHA are both refused without running `az`. The SHA guard is also the injection guard for the JSON request body.

**LIMITATION - the commit tier sees completed PRs only.** Azure records a PR's commit associations at completion, so `pullrequestquery` returns nothing for an active or abandoned PR (verified against eight real PRs). Consequences:

- A task with an ACTIVE Azure PR whose stored branch is not the PR's source branch gets nothing from the commit tier. Tier 2 needs the live worktree branch to BE the PR's source branch, Tier 4 needs the stored branch to match, and Tier 3 cannot see the PR at all. This is a property of the Azure API rather than of this code. An earlier version of this note called the gap narrow "because active PRs normally still have a live worktree", which was wrong twice: a live worktree only rescues Tier 2 when the live branch is the PR's source branch, and a task reaches Done with an open PR routinely, since `deleteTaskWorktree` nulls `worktree_path` on that move while `isEligibleForRefresh` keeps sweeping it. Tiers 5 and 6 now cover most of the gap, because they resolve BY BRANCH, which Azure supports.
- It is also why the GitHub connector's two commit-tier filters have no Azure counterpart. `gh api commits/<sha>/pulls` returns every PR whose head branch CONTAINS the commit, including a sibling that merely branched off the same base tip; Azure's query matches only a PR's own source commits. Probed against a merge product and against a base tip it returns nothing, and an open sibling can never appear at all. Both filters would be dead weight, so neither is ported.

**Fork guard, wired but unverified in the positive direction.** `isCrossRepository` is derived from `forkSource`, which is present on the branch and number tiers only; the commit-tier payload has no such field, so those candidates stay `undefined` and pass the falsy filter exactly as GitHub's optional field does. `forkSource: null` on non-fork PRs is confirmed; that a real fork PR populates it is not (no fork PR was available to test). If it does not, the failure mode is "no filtering", identical to having no guard, never a wrong rejection.
