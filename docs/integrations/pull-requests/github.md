# GitHub connector

`src/main/pr/adapters/github/github-connector.ts`

`gitHubPRConnector` resolves PRs through the `gh` CLI and detects PR URLs from terminal output. It reuses the board importer's `gh` client (`GitHubImporter` from `boards/adapters/github-common/gh-client.ts`) so binary detection and auth plumbing are shared; a module-level singleton avoids re-probing `gh` per call.

**Detection.** `extract` strips ANSI escape sequences from the tail of scrollback (a 4096-byte scan window) and matches `https://github.com/<owner>/<repo>/pull/<number>`, returning the last (most recent) match. It handles `gh pr create` stdout, `gh pr view` TTY and non-TTY output, and `gh pr view --json`. It deliberately does not match `git push`'s `/pull/new/<branch>` output (no numeric id) or `gh pr merge`'s `owner/repo#123` short form (no full URL). Detection runs against terminal scrollback only: there is deliberately no scraper for authored text such as a task description (see [The confidence ladder](pr-linking.md#the-confidence-ladder)).

**Resolution.** The three resolve methods call the shared `gh` client (`resolvePRByBranch`, `resolvePRByNumber`, `resolvePRByCommit`) and normalize the result. `resolveByCommit` additionally reads local git (see its two filters below); the other two are pure `gh`.

- `mapState` maps GitHub's `OPEN` / `CLOSED` / `MERGED` plus `isDraft` to the normalized `PRState`.
- `mapMergeReadiness` folds `mergeStateStatus` (falling back to `mergeable` when it is absent or unrecognized) and `reviewDecision` into `PRMergeReadiness`: `CLEAN` / `HAS_HOOKS` / `UNSTABLE` are `ready` (the Merge button works with failing non-required checks; required ones report `BLOCKED`), `BEHIND` / `DRAFT` are `blocked` (`BEHIND` before the bypass fold below, which can raise it to `ready`), `DIRTY` is `conflicting`, `UNKNOWN` is `unknown`, and a `ready` verdict downgrades to `blocked` only when `reviewDecision` is `REVIEW_REQUIRED` (compared against that one value, since `gh` renders a null decision as an empty string). `CHANGES_REQUESTED` is deliberately not a downgrade: where reviews are required GitHub already reports `BLOCKED`, and where they are not the Merge button works, so the literal promise says `ready`.
- `BLOCKED` is the one state the triple cannot split: a required check still running, a required check that failed, and a review still required all report it. `BEHIND` takes the same branch, because GitHub reports it INSTEAD of `BLOCKED` once the base moves under an otherwise identical PR (see the bypass fold below). `classifyRollup` reads `statusCheckRollup` into one of five classes, highest precedence first: `failed` when ANY check has failed (`FAILURE` / `TIMED_OUT` / `CANCELLED` / `ACTION_REQUIRED` / `STARTUP_FAILURE`, or a status context `ERROR` / `FAILURE`), whatever else is running; `running` when any check run is `IN_PROGRESS`; `queued` when the only unfinished ones are waiting to start (`QUEUED` / `PENDING` / `WAITING` / `REQUESTED`, or a status context `PENDING` / `EXPECTED`); `passing` when the rollup is non-empty and every entry settled green (`SUCCESS` / `NEUTRAL` / `SKIPPED`, or a status context `SUCCESS`); and `inconclusive` for an absent or empty rollup, a `STALE` or null conclusion, or a status, state, or typename this code does not know. A `BLOCKED` or `BEHIND` PR shows `running` / `queued` as its verdict and `blocked` for every other class, except a required check missing from the rollup and the bypass fold, both below. An in-flight check wins over `REVIEW_REQUIRED` on purpose (see [Merge readiness](connector-model.md#merge-readiness)). This is a heuristic, because `gh` carries no `isRequired` on the rollup: a `BLOCKED` PR whose only unfinished checks are optional reads `running` too, which corrects itself on the next resolve. Observed live on a review-required repository: `BLOCKED` + `REVIEW_REQUIRED` + every check `COMPLETED` / `SUCCESS` reads `blocked` for a viewer with no bypass.
- **A required check not in the rollup yet reads `queued`.** A required check GitHub still expects but that has not reported is absent from the rollup entirely. That is how every PR here looks for its first minute or two: the CLA workflow is green in seconds, CI's workflow has not created its runs yet, and GitHub reports `BLOCKED`. Read as `blocked`, the card showed that for up to a refresh interval (PR #479 read `merge blocked` from 14:59:05 to 15:00:44 while CI was starting). `blocked` is not an in-flight verdict, so it never started the linker's 30 s re-poll either, and a CI run shorter than one refresh interval left the card up to a whole interval behind. So on a `BLOCKED` / `BEHIND` PR whose rollup is `passing` or `inconclusive`, `requiredContextMissing` compares the rollup's names (any state) against the base branch's required contexts, and a missing one reads `queued`. A failed check still reads `blocked`. The join is by name, which is the join GitHub makes itself, so a context missing here is one GitHub also shows as "Expected, waiting for status to be reported". A required check that never reports (a path-filtered workflow, a check only a merge queue runs) therefore reads `queued` for as long as GitHub waits on it. The linker's 30 min re-poll budget bounds the cost per streak, and a project switch or config change starts a new streak (see "In-flight verdicts re-poll" in [Persist and degrade behavior](refresh-and-scheduler.md#persist-and-degrade-behavior)).

  The list comes from `resolveRequiredStatusChecks` in `gh-client.ts`: one `gh api graphql` reading `ref(qualifiedName: "refs/heads/<base>").branchProtectionRule.requiredStatusCheckContexts`, the same field the bypass probe reads off `baseRef`, and per BRANCH rather than per PR. The connector caches it per repo URL and base branch for 10 minutes (`REQUIRED_CHECKS_TTL_MS`, 32 entries, oldest evicted). One read serves every PR on that base, including a task's worktree and the main checkout. A failed read is not cached and keeps GitHub's `blocked`. A branch with no classic protection, a repo on rulesets, and a missing ref all answer `branchProtectionRule: null` or `ref: null` (measured), which reads as "no rule": such a repo keeps the old `blocked` until CI reports. The read is gated like the bypass probe (`needsRequiredChecks`): an open, non-draft PR, `BLOCKED` or `BEHIND`, and a rollup that has not already answered. It runs inside the caller's `ghQueue` slot.
- **The viewer's merge bypass** (`git.prBypassCountsAsReady`, default on, forwarded as `PRResolveOptions.bypassCountsAsReady`). When on, a PR still waiting on a required review costs a second call, `resolveMergeBypass` in `gh-client.ts` (`gh api graphql`, with gh's `{owner}` / `{repo}` placeholders filled from the repo at `cwd`), and the answer folds the verdict to `ready` at both sites where protection alone blocks: the `isBypassClearableMergeState` branch and the `ready` + `REVIEW_REQUIRED` downgrade. The gate (`needsBypassProbe`, mirroring Azure's `needsPolicyEvaluation`) is what bounds the cost: the PR must be open and not a draft, `reviewDecision` must be `REVIEW_REQUIRED`, the merge state must be one the bypass clears (`BLOCKED` or `BEHIND`, or a `ready` state), and the rollup must be `passing`. So a failed, in-flight, absent, or inconclusive rollup never probes and never folds (the bypass is a capability that reads `true` on a red PR too), a green PR with its review approved stays `blocked` (something the setting does not name blocks it: unresolved conversations, a merge queue), and `DRAFT` and `DIRTY` never fold.

  `BEHIND` folds alongside `BLOCKED` because they are one condition wearing two names. GitHub reports a single `mergeStateStatus` for a PR that is behind AND review-blocked, and which one it names is decided by whether a sibling PR landed: where the base requires branches to be up to date, a green review-required PR reads `BLOCKED` until one does and `BEHIND` immediately after. Excluding `BEHIND` therefore flipped the chip from `ready` to `blocked` because somebody else merged, with nothing about the PR itself changing. The three conditions the fold actually tests (`REVIEW_REQUIRED`, a `passing` rollup, every required context reported) are computable for `BEHIND` exactly as for `BLOCKED`, and `gh pr merge --admin --rebase` (what the Merge column runs) replays the head commits onto the current base tip, so the merge that the chip promises also resolves the staleness. What it does not do is re-test against the new base, which is what strict status checks exist for; that is a property of the Merge command, not of a chip whose promise is that the click succeeds. There is deliberately no "does the base require up-to-date branches" condition on the fold: GitHub only reports `BEHIND` where it does, so the condition would be a no-op, the field is not on the probe's wire, and where protection somehow did not require it, being behind would not block the merge at all.

  Cost: the probe is uncached, so admitting `BEHIND` means one `gh api graphql` per qualifying linked PR per check (about every 2 minutes per PR with `git.prAutoRefresh` on; the 60 s `RESOLVE_TTL_MS` coalesce is shorter than that, so it does not lower the rate). That is not a new population, it is the same PRs probing continuously instead of dropping out of the gate each time a sibling lands. If the rate ever matters, the probe could take its required list from the per-base cache the `queued` rule already keeps (`requiredChecksByBase`) and ask only for `viewerCanMergeAsAdmin`, which is per-PR and would still cost a call. The probe runs inside the caller's `ghQueue` slot, never through a nested `add`, for the same deadlock reason as Azure's policy call. Every probe failure is contained as `null` in the client (warned once per distinct cause) and leaves the verdict `blocked`; it never throws past the resolve.

  The probe asks for two things, not one, because a `passing` rollup is "nothing here failed", not "everything required ran": GitHub creates check runs per workflow run, so a fast workflow (the CLA check) can be green before a slower one has created its runs at all, and the rollup then holds one green check on a PR whose CI has not started. So the same call reads `baseRef.branchProtectionRule.requiredStatusCheckContexts` and `requiredChecksReported` folds only when every required context is present in the rollup and passing. Read it off `baseRef`, never off `Ref.refUpdateRule`: that field reports the rules AS THEY APPLY TO THE VIEWER, so on a repo where the viewer is an admin and `enforce_admins` is off it answers an empty list while the branch really requires five, which is empty for exactly the viewer this probe serves. A `null` rule (a branch with no classic protection; a repo on rulesets answers `branchProtectionRule: null`) falls back to the rollup alone. Azure DevOps has no counterpart: its bypass is a security-namespace permission ("Bypass policies when completing pull requests") and is out of scope.
- All four `gh pr` fields ride the same `gh pr list` / `gh pr view` call, so they cost no extra call on the branch and number tiers. `statusCheckRollup` is a per-check-run array on every PR in the list (about 7 KB for a PR with 26 checks), the price of telling "still running" apart from "failed"; the list's `--limit 30` and a 10 MB `maxBuffer` bound it. The commit tier's REST payload (`repos/{owner}/{repo}/commits/{sha}/pulls`) carries none of them, so those items omit the verdict, never probe the bypass, and the linker preserves the stored one.
- `disambiguate` picks the best candidate for inferred (branch / commit) matches: it drops fork (cross-repository) PRs, restricts to PRs whose head ref matches `branchHint` (returning null rather than guessing when SEVERAL non-matching candidates remain, but keeping a LONE one), then prefers open/draft, then a matching base branch, then the most recently updated. `resolveByNumber` bypasses this guard because an explicit number is unambiguous.

  Keeping the lone non-matching candidate is deliberate, not an oversight in the hint rule. It is the anchor for a Done task whose branch was renamed and pushed under a different head ref, which is the case the commit tier exists for; the two filters below are what reject a wrong candidate.
- `resolveByCommit` filters the candidate pool twice before disambiguating, because `gh api commits/<sha>/pulls` returns every PR whose head branch contains the commit - including one that merely branched off the same base tip and therefore inherited it:
  - drop any PR whose merge commit IS the resolved commit, so a fresh worktree sitting on the base branch's tip is never magneted onto the last-merged sibling PR;
  - drop any remaining PR whose OWN base branch already contains the commit (`isShaContainedInRef` in `src/main/git/worktree-head.ts`, run against `origin/<baseRefName>` and falling back to the local ref). `baseRefName` already rides along on the REST response, so this costs a local `rev-list`, not an API call.

  The second filter exempts `MERGED` candidates: a merged PR's own commits ARE in its base afterwards, so containment cannot separate "this task's work, now merged" from "inherited base history" - the merge-commit filter covers that shape instead. When the base ref is not fetched locally the probe is undetermined and the candidate is kept, so on its own an unfetched ref costs a mislink guard rather than an existing badge.

  One caveat, currently unresolved. Because the filter runs BEFORE `disambiguate`, dropping a proven-contained sibling can leave a kept-undetermined candidate as the LONE survivor. It then slips past the hint rule's ambiguity guard, which only returns null when MORE than one non-matching candidate remains, so a candidate never verified as its own work can win a comparison that previously returned null. Whether an undetermined survivor should still count toward that ambiguity threshold is an open question, not a settled trade-off.

**Concurrency + error translation.** All resolves run through a global `p-queue` capped at `GH_CONCURRENCY = 3`, so a multi-card drag or board-load burst cannot fan out into dozens of concurrent `gh` processes. The `viaGh` wrapper translates `GhUnavailableError` into `PRResolverUnavailableError` and `GhTransientError` into `PRResolverTransientError`, keeping the generic layer free of provider-specific error types.

**Ownership.** `matchesRemote` claims any host label containing `github`, so `github.mycorp.com` (GitHub Enterprise) keeps resolving. KNOWN GAP: GHE hosted on a name with no `github` in it (`ghe.corp.example`) no longer resolves PRs. Before the ownership gate this connector ran on every remote and would at least have tried; the failure is now diagnosable, because the thrown message names the unmatched remote URL. A per-project list of extra hosts is the follow-up.

**Repo mismatch is not an auth failure.** In a non-GitHub repo `gh` exits 1 with "none of the git remotes configured for this repository point to a known GitHub host. To tell gh about a new GitHub host, please use `gh auth login`". That message ends with `gh auth login`, so `classifyGhError`'s auth pattern used to match it and the UI told the user to re-login while `gh` was working perfectly. `ghErrorToThrow` now tests for the mismatch FIRST (ordering is load-bearing) and reports the real reason. It stays classified `unavailable`, not `not-found`: with the ownership gate this is only reachable when our own remote read says GitHub owns the repo and `gh` disagrees (a submodule cwd, an `insteadOf` rewrite, a host alias), and `gh` did not run cleanly there, so a clean `not-found` would let the linker clear the link.
