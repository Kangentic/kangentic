# PR refresh and scheduler

`src/main/pr/pr-linking.ts` decides what each resolve writes. `src/main/pr/pr-refresh.ts` and
`src/main/pr/pr-refresh-scheduler.ts` decide when a linked PR is checked again. How a resolve finds
the PR in the first place is in [PR linking](pr-linking.md).

## Persist and degrade behavior

- **Auto triggers** (non-force) skip terminal `merged` / `closed` PRs (they cannot change) and coalesce rapid re-resolves through a per-task 60s throttle (`RESOLVE_TTL_MS`, a bounded `Map` pruned on each run). Explicit user/agent actions pass `force: true` to bypass both. The `pr-candidate` signal passes `bypassThrottle: true` to skip only the coalesce: the agent's own PR command just finished, which is the strongest hint there is, and it routinely lands inside the window an idle resolve stamped after the push that preceded it (push, turn ends, `gh pr create`); coalescing it away left the card unlinked until the next idle or sweep. A merged or closed PR is still left alone, since a `gh pr view` on a finished PR is not news.
- **Degradation.** When the resolver throws `PRResolverUnavailableError` or `PRResolverTransientError`, the linker records a `resolver-unavailable` / `transient-error` status, falls back to `detectPR` on any provided scrollback (url+number only), preserves a known state when the URL is unchanged, and logs a hint. A degraded resolve never clears an existing link.

  The hint is logged once per distinct REASON, not once per run: `resolverUnavailableHintsShown` is a bounded `Set` keyed on the error message, capped at 32, evicting the single oldest entry when full (`Set` preserves insertion order). A single process-lifetime boolean was wrong once a repo could be unowned - the first sweep over a project no connector claims burned the latch and permanently suppressed a genuinely different later hint, such as "gh is not installed", for every other project. Eviction is one entry rather than a wholesale clear because clearing discards every already-warned message at once, so the next sweep re-warns all of them and a workspace that keeps crossing the cap settles into a clear-then-restorm cycle.
- **Confident not-found.** When the resolver ran cleanly and matched no PR yet the task still carries a link, the linker clears `pr_url` / `pr_number` / `pr_state` / `pr_merge_readiness` atomically so a stale `merged` never lingers. A link-time resolve (`preserveLinkOnNotFound`) is the one exception: a resolve fired BY a link write must never undo that write, so a URL that matches nothing (typo, cross-repo, private) keeps its link with a null state. The non-force sweep clears it on a later pass, but only once the task leaves a To Do lane AND still carries one of the sweep's own anchors: `isEligibleForRefresh` checks the lane first, then requires a `pr_number`, a live `worktree_path`, or a `pushed_branch` outside a Done lane (the Done gate keeps the sweep bounded, since `pushed_branch` survives Done and a Done task that never linked would otherwise be swept forever). A preserved link that has none of these (a URL naming no PR number, on a task with no worktree and no recorded push) is never eligible, so in that shape only an explicit refresh clears it. An explicit refresh (kebab, `link_pr`) leaves the flag unset and still clears.
- **SHA backfill.** It opportunistically persists the freshly-read worktree HEAD SHA so the commit anchor (Tier 3) and the remote-tip anchor (Tier 6) are available later, after the worktree is reclaimed on Done. The same write carries any `pushed_branch` Tier 6 established.
- **Merge readiness is preserved on undetermined, and held through a pending answer.** `pr_state` never needed either rule because every tier can determine a state; readiness cannot be determined by the commit tier on either provider or by the scrollback scraper. A resolve whose connector omits `ResolvedPR.mergeReadiness` keeps the stored `pr_merge_readiness` while rewriting the other three columns, exactly as a resolve that never reached Tier 6 keeps `pushed_branch`; the scrape fallback keeps it only when the scraped URL equals the stored one, like `pr_state`, and a link that moved to a different PR starts from null. A platform `unknown` on a determined verdict (`ready` / `blocked` / `conflicting` / `queued` / `running`) of the same open PR is HELD rather than written: GitHub answers `UNKNOWN` for a few seconds after every push while it recomputes, and Azure's `succeeded` is `unknown` whenever the policy call gave no readable answer, so writing it on first sight would blank the card's chip for a refresh interval and then restore it. The linker keeps the stored value and re-polls (`PENDING_VERDICT_RETRY_DELAYS_MS`, 5 s then 20 s, forced so the 60 s throttle does not swallow it, one timer in flight per task, `unref()`'d, and cleared by the scheduler on project switch and shutdown, by `cancelVerdictRepollsForTask` when a To Do move forgets the PR, and when a re-poll finds its task deleted); only when that budget is spent does `unknown` land, which is what lets a chip clear once its host really has stopped answering (an Azure PR whose policy call started failing after it read `ready`). `queued` and `running` are answers, not holds: they write straight through, and then re-poll (see "In-flight verdicts re-poll" below). A terminal PR is never held, since the chip does not render readiness there. `unknown` over null writes immediately, so "asked, no verdict yet" is recorded and distinguishable from never checked. A readiness-only change counts as a link change: it writes, notifies the renderer on `TASK_PR_LINK_CHANGED`, and returns `linked`.
- **In-flight verdicts re-poll.** A `queued` or `running` verdict expires when CI finishes, not when the sweep next ticks. Left to the background refresh, a card read `running` for up to a whole refresh interval after its last check completed. An agent going idle right after CI could not rescue it either, because the sweep's own resolve seconds earlier had stamped the 60 s coalesce. That shipped: PR #479's pill lagged 2m47s behind its last check, and only an incidental prompt kept it under 5 min. So while an open PR's PERSISTED verdict is in flight, the linker re-asks every `IN_FLIGHT_VERDICT_REPOLL_MS` (30 s) with `bypassThrottle`. This holds whichever trigger wrote the verdict.
  - **Scope.** One timer per task, `unref()`'d, cleared with the pending-verdict re-polls (and per task, by a To Do move that forgets the PR or by a deleted task, through `cancelVerdictRepollsForTask`) on project switch, config change, and shutdown. Drafts are excluded (the chip does not render readiness there), and so are terminal PRs. A resolve the 60 s coalesce swallows still arms the chain from the stored row. Without that, the on-open sweep after a switch-back (or the re-arm after a config change) lands inside the window the last re-poll stamped, and the card waits a whole refresh interval again.
  - **Budget.** A streak is bounded by `IN_FLIGHT_VERDICT_REPOLL_BUDGET_MS` (30 min) from its first in-flight answer. The bound is sticky: a spent streak stays spent until the verdict leaves the in-flight states, so a PR stuck `queued` with no runner does not start a fresh chain on every sweep. The budget is per streak, not per PR: the cancel on a project switch, switch-back, or config change drops spent streaks along with live ones, so each of those starts a new 30 min budget for any PR still in flight.
  - **Composing with the unknown hold.** GitHub's real sequence is `running`, a few seconds of `UNKNOWN` while it recomputes, then `ready`. The two re-polls keep separate state, and a hold running mid-chain leaves the streak and its budget alone. The chain follows the persisted row rather than the raw answer, so a degraded resolve (which keeps the stored verdict) keeps re-asking within the budget, and a confident-not-found clear ends it.
  - **Background refresh off.** `PRLinkDeps.repollInFlightVerdict` is set only when `git.prAutoRefresh` is on (`prRepollInFlightFromGitConfig`), so a project with background PR refresh off gets no background polling from this either. `linkPR` reads it off the project config, and the MCP command context reads the same mapping through `getPrRepollInFlight`, so an agent's own link write (`create_task` / `update_task` with a PR, or `link_pr`) arms the chain too. It has to: during `/pull-request` the agent links its PR and then waits on CI inside one turn, so no idle arrives to arm it.
  - **Re-poll writes go out quietly.** A timer-driven re-poll resolves with the scheduling caller's deps, and `link_pr` announces its own call as "Task updated by agent". `PRLinkDeps.onRepollLinked` replaces `onLinked` for both kinds of re-poll, and `link_pr` sets it to the quiet `TASK_PR_LINK_CHANGED` channel, so a verdict that flips when CI settles minutes later is not announced as the agent's update.
  - **Cost.** On GitHub, one `gh pr view` per in-flight open PR per 30 s. Once CI has created its runs the bypass probe does not fire mid-chain, because its gate needs a `passing` rollup. In the minute or two before that, a review-required PR whose rollup holds only already-green checks (the `queued` case in the GitHub connector section) does pass that gate, so each re-poll there also spends the probe, plus the required-checks read until its 10 min cache is warm. Azure's policy fold also produces `queued` / `running`, so an in-flight Azure PR costs an `az` call per 30 s, plus the policy call.
  - **Log lines.** Each streak start is logged once (`checks in flight ... re-polling every 30s`), and so is a spent budget, so a lag report can be measured from the log instead of inferred.

## The on-open sweep and the queue

Two passes keep a project's PRs current, and both re-resolve through the `linkPR` backbone (unchanged, non-force). That refreshes an already-linked PR's state and merge readiness (so an off-app merge/close, a review, or a failed check shows on the board) and discovers a PR for a still-unlinked task with a live worktree (e.g. an agent created the PR mid-session on a renamed branch and no other trigger caught it).

- **On open**, `refreshProjectPRs` checks every eligible task once, sequentially. It runs whatever `git.prAutoRefresh` says.
- **After that**, with `git.prAutoRefresh` on, a queue keeps each PR current on its OWN clock. A PR falls due `PR_REFRESH_INTERVAL_MS` (2 min) after its last check, and `pickNextDuePR` takes the longest-unchecked due PR first (a PR never checked this session counts as the oldest). The queue checks one PR at a time and waits `PR_REFRESH_MIN_GAP_MS` (10 s) between the end of one check and the start of the next, so the load is capped at 360 checks an hour however many PRs are open. Past 12 open PRs each PR's interval stretches instead of the cost growing. With nothing due, the queue sleeps until `nextPRDueAt`, and looks again at least once an interval so a task that just gained a worktree or a PR joins it.

The clock is the PR's, not the queue's. `linkPRForTask` stamps `lastPRCheckAt` after its throttle and terminal gates, so ANY check resets it: the queue, the 30 s in-flight re-poll, an agent's `gh pr create`, a column move, a manual "Refresh PR". A PR checked a moment ago is not checked again. The sweep this replaced fired every PR back to back each interval (`git.prRefreshIntervalMinutes`, default 5), which spent the whole budget in one burst and re-checked a PR CI had just settled.

Readiness changes far more often than state (every base push, review, and CI run), so a `ready` chip is only as fresh as the PR's last check or the task menu's "Refresh PR"; the chip's tooltip says so, and the hold-and-re-poll rule above keeps it from blanking between checks. The exception is a PR whose checks are in flight, which the in-flight re-poll above refreshes every 30 s until CI settles. Each open Azure PR whose preview merge succeeded costs a check a second `az` call (about a second). With `git.prBypassCountsAsReady` on (the default), each open GitHub PR still waiting on a required review, `BLOCKED` or `BEHIND`, costs a check a second `gh` call (the GraphQL bypass probe, milliseconds each); a PR with a check failed or running costs nothing extra. Whatever the setting says, a `BLOCKED` or `BEHIND` PR whose rollup has not already answered also costs the required-checks read, one `gh api graphql` per repo and base branch every 10 minutes. Toggling either PR setting restarts the scheduler and runs the on-open sweep at once, but the per-task 60 s coalesce still applies, so a task resolved within the last minute picks the change up on its next check or on "Refresh PR".

A task is eligible when its PR can still change or be found: a non-terminal linked PR (`pr_number`), a live worktree (`worktree_path`), or a recorded `pushed_branch` outside a Done lane (the sweep resolves the Done lane ids alongside the To Do ones for that gate; `pushed_branch` survives Done, so without it a Done task that never linked would be swept forever). Terminal `merged` / `closed` PRs are skipped first, as are tasks in a To Do lane (To Do resets the task, so there is no PR to link there - the same gate `autoLinkPRForTask` applies to every implicit trigger). Both gates are for IMPLICIT triggers only: the link-time resolve applies neither, since a caller that just wrote a PR link has named the PR explicitly, whatever lane the task sits in. `head_sha` is deliberately not an anchor here (nearly every historical task has one, which would make the sweep unbounded), and neither is a PR URL in the description (see the ladder above). The sweep is sequential and best-effort: a per-task failure is swallowed, and the backbone's `onLinked` pushes `TASK_PR_LINK_CHANGED` so cards update live without toasting (a pass that finds N changed PRs would otherwise raise N "Task updated by agent" toasts for work no agent did).

## The scheduler

`prRefreshScheduler` keeps a single active queue (Kangentic focuses one project at a time):

- `startForProject(context, project)` tears down any prior queue, defers the on-open sweep off the IPC critical path (`setImmediate`), and, when `git.prAutoRefresh` is on, arms the queue from the sweep's `.finally`, so the queue never races the sweep for the same unchecked PR. It is called on every `PROJECT_OPEN` (cold restart and warm switch-back) and after a config change (`CONFIG_SET_PROJECT_BY_PATH`). There is no system-resume caller: `powerMonitor`'s suspend handler only tracks the heartbeat.
- `stop(projectId?)` clears the active timer and the check stamps. With a `projectId` it no-ops unless that project owns the active queue; with no argument it always stops (shutdown / unconditional). Called on project switch/delete and on shutdown. It also calls `cancelPendingVerdictRepolls`, which drops both kinds of per-task re-poll (the unknown holds and the in-flight chains). A switch-back's on-open sweep re-arms any chain that still applies. Each tick also prunes the stamps of tasks that left the queue (merged, moved to To Do, deleted).

`git.prAutoRefresh` replaced `git.prRefreshIntervalMinutes`. `legacy-git-keys.ts` reads the old key once on load: a saved interval reads as on, `null` or `<= 0` as off, and the old key is dropped from the file.

Timer-leak safety: each `setTimeout` is created outside `runWithProjectLogContext` (each check wraps its own work inside it, and the sweep's handlers attach outside the run, since a promise reaction takes the async context current when it is attached), is `.unref()`'d so it never blocks a clean quit, and is explicitly cleared on switch/delete/shutdown. A stale-switch guard skips a check whose project is no longer focused.

The background remote-fetch scheduler (`src/main/git/git-fetch-scheduler.ts`, documented under [Background remote refresh](../../worktree-strategy.md#background-remote-refresh)) mirrors this lifecycle exactly and is started, re-armed, and stopped at the same four sites.
